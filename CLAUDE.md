# Overview

This is a PhD project about Security of Software Engineering on Solidity Smart Contracts.
The projet aim to analyze whether the vibe code of Solidity smart contracts make the contracts less secure than human did.

Use docker to create evironment for running the executables PoV.

## Writing rules

1. **Plain English, written the way it would be spoken.** Short sentences, clear subject, one idea per sentence. Use the ordinary word: "use" not "leverage", "shows" not "surfaces", "we took it out" not "it was excised from the pipeline". Avoid stacked noun phrases and ideas joined with slashes. Never compress an idea into a dense phrase the reader has to unpack — write the extra sentence instead, even though the paragraph gets longer. Test: read the paragraph aloud. If you would not say it that way to a colleague standing at a whiteboard, rewrite it.
2. **No invented vocabulary.** Do not coin terms. Do not build composite nouns that do not already exist in the field. Do not label an idea with a metaphor and then reuse the label as if it were a term. No "verification surface", no "oracle-completeness debt", no "trust flywheel", no quotation marks around a name you made up two sentences earlier. Real terms of the field are expected and welcome — reentrancy, held-out set, proof of vulnerability, taint analysis, differential testing — because a reader can look them up. An invented term cannot be looked up, so it costs the reader time and hides how much you actually understand. When an idea has no accepted name, describe it in a sentence: not "the hint-leak problem", but "the prompt names the vulnerable function, so the score measures repair and not detection".
3. **File, tab, and column names carry what they contain.** "the benchmark inventory (`extraction/benchmarks.md`)", not the bare path. Spreadsheet cells are named as well as addressed: "the *Oracle type* column in the *Extracted studies* tab".
4. **Slides obey the same rules.** No index-only cells; each slide readable on its own.
