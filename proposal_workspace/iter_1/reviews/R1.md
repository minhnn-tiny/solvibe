# Review R1 (SE PC member: ICSE, FSE, ASE)

Proposal reviewed: `proposal_workspace/iter_1/proposal.md` (version 6).

What I checked besides the proposal:
- the literature review (`proposal_workspace/lit_review.md`);
- the RQ1 simulation code (`tools/power_sim_v7.py`) and its results file (`tools/power_results_v7_rq1_calibration.txt`);
- the eight-task pilot report (`docs/pilot/pilot_results.md`);
- the 144-run repair study report (`docs/pilot/repair_input_study_results.md`);
- the control-group note for finding 63008 (`pilot/tasks/63008/control_group.md`) and its agent results file (`pilot/tasks/63008/feature_tasks/results.md`).

## Summary

The proposal compares AI coding agents with human developers on audited Solidity code. An agent rewrites one function body inside a fixed audited snapshot. The human baseline is the historical function in that snapshot.

Functions are drawn by a probability sample from two groups. One group holds functions linked to a High or Medium audit finding. The other holds all other eligible functions. A weighted estimator combines the two groups.

A flaw counts only if an executable proof of vulnerability (PoV) shows it, and if replacing only the target function with a correct version removes it. Every output, human or agent, gets the same fuzzing campaign and the same two LLM reviews. Every validated PoV is replayed on every implementation of that function.

There are four research questions:
- RQ1 is the main weighted comparison.
- RQ2 is a factorial experiment. It crosses repository tests that assert the vulnerable behaviour (fault-enforcing tests) with permission to run those tests, during writing and during PoV-guided repair.
- RQ3 varies the wording of the request.
- RQ4 checks the automatic labels against two paid auditors.

The plan targets 250 to 300 functions from 25 to 30 protocols and up to 12,120 agent runs in 12 months. The primary venue is the ICSE research track.

## Strengths

1. **It fixes a real selection problem in prior work.** SecureVibeBench, SusVibes and Foresight-SWE build every task from a place where a human failed. They cannot say whether agents add flaws in code that humans wrote correctly. Sampling unflagged functions with known probabilities and weighting them back to the population is the right fix. To my knowledge, no verified paper in the literature review does this with executable evidence.
2. **The evidence standard is higher than in existing human-versus-AI comparisons.** Sajadi et al. (https://arxiv.org/abs/2507.02976) and SolAgent (https://arxiv.org/abs/2601.23009) count static warnings. Here a flaw needs a PoV, a target-only correction and a passing legitimate-behaviour suite. Compilation failures stay in the denominator and never count as avoided vulnerabilities.
3. **The proposal is honest about its limits.** It says a null result does not show equivalence. It says injected tests do not show how often the condition occurs in real repositories. It says pilot contrasts do not estimate an interaction.
4. **The pilot is real and checkable.** The eight PoVs pass on the vulnerable commit and fail on the fix. The repair study shows something concrete: repairs that block the shown PoV while a held-out attack still steals rewards. In the control group, a new vulnerability was confirmed by two PoVs that pass on the agent version and fail on the human version.
5. **The simulation numbers match the code.** The calibration values in Section 6.3 match the results file: 0.046 at 0.025, 0.051 at 0.030, then 0.041 and 0.959 on validation.
6. **RQ2 asks an SE question that matters.** Tests act as specifications. This question asks whether running tests that encode a developer's mistake pulls an agent toward that mistake. That matters for any team that hands an agent its existing test suite.
7. **The released benchmark would be useful.** It would include threat-model records, acceptance specifications, frozen requests, PoVs and hidden variants for real DeFi code. The SE and security communities both lack this.

## Weaknesses

1. **The two authors do not face the same search for flaws, despite the claim that they do.**
   Contribution 3 says "Discovery budgets are matched". But every human flaw in group V was found by a professional audit, and a PoV was then built from the audit report (Section 5.7). The agents' code never gets an audit. Replaying the audit PoV only catches a flaw the agent copied. Any *different* flaw in agent code can only be found by the cheaper automatic search: fuzzing, two LLM reviews and a capped number of confirmation attempts. Over the whole population, human code is therefore searched by the audit plus the automatic search. Agent code is searched by the automatic search alone. This bias makes agents look safer, and it most affects the paired counts of "avoided" human vulnerabilities in group V.
   The pilot shows that the automatic search's recall is unknown and varies a lot. In the repair study, Claude Opus 5.5 reported all seven confirmed flaws and GPT-6.1 Sol reported two (`docs/pilot/repair_input_study_results.md`, Section 6). In the control group, "A first reading of the 8 Aider and OpenHands control patches found no security flaw. The blind LLM security review below found that this was wrong for one patch" (`pilot/tasks/63008/feature_tasks/results.md`).
   Required change: Run the automatic search, without the audit report, on every sampled human group V function. Report the share of audit findings it finds again. Then add a co-primary RQ1 estimate in which a flaw counts for either author only if the automatic search finds it. Report audit-only discoveries separately.

2. **The "human" baseline may itself be AI-assisted, and the threats section does not mention this.**
   The proposal's own worked example is affected. The note for finding 63008 says: "The Angstrom repository has had a `CLAUDE.md` since its first commit (`621bef2`, 2025-08-29)... `661468b` came three days later... we cannot tell which lines a person typed. This weakens the human-versus-AI comparison for this finding" (`pilot/tasks/63008/control_group.md`, Section 7). The same note found agent instruction files in other pilot repositories. Section 2 cites a survey in which 58% of Solidity developers use AI tools daily. Section 5.1 prefers recent findings to reduce training exposure, which makes AI-assisted "human" code more likely. Section 6.8 lists no threat about this. If part of the baseline was written with an agent, RQ1 compares agents with partly-agent code. The title's claim about "human developers" then does not hold.
   Required change: For every sampled function, record at the commit that introduced the human code whether there are signs of AI assistance: agent instruction files, AI co-author trailers, or pull-request text. Add this as a threat in Section 6.8. Pre-register an RQ1 sensitivity analysis that keeps only functions with no such signs, and call the baseline "the historical developer implementation" wherever AI assistance cannot be ruled out.

3. **The headline effect sizes have no empirical basis, and a likely smaller effect cannot be detected.**
   About 95% of the population weight sits in group N. The simulation sets the group V share to `EPI = 4 / 79` in `tools/power_sim_v7.py`. So RQ1 is mostly a question about ordinary audited functions. The simulation fixes the human group N rate at `hN = 0.02`. Its "larger" and "middle" scenarios set the agent rate to `hN + 0.13` and `hN + 0.09`. That means agents would add confirmed High or Medium flaws to ordinary functions 5.5 to 7.5 times as often as humans. The only group N evidence is two functions from one commit. One of them is the mirror image of the vulnerable function (`pilot/tasks/63008/control_group.md`, Section 3). At a difference of about +0.04, the minimum power is 0.12 to 0.39 with 25 protocols (Section 6.3). A 12-month study could easily end with an interval that cannot separate a harmful effect from no effect.
   Required change: In month one, run the full RQ1 pipeline on the group N functions of the ten development cases, with all six configurations. Report the observed human and agent rates. Then set the power scenarios from those rates. Also declare a smallest difference of interest, and pre-register an equivalence test (two one-sided tests) against it, so that a null result is still informative.

4. **The core study is too large to be feasible, and a smaller core loses its power.**
   The protected core in Section 8 includes:
   - 25 to 30 threat-model records;
   - Foundry invariant harnesses for each protocol;
   - legitimate-behaviour suites for 250 to 300 functions;
   - PoVs and hidden variants for 50 to 60 group V functions;
   - target-only corrections, reviewed by a person, for every confirmed candidate;
   - two LLM reviews for every output;
   - 4,500 to 6,000 RQ1 runs;
   - 100 hours of paid expert review.

   Section 10 gives four months (months 2 to 5) to build all of this. The proposal admits the pilot "does not establish the full labor cost". The pilot also shows that many steps still lack the person who is meant to do them: "No person has reviewed the repairs yet" (`docs/pilot/repair_input_study_results.md`, Section 10), and the Claude subagents did the review that the design gives to a person. Three of the eight pilot tasks had no project test for the target function at all (`docs/pilot/pilot_results.md`, Section 4.2), so their legitimate-behaviour suites would have to be written from scratch. The order of reductions removes RQ3 and parts of RQ2 first. It never reduces RQ1, yet RQ1 is the most expensive part. With fewer than 25 protocols, Weakness 3 gets worse.
   Required change: Add a costed plan. It should give measured person-hours per protocol and per function from at least three pilot cases built to the full Section 4 and Section 5 standard, with every human-review step done by a person. Then state the smallest RQ1 the student can build in months 2 to 5, and the precision that size gives.

5. **The primary endpoint counts broken code that the project's own tests would reject.**
   The primary endpoint is K = CV. It counts any compiled output with a confirmed flaw, even when it fails the functional tests. The pilot's only added vulnerabilities are both of this kind. Both control-group flaws come from the same early return in `reset(TickIteratorUp)`, and both versions fail the repository's own `test_iterateUp_emptyRange` (`pilot/tasks/63008/feature_tasks/results.md`). A developer who runs the existing tests would never merge them. The practical question for SE is how often an agent produces code that passes the tests but can be exploited. That is the secondary endpoint D = CLV, and it is also how SusVibes reports its headline result. The simulation does not model D at all: "Compilation and functional outcomes are not generated separately" (Section 6.3).
   Required change: Make D co-primary with K. Extend `tools/power_sim_v7.py` to generate the functional outcome together with the security outcome, and report power for D before the month-two freeze.

6. **The primary hypothesis family is built from the pilot's convenience configurations, not from tools practitioners use.**
   The six configurations in the Holm family pair Aider, OpenHands and Codex CLI with GPT-5.4-mini or Claude Sonnet 4.5 (Section 5.9). Two of them use a translation layer that the authors say does not measure "vendor-supported product performance". In the pilot, Aider in its default setup "cannot run the compiler" and "sees only the file it must change" (`docs/pilot/pilot_results.md`, Sections 1 and 4.3). The two current, vendor-supported agents run only on "a declared common subset" and sit outside the primary family. By the time of an ICSE submission, findings about a mini model and a model from 2025 will tell practitioners little. Reviewers will ask why the confirmatory claims rest on them.
   Required change: Make the vendor-supported current agents (Claude Code and Codex CLI with current models, versions pinned at month two) the primary family and run them on the full RQ1 sample. Move the translated and pilot configurations to a secondary, exploratory family.

7. **Tests written against the human function can steer the agent toward the human's choices, so RQ1 does not separate the agent's own judgement from test-fitting.**
   Section 4 says the agent "may see code and tests written after the human originally implemented the function". In the audited snapshot, those tests pass on the human function. So they encode its behaviour, including its mistakes. Finding 63008 shows this happens: four tests assert the faulty boundary. In the repair study, "Almost every OpenHands run opened or ran that test file". RQ2 studies this effect under control. RQ1 leaves it uncontrolled, and it pushes agent and human outcomes toward each other in both groups.
   Required change: When a task is built, record whether the workspace contains tests that directly call the target function. Pre-register RQ1 estimates split by this property, which is fixed before any agent runs, as a secondary analysis.

8. **Requiring one function to carry the blame may quietly drop the cross-function logic bugs that cost DeFi the most.**
   A flaw counts only when "replacing only that function with an independently justified correction removes the violation" (Section 4). Defects caused by unchanged surrounding code are excluded. The pilot already had a two-function task: 63185 needs both `transferOwnership` and `acceptOwnership` (`docs/pilot/pilot_results.md`, Section 3). The fix for 63008 also changes `_advanceToNextUp` (`pilot/tasks/63008/control_group.md`, Section 5). Zhang et al. (ICSE 2023, https://raw.githubusercontent.com/ZhangZhuoSJTU/Web3Bugs/main/papers/icse23.pdf) show that most exploitable smart-contract bugs are logic and accounting bugs. Many of those span functions. If such findings become "unresolved" or are left out of the eligible group V functions, then RQ1 describes a narrower set of bugs than the title suggests.
   Required change: In the month-one frame refresh, report how many High and Medium findings have a fix that touches more than one function. Then state, before sampling, one rule for them: either sample the set of changed functions as one unit, or exclude them and report their weighted share as a limit on the population.

9. **The related work leaves out the closest Solidity design and a large unconditional comparison. It also overstates how new the injected-test experiment is.**
   SolEval (EMNLP 2025, https://aclanthology.org/2025.emnlp-main.218/) already regenerates function bodies in 28 real Solidity repositories and reports a vulnerability rate based on Slither (literature review, Section 5, row 14). That is the closest earlier setup to group N. Cotroneo et al. (ISSRE 2025, https://arxiv.org/pdf/2508.21634) compare more than 500,000 human and AI functions paired by docstring. Neither appears in Section 7 or its table. RQ2's primary family uses only injected tests. Those tests change an assertion so that it disagrees with correct behaviour, and the experiment varies whether the agent can run them. ImpossibleBench (ICLR 2026, https://arxiv.org/abs/2510.20270) already changes tests to contradict the specification and varies access to them and feedback from them. Section 7 calls RQ2 "a controlled extension of this prior work", but the table does not say what is new in technique.
   Required change: Add SolEval and Cotroneo et al. to Section 7 and its table. For RQ1 and for RQ2's injected group, write one sentence each that names the delta against SolEval and against ImpossibleBench, in terms of technique, not only domain.

10. **RQ2's practical relevance depends on how common fault-enforcing tests are, and the design throws away a nearly free estimate of this.**
    Section 6.4 says the RQ2 sample "is not a prevalence estimate for natural fault-enforcing tests". But the group V functions in RQ1 are a probability sample. For each of them, the screening in Section 5.8 already checks whether a repository test passes on the vulnerable code and fails on the correction. Without a prevalence figure, an SE reader cannot tell whether RQ2 studies a common hazard or an odd case. The literature review gives only weak indirect numbers, for example 3% of fixed test bugs in Apache projects (Vahabzadeh et al., ICSME 2015).
    Required change: Report the weighted share of sampled group V functions that have at least one natural fault-enforcing test, with a confidence interval, as a descriptive RQ2 result.

11. **The proposal reports the pilot's most striking exploratory contrast without the results that point the other way.**
    Section 3 reports "10 of 12 runs without execution and 2 of 12 runs with a terminal". The repair study report says: "Neither primary contrast shows a difference". For Codex, adding a full terminal to the shown-test tool changed nothing: 6 of 12 against 6 of 12. Both points are in `docs/pilot/repair_input_study_results.md`, Sections 1 and 4. The blind review was done by Claude subagents, not by a person. A PC member who reads the pilot report will see that the summary is selective.
    Required change: In Section 3, add the two pre-registered primary contrasts and the Codex P-E1 against P-E2 result. Also state that the repairs have not yet been reviewed by a person.

12. **Four research questions, two of them factorial, will not fit in one ICSE research-track paper.**
    Section 10 plans to "Write and submit the paper" in months 10 to 11. RQ1 alone needs a description of the sampling, an estimator, an attribution procedure and a validation study. RQ2 is a separate controlled experiment with its own sample, tools and mixed model. Packing both into one paper will leave each one too thin for the page limit of an ICSE research-track paper.
    Required change: Plan two papers. One covers RQ1 and RQ4 and goes to ICSE. The other covers RQ2 and goes to a venue such as FSE or ISSTA. Give each paper its own month-two freeze and its own submission date in the timeline.

## Ratings

- C1: concern — Sampling unflagged functions with weights and crossing fault-enforcing tests with execution are new combinations. But RQ1 is close in technique to SolEval, Sajadi et al. and SecureVibeBench, and RQ2's injected group is close to ImpossibleBench (Weakness 9).
- C2: concern — Agent use and DeFi losses are well documented. But the primary endpoint counts code that the project's own tests reject, and the link from per-attempt function rewriting to practice is not argued (Weakness 5).
- C3: pass — The contribution is a measurement design with weighting, target attribution and shared replay, not "apply an LLM to task X".
- C4: concern — The two authors do not face the same search for flaws, and the human baseline may be AI-assisted. Both undermine the main comparison (Weaknesses 1 and 2).
- C5: pass — The attacker, assets, environment and exclusions are explicit and recorded per protocol before agent runs.
- C6: concern — RQs, metrics and baselines are named. But the primary configurations are dated or translated, D has no power analysis, and the effect sizes have no empirical basis (Weaknesses 3, 5 and 6).
- C7: fail — The protected RQ1 core is not costed in person-hours, and it exceeds what one first-year student can build and check in four months of construction (Weakness 4).
- C8: pass — Offline execution, reporting through security contacts, an embargo while deployments remain exposed, and an institutional review check are all stated.

## Questions for authors

1. Of the 43 findings with public history, how many have a fix confined to one function?
2. Which models will be the two LLM reviewers in the discovery step? Are they from the same model families as any agent under test? The literature review cites evidence that LLM judges favour their own outputs (Panickssery et al., NeurIPS 2024, https://arxiv.org/abs/2404.13076).
3. Who writes the security properties and invariant harnesses for group N functions, and how is their adequacy checked before agent runs? For example, do the invariants catch seeded faults?
4. Where does the human group N rate of 0.02 in the simulation come from?
5. In the pilot, the drop in repair success appeared only with a full terminal. RQ2 compares a repository-test tool against no such tool, and neither arm has a terminal. Why do you expect the pilot effect to appear under this narrower manipulation?
6. How will RQ1 treat agent outputs that closely match the human function, such as a near-verbatim recall of public code? Will they count as independent agent attempts in the main estimate?
