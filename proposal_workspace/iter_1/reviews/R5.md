# Review R5 (fresh general PC member), iteration 1

## Summary

The proposal compares AI coding agents with the human authors of audited Solidity code. Each agent rewrites one function body inside a fixed audited snapshot. Functions are drawn with known probabilities from two strata: functions linked to a High or Medium audit finding (V), and other eligible functions (N). A flaw counts only when a PoV shows a recorded property violation and replacing only the target function with a justified correction removes it. The primary estimate is a weighted difference, over all scheduled attempts, between the agents' rate of compiled confirmed-vulnerable outputs and the human rate. Inference uses a delete-one-protocol jackknife that was calibrated by simulation.

A second experiment (RQ2) crosses repository tests that assert faulty or corrected behaviour with permission to run those tests, during writing and during PoV-guided repair. RQ3 varies request wording. RQ4 checks the evaluation against paid blinded auditors. The plan has 25 to 30 protocols, 250 to 300 functions, six primary agent configurations, and about 12,000 agent runs in 12 months.

I checked the claims about the simulation against the RQ1 calibration code (`tools/power_sim_v7.py`), its output (`tools/power_results_v7_rq1_calibration.txt`) and the RQ2 results (`tools/power_results_v5_rq2.txt`). They match. I also checked the pilot claims against the pilot results report (`docs/pilot/pilot_results.md`), the repair input study results (`docs/pilot/repair_input_study_results.md`), the 63008 control group notes (`pilot/tasks/63008/control_group.md`) and the 63008 agent results (`pilot/tasks/63008/feature_tasks/results.md`). The numbers match, but the proposal leaves out some pilot findings that work against it (weaknesses 2 and 7).

## Strengths

- The proposal is unusually careful about what its evidence does not show. It labels pilot results as single-case observations, calls the Moonwell incident unattributed, and says that a non-significant result does not establish safety.
- The sampling design answers a real gap in the conditional designs. Functions the human got right are included with known weights, and failed attempts stay in the denominator. A compilation failure never counts as avoiding a vulnerability.
- The rule for counting a flaw is strict and executable. A PoV must show the violation, a correction to the target alone must remove it, and the correction must pass the legitimate-behaviour suite. PoV results have three values, so "unresolved" is not silently read as "safe".
- The statistics are real work, not decoration. Calibration and validation use separate random streams. The offsetting null scenarios are balanced within each simulated study, and the code asserts this. The proposal reports Monte Carlo intervals and states the simplifications that remain.
- The 63008 pilot is concrete and reproducible. Three PoVs judge the vulnerable function. A shallow repair blocks the shown PoV while the held-back P3 still takes 48.88 ETH. Two agent-written control functions have new flaws confirmed by PoVs.
- RQ2 tests that the execution restriction is enforced before any run, and it records which tools each agent actually used.
- Exploits run offline. There is a disclosure path and an embargo rule for deployed copies.

## Weaknesses

1. **The human code gets a round of discovery that the agents never get: the audit itself.**
   - Problem. In stratum V, the human's flaw was found by expert auditors, and it counts toward the human rate once confirmed. An agent's flaw that differs from the human's can be found only by Foundry invariant fuzzing and two LLM reviewers. A flaw that an audit would catch but these tools miss is counted for the human and missed for the agent. This biases the difference in the agents' favour. By the proposal's own motivation, this kind of miss is common for logic bugs.
   - Evidence. The abstract says "Discovery budgets are matched". Section 5.10 gives every implementation the same fuzzing, the same two reviewers and the same confirmation budget. Section 6.3 says "The human V-stratum rate is not automatically one. It depends on successful confirmation and attribution", so the audit finding feeds the human rate. Section 2 cites Zhang et al. (ICSE 2023, https://raw.githubusercontent.com/ZhangZhuoSJTU/Web3Bugs/main/papers/icse23.pdf): more than 80% of 516 exploitable bugs were beyond the automated tools studied. In the 63008 agent results, a person's first reading of the control patches "found no security flaw" before the LLM review found one. The pilot review prompt also listed the audit's five known findings, which would give the human's flaw a further head start.
   - Required change: Define the primary RQ1 endpoint using only flaws found by the common procedure, run without the audit findings as input. This procedure is fuzzing, the two reviewers, and replay of every PoV it produces. Use the audit-confirmed human flaws only to measure that procedure's recall, and report the count that includes audit findings as a secondary endpoint.

2. **The human baseline may itself be AI-assisted, and the proposal does not mention it.**
   - Problem. The study takes recent findings to limit contamination, but recent Solidity code is exactly the code most likely to have been written with an AI tool. If part of the "human" code was written with an agent, RQ1 compares agents with agent-assisted humans, and the sign of the difference becomes hard to interpret.
   - Evidence. The 63008 control group notes (`pilot/tasks/63008/control_group.md`, section 7) say: "The 'human' code may have been written with an AI agent. The Angstrom repository has had a `CLAUDE.md` since its first commit." The faulty commit `661468b` came three days later. The same notes find `AGENTS.md` or `CLAUDE.md` files in Ekubo and Wannabet, and a `.cursorrules` file in the Megapot audit copy. Section 2 of the proposal cites 58% daily AI use among Solidity developers [Solidity Survey, https://soliditylang.org/blog/2026/04/15/solidity-developer-survey-2025-results/]. Neither the threats to validity (section 6.8) nor the worked example (section 5.12) mentions this. The worked example is the same function.
   - Required change: Add a recorded, pre-registered screen for evidence of AI tools in each protocol's history up to the target function's introducing commit, such as agent configuration files and AI co-author trailers. Exclude flagged functions from the primary RQ1 estimate, and report the estimate with them included as a sensitivity analysis.

3. **The plan does not fit one first-year PhD student in 12 months.**
   - Problem. Every one of 250 to 300 functions needs work by hand:
     - a threat-model record for its protocol;
     - security properties and a Foundry invariant harness;
     - a legitimate-behaviour suite;
     - a request in which every sentence is checked against a source.

     Every V function also needs an adapted PoV, a hidden variant and a target-only correction. Then every compiled output of about 6,000 RQ1 runs needs fuzzing, two LLM reviews, and confirmation of each candidate with a person deciding it. RQ2 adds 40 to 60 more PoV-validated functions and 4,320 runs. RQ4 adds 100 paid hours plus adjudication. One paper with four RQs is also too much for one ICSE submission.
   - Evidence. The workload table in section 8 gives 12,120 agent runs before calibration. Section 8 says the pilot "does not establish the full labor cost". Section 10 puts all construction in months 2 to 5. The pilot built 8 tasks from 77 candidates, of which 43 had public history. Four of the eight came from one protocol (`docs/pilot/pilot_results.md`, section 3). The 63008 material alone spans reports dated 8 to 20 October, and those reports still say "A person has not yet reviewed the repairs". The order of reductions protects probability sampling, symmetric evaluation and attribution. These are the most expensive parts. Whether the 43 candidates span 25 to 30 eligible protocols is not shown [uncertain].
   - Required change: Commit to a minimal core scope, for example about 10 to 12 protocols, two agent configurations, RQ1 and PoV-guided repair only. Size it from per-task construction hours measured on the month-one development cases, and show the arithmetic that it fits months 2 to 8. Treat the 25-to-30-protocol, six-configuration design as an extension that runs only if the core finishes early.

4. **The request text can decide the V-stratum outcome, and the rule for this case is not fixed.**
   - Problem. The pilot showed that the request decided whether agents rewrote the bug. The main study writes requests from existing comments and documentation, and those sources can describe the vulnerable behaviour. If they do, an agent that follows the request reproduces the bug because it followed its specification, not because it missed a security issue. The proposal records a diagnostic "later" but does not say how such tasks are scored. It also says a task without a coherent acceptance specification is unresolved. This could move an unknown share of V tasks out of the analysis after the requests have been written.
   - Evidence. The pilot results report (section 5.4) gives 13 of 13 compiled runs with the bug when the request described the vulnerable design, against 3 of 15 when it stated the fixed rule, and concludes "this pilot mostly measured whether agents follow the request". In 63008 the `initDown` comment calls the start tick "exclusive" (section 5.12). In the 63008 agent results, OpenHands with Sonnet 4.5 "quotes the `@param startTick The starting tick (exclusive)` comment and concludes the walk is 'exclusive on both ends'". Section 5.5 says the diagnostic "does not trigger rewriting".
   - Required change: Pre-register, before any run, a rule for V tasks whose sources describe the vulnerable behaviour: whether such a task is kept and scored, or marked unresolved. Also pre-register that the V-stratum results are reported separately for requests the diagnostic classes as favouring the vulnerable behaviour, as neutral, and as favouring the corrected behaviour.

5. **The primary agents are not the agents practitioners use, and some are configurations that no vendor supports.**
   - Problem. The six-configuration primary family uses GPT-5.4-mini and Claude Sonnet 4.5 in Aider, OpenHands and Codex CLI. Codex with Sonnet 4.5 runs through a translation layer. Current models appear only as "supported baselines" on a subset. At submission time, about month 11, reviewers will discount conclusions about these models. The pilot itself used stronger models (Claude Opus 5.5 and GPT-5.4) as reviewers than as the agents under test.
   - Evidence. Section 5.9 sets up these configurations. The 63008 agent results say Codex CLI 0.160.1 "has no settings for either model" and warns that its fallback "can degrade performance". In one pilot run, a LiteLLM output cap cut off a Codex with Sonnet 4.5 reply in the middle of a sentence.
   - Required change: Make the primary Holm family the native current configurations, for example Claude Code with a current Claude model, Codex CLI with a current GPT model, and one open scaffold with a current model. Move the translated and mini-model integrations to exploratory analyses.

6. **The primary endpoint counts broken code, and the power analysis assumes perfect detection and large effects.**
   - Problem. The endpoint K counts a vulnerable output even when it fails the functional suite. Such code would usually not be merged. The only pilot evidence of flaws added by agents is of exactly this kind. The simulation generates K directly, with no compilation, functional or detection step. It assumes a human N-stratum rate of 0.02 and agent rates 0.06 to 0.13 higher, with no empirical anchor. Even so, power at a difference of about +0.04 is only 0.12 to 0.47. Missed detections would shrink the observed difference further. In the simulated frames the V stratum is about 5% of the population (`EPI = 4/79` in `tools/power_sim_v7.py`), so the weighted difference is almost entirely the N-stratum difference.
   - Evidence. Section 5.12 says of the two confirmed control flaws: "Both vulnerable implementations also failed a functional test". The 63008 agent results confirm that both fail `test_iterateUp_emptyRange`. Section 6.3 says "Compilation and functional outcomes are not generated separately". Its power table gives "Smaller effect … 0.12 to 0.39" at 25 protocols and "0.20 to 0.47" at 30.
   - Required change: Extend the RQ1 simulation to generate compilation, functional status and detection separately. Take the detection probability from the recall measured under weakness 1. Report power for the endpoint D (vulnerable and passing the functional suite) at the planned allocation.

7. **RQ2's confirmatory claim rests on tests the authors inject, and its motivating pilot contrast is overstated.**
   - Problem. The natural stratum is descriptive only. The confirmatory test uses synthetic assertions. A run in which the agent may execute a test that asserts the bug is expected to reproduce the bug more often, and ImpossibleBench has already measured this kind of test-following. Nobody knows how often audited Solidity repositories actually contain fault-enforcing tests, so the practical weight of the effect is unknown. In addition, section 3 presents "10 of 12 runs without execution and 2 of 12 runs with a terminal" without saying three things:
     - this contrast was exploratory;
     - both preregistered pilot contrasts were null;
     - it compared a full terminal with no execution, not a repository-test tool.
   - Evidence. ImpossibleBench (ICLR 2026, https://arxiv.org/abs/2510.20270) changes tests to contradict the specification and varies test access and feedback. Coding Agents Can Deliver What You Check (ICLR 2027 submission, under review, https://openreview.net/forum?id=gCG1W765UW) varies access to checking tests. The repair input study results report (section 1) says "Neither primary contrast shows a difference" and calls the terminal effect "exploratory, because it was not a primary contrast". There, Codex with the same model succeeded in 6 of 12 runs both with the shown-test tool and with a full terminal. Of the eight pilot tasks, the pilot results report (section 4.2) marks only 63008 as having repository tests that assert the buggy behaviour.
   - Required change: In month one, count the natural fault-enforcing tests across all V functions in the refreshed frame, and report that count as an RQ2 result. The literature review (section 4.5) notes that no study has examined the test suites of audited DeFi protocols in this way.

8. **The title and abstract claim more than the design measures.**
   - Problem. Each agent rewrites one function body inside a mature snapshot. It sees the callers, the tests and code written after the human wrote the function. This is neither how the human built the feature nor how agents are used for "vibe coding". The title, "AI Coding Agents and Human Developers", and the abstract's opening invite a reading the design cannot support.
   - Evidence. Section 4 says "This is a retrospective replacement study … The agent may see code and tests written after the human originally implemented the function." The pilot found that starting from the parent commit "fits only 1 of the 8 tasks" (pilot results report, summary item 8).
   - Required change: Retitle the paper and restate RQ1 as a comparison of function-body replacements in audited snapshots. Remove wording that presents the result as a comparison of AI agents with human developers.

9. **The main novelty claim for RQ1 is already known in principle.**
   - Problem. Section 3 says the distinct question is "the weighted comparison that includes unflagged functions". The idea that conditional designs measure repeated human bugs while unconditional designs measure average differences is already stated in the literature the proposal relies on. Inverse-probability weighting is standard survey practice. What remains is a careful combination of known designs with executable evidence in Solidity.
   - Evidence. Sajadi et al. (https://arxiv.org/abs/2507.02976) and Cotroneo et al. (ISSRE 2025, https://arxiv.org/pdf/2508.21634) compare AI and human code on the same tasks without conditioning on human failure. Guo et al. (https://arxiv.org/abs/2503.11082) contrast bug-prone locations with ordinary code. SolAgent (https://arxiv.org/abs/2601.23009) compares agent and human Solidity on the same files. SecureVibeBench (ACL 2026, https://arxiv.org/abs/2509.22097) runs the same PoV on human and agent code. The literature review (section 4.2) already says: "Designs that start where the human failed measure how often AI repeats a known human bug. Unconditional designs measure average differences."
   - Required change: Make the headline methodological result a direct comparison on the same data. Put the estimate that a V-only design would report (the SecureVibeBench or Foresight-SWE design) next to the weighted estimate, and show whether the conclusion changes.

## Ratings

- C1: concern — The weighted inclusion of unflagged functions and the faulty-test by execution design are careful combinations of known designs (unconditional same-task comparisons; ImpossibleBench), not new techniques or insights.
- C2: concern — DeFi losses are real, but evidence that agents cause Solidity vulnerabilities is thin (one unattributed incident and self-reported AI use), and function-body replacement on older models limits what practitioners can take from the result.
- C3: pass — Attribution by target-only correction, common replay and the weighted design go well beyond applying an LLM to a task.
- C4: concern — The audit gives the human code a round of discovery the agents never get, the human baseline may be AI-assisted, and request wording can decide the V-stratum outcome.
- C5: pass — Attacker, capital, environment, permitted state changes and the exclusion of privileged roles are stated for each protocol, which is adequate for the primary SE venue.
- C6: concern — RQs, metrics, ablations and threats are thorough, but the primary agents are not current, the power analysis assumes perfect detection and large effects, and the confirmatory RQ2 claim rests on synthetic tests.
- C7: fail — About 300 hand-built tasks, about 12,000 agent runs and person-adjudicated confirmation of every candidate do not fit one first-year student in 12 months.
- C8: pass — Offline execution, disclosure through security contacts, an embargo while deployments are exposed, paid experts and an institutional review check are all stated.

## Questions for authors

1. How many distinct protocols do the 43 findings with public history span? How many of those protocols have two V functions that meet every eligibility rule in section 5.2?
2. How many hours did one V task and one N task take to build in the pilot, counting the threat-model record, properties, invariant harness, legitimate-behaviour suite, request checks and PoVs?
3. Will the LLM reviewers in the main study receive the audit's known findings, as the pilot review prompt did?
4. Who writes the "independently justified correction" for a flaw an agent adds to an N function? May the human implementation serve as that correction, and what happens when the human implementation has its own unconfirmed flaw?
5. Since the V stratum is about 5% of the simulated population, will you report stratum-specific differences as co-primary? If not, why does most of the construction effort go to V functions?
6. How does the primary estimate treat agent outputs that are near-verbatim copies of the human code or of the fix? Do they stay in the primary estimate or only in the sensitivity analysis?
7. The pilot recorded tool lists for Codex and OpenHands. How will you verify the RQ2 execution restriction for the supported native agents, whose tools you cannot change?
8. If the common procedure finds new flaws in audited human code that is still deployed, how will disclosure timelines interact with the month-11 submission?

## Overall score

The design is careful and honest, but the plan cannot be finished in the stated time. The core comparison also gives the human code an extra round of discovery and may compare agents with AI-assisted humans. Weaknesses 1, 2 and 3 are the changes that would most raise my score. Weaknesses 4 and 7 are next.
