# Review R3 (evaluation expert), iteration 1

## Summary

The proposal compares AI coding agents with the historical human author of the same Solidity function. Each agent rewrites one function inside an audited snapshot. Functions come from a two-stratum probability sample. Stratum V holds functions linked to a High or Medium audit finding. Stratum N holds the other eligible functions. Every implementation, human or agent, gets the same discovery steps: property fuzzing, differential fuzzing where a reference exists, and two LLM reviewers. A flaw counts only if a PoV shows it, a correction to the target function alone removes it, and the corrected function passes the legitimate-behavior suite. Every validated PoV is then replayed on every implementation of the same function.

The primary endpoint is the weighted difference, per configuration, in the rate of compiled outputs with a confirmed vulnerability (K = C·V). It is tested with a delete-one-protocol jackknife, a t reference, and Holm over six configurations. The level (0.025) and the interval multiplier (1.24) were chosen by simulation. RQ2 is a 2×2 experiment: faulty or corrected repository tests, crossed with permission to run them, during writing and during PoV-guided repair. It is analysed with a logistic mixed model. RQ3 varies request wording. RQ4 compares the automatic evaluation with two paid auditors on about 150 implementations.

I read the proposal and the RQ1 calibration script (`tools/power_sim_v7.py`) with its recorded output (`tools/power_results_v7_rq1_calibration.txt`). I also read the RQ2 simulation (`tools/power_sim_v5.py`) with its output (`tools/power_results_v5_rq2.txt`), and the pilot reports the proposal cites. I reran the RQ1 calibration script, and it reproduced the recorded output exactly. I also ran a few variations of the authors' own simulation functions to test their assumptions. I changed no files. Those numbers appear in the weaknesses below.

## Strengths

1. **The population and the denominators are defined.** Inclusion weights link the sample to a stated eligible population. Every scheduled attempt stays in the denominator. Sampled construction failures are not replaced by easier functions. Compilation failures are recorded as failures, and the proposal says they must not be read as avoiding vulnerabilities.
2. **The standard for confirming a flaw is strict.** A flaw needs an executable PoV, a correction to the target function alone, and a passing legitimate-behavior suite. A PoV has three possible results, and an exit code is not treated as a verdict. The pilot shows why this matters. In the repair study, 7 of 64 repairs that passed every frozen check still had a flaw that a test confirmed (the repair study results, `docs/pilot/repair_input_study_results.md`, section 1, item 7).
3. **The statistical plan is fixed in advance, and the code is public.** The offsetting nulls in the v7 script are exactly zero in each simulated study, and the script checks this. Calibration and validation use separate random streams. The proposal reports low power for differences of +0.04 openly. It also says a nonsignificant result does not establish equivalence.
4. **The RQ2 execution factor is controlled with care.** Both arms get the same read, search, edit and build tools. Tests run only through a tool that sits outside the writable workspace. Enforcement is checked before any run. Tool use and denied requests are recorded, and the analysis follows the assigned permission.
5. **Scope decisions have a fixed order.** There is a gate at month two and a declared order of reductions. The proposal commits not to pick convenient PoVs and not to stop early.

## Weaknesses

1. **Common replay gives agent flaws more chances to be found than human flaws.**
   Problem: each function has 18 agent attempts across the six experimental configurations, and one human implementation. If several agent attempts share a flaw, any one of their discovery campaigns can find it, and replay then credits it to all of them. A flaw that only the human wrote has a single campaign. Suppose one campaign finds a given flaw with probability 0.3. A flaw present in 9 of the 18 attempts is then found at least once with probability 1 − 0.7⁹ ≈ 0.96, and it is credited to all 9 attempts. A flaw only the human wrote is found with probability 0.3. This gap comes from how the flaws are measured, not from how secure the code is, and it pushes Δ^K upward.
   Evidence: section 5.10 says "Every validated PoV for a function is replayed on every compiled implementation in its cohort." Agent attempts do share flaws. In the pilot, the same new B1 flaw appeared in two different configurations, Aider + GPT-5.4-mini and Codex + Sonnet 4.5 (the agent results for finding 63008, `pilot/tasks/63008/feature_tasks/results.md`).
   Required change: record which campaign first found each confirmed vulnerability. Then pre-specify a sensitivity analysis of Δ^K that counts a vulnerability only when the implementation's own campaign, or the frozen audit-report PoV, found it. Report it beside the primary estimate.

2. **The evaluation may find flaws more easily in agent code than in human code, and RQ4 is too small to measure the difference.**
   Problem: there are three reasons the procedure's sensitivity may differ by author. (a) Human N-stratum code has already passed a professional audit. The human flaws that remain are ones the experts missed, so they are probably harder to find. Agent flaws were never filtered this way. (b) The two LLM reviewers come from the same model families as the agents. LLM evaluators recognize and favour their own outputs (Panickssery et al., NeurIPS 2024, https://arxiv.org/abs/2404.13076). They also favour the outputs of related models (Li et al., ICLR 2026, https://arxiv.org/abs/2502.01534). (c) Reviewer recall varies a lot. Section 6.3 promises "sensitivity to unequal missed-vulnerability rates", and RQ4 asks whether "detection differ[s] between human and agent implementations". But RQ4 reviews about 150 implementations, stratified over 2 authors, 2 strata and 3 automatic results. That leaves about a dozen implementations per cell, at 20 minutes each. At the planning rate h_N = 0.02 used in the RQ1 simulation, a dozen human N-stratum implementations with a negative automatic result contain fewer than 0.25 expected vulnerabilities. With so few, the difference in sensitivity cannot be estimated.
   Evidence: in the pilot, the reviewers were claude-opus-5-5 and gpt-5.4, and the agents used Claude Sonnet 4.5 and GPT-5.4-mini (the agent results for finding 63008, section "Code review"). On the seven confirmed repair flaws, one reviewer reported all seven and the other reported two (the repair study results, section 6). A first human reading of the control patches missed the B1 flaw that the LLM review later found (the agent results for finding 63008).
   Required change: size RQ4 from a target interval width for the human-minus-agent difference in the procedure's sensitivity. If natural positives are too rare to reach that size, seed the same set of known vulnerability patterns into matched human and agent implementations.

3. **The "human" baseline may itself be AI-assisted, and the threats section does not mention this.**
   Problem: the comparison is labelled human against agent. The frame favours recent audits to reduce training exposure (section 5.1), but recent code is also more likely to have been written with AI help. Section 6.8 lists no such threat.
   Evidence: the pilot's note on the 63008 control group (`pilot/tasks/63008/control_group.md`, section 7) found a `CLAUDE.md` in the Angstrom repository from its first commit. That was three days before `661468b`, the commit that introduced the bug. The same note found AI agent files in the Ekubo, Wannabet and Megapot repositories. The proposal's own motivation (section 2) cites that 49% of surveyed Solidity developers use AI tools to write code.
   Required change: record AI-assistance markers at each sampled function's introducing commit as a pre-registered covariate. The markers are agent configuration files, co-author trailers and pull-request text. Report Δ^K again on the functions that have no marker.

4. **The primary endpoint drops whenever an agent fails.**
   Problem: K = C·V scores 0 for an output that does not compile. It also scores 0 for a broken output with no confirmed flaw. The primary test is two-sided. So a configuration that often fails to compile, or writes code that does little, will show a negative Δ^K. The paired-outcome breakdown in section 6.3 separates these cases, but only descriptively. It is not part of the tested claim.
   Evidence: section 3 says compilation failures "cannot count as successful vulnerability avoidance". In the primary test statistic they lower K in exactly the same way that a secure implementation does.
   Required change: add a pre-specified reading rule. A negative Δ^K may be reported as better agent security only if the difference in the rate of working outputs with no confirmed vulnerability, C·L·(1−V), is also not negative. Otherwise it is reported as a difference in capability.

5. **The power simulation assumes that a protocol affects the agents and the human in the same way.**
   Problem: in the v7 script (lines 80–81), the same protocol effect `up[p]` enters the human's linear predictor and every agent's, with coefficient one. So the human-agent difference has almost no protocol-level variation of its own. The proposal's paragraph on remaining simplifications says protocol effects are shared across configurations. It does not say they are also shared with the human. I reran the authors' `simulate` code with an extra protocol-level effect for the agents only, and recalibrated the agent intercepts so the marginal rates did not change. I used 25 protocols, a human V rate of 1.0, and the "middle effect" (true difference +0.065), with 400 studies per cell. In two of the authors' scenarios, the lowest configuration power was 0.72 and 0.55 without the extra effect. It fell to 0.48 and 0.41 with an SD of 0.75, and to 0.40 and 0.35 with an SD of 1.0. The two scenarios were protocol and function SDs of 0.5 and 1.5 with ρ = 0.3 and γ = 1, and SDs of 1.0 and 2.0 with ρ = 0.6 and γ = 0.5. Family-wise error stayed at or below 0.046. There is a second problem. All 48 calibration scenarios fix the human N-stratum rate at 0.02. At a rate of 0.005, the selected procedure had family-wise error of 0.001 to 0.005 (1,000 studies each). So the level is tuned to one guessed base rate. The month-two rerun measures the frame, but not these outcome parameters.
   Evidence: `tools/power_sim_v7.py`, lines 80–81 and the function `grid()` (`hN = 0.02`). The recorded power is in `tools/power_results_v7_rq1_calibration.txt`, step 3.
   Required change: add a protocol-by-author random effect and a range of human N-stratum rates to the calibration and power grid. Then state, in the preregistration, the minimum detectable difference under the worst scenario kept in the grid.

6. **The primary test does not say what value an unresolved attempt takes.**
   Problem: the test statistic needs a number for every attempt. If unresolved rates differ by author, the coding choice shifts Δ^K. For example, agent code may break harnesses more often than human code. The simulation generates no unresolved outcomes at all.
   Evidence: section 6.2 says "Unresolved evaluations remain in the denominator and receive bounds consistent with the known outcome dimensions". Section 5.10 says candidates beyond the budget "do not become negative evidence". Section 6.3 says "The endpoint K is generated directly".
   Required change: state in the analysis plan the value an unresolved attempt takes in the primary test statistic. Then require that the primary claim keeps its sign when the test is rerun with every unresolved attempt set to each bound.

7. **The RQ2 model assumes that the treatment effects are the same for every function.**
   Problem: test content and execution vary within each function, so their effects can differ between functions. The declared model and the simulation have random intercepts only. I reran the authors' likelihood-ratio test on writing data that had function-level random slopes on test, execution and their interaction. The setup was 40 functions, 20 protocols, a true mean interaction of 0, and 300 studies per row. Rejection at a nominal 0.05 was 0.033 with no slope variation. It rose to 0.057 with a slope SD of 1.0 and to 0.073 with an SD of 1.5. The Monte Carlo SE is about 0.014. I also tried cell rates near the ceiling, as in the pilot, where requests describing the human design gave the bug in 13 of 13 runs. Power for an interaction of 1.5 was 0.78 at a single-test level of 0.05, against 0.90 in the proposal's table. The conditional cell probabilities were 0.27, 0.27, 0.88 and 0.97.
   Evidence: in `tools/power_sim_v5.py`, the function `rq2_dataset` gives every function the same treatment effects. Section 6.4 declares "Random intercepts represent protocol and function nested within protocol."
   Required change: add function-level random slopes for test content, execution and their interaction to the RQ2 model. A function-level difference-in-differences with protocol-clustered inference would also work. Then redo the RQ2 calibration with effects that vary by function and with cell rates like the pilot's.

8. **RQ2's confirmatory result rests on one agent configuration, and the pilot shows that the agent changes the answer.**
   Problem: if the replication is removed, the interaction is estimated for one agent only.
   Evidence: section 6.4 says "RQ2 runs in two configurations: one primary and one replication". Reduction 4 in section 8 removes the replication. In the repair study, the same input gave 3 of 12 to 11 of 12 successes depending on the agent (arm P-E0). Codex showed no drop from the shown-test tool to a full terminal: 6 of 12 in both (the repair study results, sections 3 and 4).
   Required change: take the replication configuration off the reduction list. Pre-specify that RQ2 is claimed to hold beyond one configuration only if both configurations show the same sign.

9. **The pilot evidence that motivates RQ2 is reported selectively.**
   Problem: section 3 cites "10 of 12 runs without execution and 2 of 12 runs with a terminal" as the motivation. The repair study report calls this contrast exploratory. It also reports that both pre-registered contrasts showed no difference, with Holm p-values of 0.96 and 1.00. In the arm that could rerun only the shown PoV, OpenHands succeeded in 9 of 12 runs. So the drop came with a full terminal, and RQ2 does not test a full terminal. RQ2 tests a tool that runs only the repository tests.
   Evidence: the repair study results, sections 1, 4 and 9.
   Required change: in section 3, report the two pre-registered pilot contrasts and the 9 of 12 shown-test result next to the 10 of 12 against 2 of 12 figure. State that the RQ2 hypothesis was formed after seeing the pilot.

10. **The strongest current agents are only a secondary comparison.**
    Problem: the primary family is two models, GPT-5.4-mini and Claude Sonnet 4.5, in three harnesses. Both Codex configurations run on Codex's fallback prompt, and one reaches its model through a translation proxy. The pilot already uses stronger models as reviewers (Claude Opus 5.5 and GPT-6.1 Sol). The current supported agents run only on "a declared common subset", and reduction 5 can shrink that subset further. A result about a mini model and an older Sonnet in research harnesses will be challenged as out of date.
    Evidence: the configuration table in section 5.9, and the reduction order in section 8. The repair study results (section 10) say Codex "uses its fallback prompt and tools with GPT-5.4-mini".
    Required change: put the two supported current configurations into the primary Holm family on the full main sample. Move the translated integrations to secondary analyses.

11. **The protocol pool is built from findings, so the population is limited to protocols where a human had already failed.**
    Problem: a protocol with no qualifying High or Medium finding cannot enter the pool. Section 2 criticizes earlier designs because they "select tasks because a human previously failed". This design makes the same selection one level up. Stratum N then means unflagged functions in protocols where auditors found at least one serious bug.
    Evidence: section 5.1 builds the pool from "19,666 Solidity findings" down to "77 recent candidates". Section 5.2 plans two V functions per protocol.
    Required change: build the protocol frame from audit contest listings, so that protocols without a qualifying finding can be sampled. If that is not possible, name the RQ1 population as protocols with at least one qualifying finding.

12. **Severity and attribution are decided by people who know which code is the human's.**
    Problem: whether a flaw is High or Medium under the platform's criteria is a judgment. So is whether a correction is "independently justified". These judgments decide V. They are made during confirmation by the team that traced the historical code.
    Evidence: section 5.10 hides the author only from the LLM reviewers. The confirmation record includes "human adjudication". Section 6.6 refers to the construction team's "unblinded review". In the pilot, Claude subagents did the blind review that the design gives to a person. Their review pack also included, by mistake, the output of checks written after the runs had started (the repair study results, sections 7 and 10).
    Required change: have severity and attribution decided by two adjudicators from outside the construction team. Blind them to author and arm as far as the code allows, and report how often they agree.

13. **The workload for confirming flaws is not estimated, and the pilot rates suggest it is too large for one student in 12 months.**
    Problem: RQ1 with the supported baselines yields up to about 6,250 implementations: 250 functions × 8 configurations × 3 attempts, plus 250 human implementations. In the pilot, 8 of 64 reviewed repairs had at least one reviewer report that needed a confirming PoV (the repair study results, section 6). So did 3 of 13 reviewed control versions (the agent results for finding 63008). At these rates, about 780 to 1,440 implementations would each need a PoV, a correction to the target function, and adjudication. That count is before any deduplication, and before RQ2 or RQ3 adds anything. The same schedule also builds 250 to 300 main tasks and 40 to 60 RQ2 tasks in months 2 to 5.
    Evidence: section 8 gives token formulas only. It says confirmation needs "an additional measured allowance".
    Required change: estimate the human hours for confirmation from the pilot rates and the month-one timings. Then fix the number of configurations and attempts at month two so that this estimate fits the funded time.

## Ratings

- C1: pass — The weighted comparison that includes unflagged functions differs in design from SecureVibeBench, SusVibes and Foresight-SWE; the RQ2 intervention is closer to ImpossibleBench and Building to the Test.
- C2: pass — Contracts hold funds and agent use is reported by developers; the proposal is careful not to claim an AI-caused loss rate.
- C3: pass — Executable confirmation, target-only attribution and a calibrated weighted estimator go well beyond applying an LLM to a task.
- C4: concern — Common replay, the earlier audit of human code, and scoring failures as zero can each move Δ^K for reasons other than security (weaknesses 1, 2 and 4).
- C5: pass — The attacker, the environment, the protected assets and the exclusions are explicit for each protocol.
- C6: concern — The plan is detailed, but the difference in detection between authors is not measurable as RQ4 is sized, the strongest current agents are secondary, and the power model leaves out a protocol-by-author effect.
- C7: fail — Pilot rates imply roughly 780 to 1,440 RQ1 implementations needing confirmation, on top of building 250 to 300 tasks in four months, and the proposal gives no human-hour estimate.
- C8: pass — Exploits run offline, there is a disclosure and embargo procedure, and generated code is never deployed.

## Questions for authors

1. Is the RQ1 estimand the finite set of eligible functions in the frame, or a superpopulation? The simulation's true value uses superpopulation marginal rates with the frame share each study draws, and the jackknife has no finite-population correction. If 25 to 30 protocols are drawn from a pool of about 43 candidates, which coverage claim do you intend?
2. The tests and intervals do not agree. At 25 protocols, Holm at α* = 0.025 needs |t| ≥ 3.17 at its first step and |t| ≥ 2.39 at its last step. The interval half-width is 1.24 × 2.06 = 2.56 standard errors. So an interval can exclude zero for a configuration that is not rejected, and the reverse can also happen. Which one decides the reported claim?
3. Why is the RQ2 primary estimand the interaction, and not the effect of execution within the faulty-test arms, given how RQ2 is worded? The injected corrected tests distinguish vulnerable from corrected behavior, so the corrected-test execution arm gives the agent a test of the fix. How will you separate "faulty tests hurt" from "correct tests help"?
4. What result of the blinded realism check would lead you to change or drop the injected tests? With one human reviewer, agreement cannot be estimated.
5. How many protocols in the refreshed pool have at least two V functions that meet every eligibility rule, including the unprivileged-attacker scope and target-only attribution?
6. Section 6.3 says the marginal rates are "checked independently by Monte Carlo sampling". That check is in `tools/power_sim_v5.py` (lines 124–126), not in `tools/power_sim_v7.py`. It also does not cover the per-study rates of the offsetting configurations. Will the month-two run include it?
7. Which model will RQ3 use? How will you stop a request written from the vulnerable implementation from simply stating the answer?
