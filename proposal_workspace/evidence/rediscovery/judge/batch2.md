## Notes

- **65028.** The fix does more than clamp the subtraction. It removes the call to `getCrossBalances` and the whole cross-token split of the bonus, and computes the bonus per token from `bal0`, `req0`, `bal1` and `req1`. Both lists still name the exact subtraction that underflows, so the match holds. The finding is inside the threat model: any user can open the position, and the harm is that a third party cannot liquidate it.
- **65029.** The fix is one character (`=` to `+=`). The harm falls on a user who holds a token id with two or more credit legs in the same token. The attacker is an ordinary liquidator, so this is inside the threat model. List B's second candidate (credits counted twice in `getLiquidationBonus`) is a different issue and was not used for the verdict.
- **65030.** The fix commit also changes the `EMA_PERIODS` constant outside the target function. The key treats that change as unrelated, and the key's fix-scope confidence is only medium. Both lists name the same wrong destructuring line. Their impact story differs from the key's. The key says the TWAP leans on the slow EMA, so it lags and insolvent accounts escape liquidation. Both lists say the TWAP drops the eons EMA, so it follows a moved price too quickly and healthy accounts can be liquidated early. The root cause is the same, so I counted both as matches.
- **65032.** The finding only applies to pools with tick spacing 1. Both lists state that condition. The fix touches only the target line (`positionWidth / 2` becomes a division that rounds up).
- **65036.** The fix is a change to the margin model: it subtracts the credit from the loan requirement instead of taking the larger of the two. The harm is that a user's requirement is too high, so the user can be liquidated while solvent. The protocol does not lose funds. No privileged role is needed, so this is inside the threat model.
- **65040.** The finding text names `CollateralTracker._updateInterestRate` and `_accrueInterest` as the place where the rate at target is stored again within the same epoch. The fix is in the target function `_borrowRate`, which now measures elapsed time from the start of the current epoch instead of from `block.timestamp`. Both lists name that subtraction in `_borrowRate`, so the change to the caller does not affect the verdict.
- **65044.** Panoptic marked this finding as informative, although the key's severity field says Medium. The finding is that a safety check can never fire. It has no direct attacker path to fund loss. That likely explains why List A reported no candidate under a threat model that asks for an exploitable path. The fix only lowers the threshold of the median versus slow EMA check from `MAX_TICKS_DELTA * 2` to `MAX_TICKS_DELTA / 2`. List B's second candidate also claims that the spot versus fast EMA check (threshold 476) can never fire. The key does not say that, and the fix does not change it. List B's lag estimates also differ from the key's (about 410 ticks for the slow EMA, against about 1397 ticks in the key). Both still conclude that the 1906-tick threshold is out of reach.
