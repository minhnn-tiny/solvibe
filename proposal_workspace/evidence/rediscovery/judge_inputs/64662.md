## List A

- **Uncollected proceeds are lost when an active order's sale rate is reduced to zero**
  - Root cause: in the `callType == 0` branch, `purchasedAmount = computeRewardAmount(rewardRateInside - rewardRateSnapshot, saleRate)` (line 227) is never paid out. It is only carried forward through the snapshot, `rewardRateSnapshotAdjusted := mul(sub(rewardRateInside, div(shl(128, purchasedAmount), saleRateNext)), iszero(iszero(saleRateNext)))` (lines 234-238). When `saleRateNext == 0`, the multiplier is 0. So the snapshot is written as 0 (line 272) and the sale rate is written as 0 (line 251). After that, every later `computeRewardAmount(..., 0)` in the collect branch (line 366), or in a later increase (line 227), returns 0. The bought tokens stay in the TWAMM saved balance, and no one can claim them.
  - Attack sketch: an order owner (or the Orders periphery that owns the order for them) has an active order with proceeds that have built up since the last collect. The owner cancels the order with `callType 0` and `saleRateDelta = -saleRate` while `startTime <= block.timestamp < endTime`. The refund of unsold tokens is paid (lines 316-342), but the bought tokens are dropped. Cancelling an order is a normal user action, so any user who cancels without collecting first loses everything bought since the last collect. No outside attacker is needed. The harm is to the order owner, and the bought tokens stay locked in the contract.
  - Severity: Medium
  - Confidence: medium

- **Anyone can take the order-withdrawal fee with liquidity added just before the fee is paid, or the canceller can avoid paying it**
  - Root cause: when `amountDelta < 0` (lines 324-335), the fee `computeFee(uint128(uint256(-amountDelta)), poolKey.config.fee())` goes straight to whatever liquidity is in the pool at that moment, through `CORE.accumulateAsFees(poolKey, fee0, fee1)` (lines 328 and 331). Nothing in the function protects against liquidity that is added and removed within the same block. TWAMM pools are full range only. No time passes between the steps, so no virtual orders run and the price does not move.
  - Attack sketch: (1) The attacker sees a large order decrease or cancel. In the same block, or in one transaction using a flash loan, the attacker adds a large full-range position to that TWAMM pool. (2) The victim's `callType 0` decrease runs, and `accumulateAsFees` spreads the fee over all liquidity, so the attacker gets almost all of it. (3) The attacker removes the position and collects the fees. The long-term LPs lose the fee they are owed. The order owner can run the same three steps around their own cancel and get most of their own fee back, which defeats the purpose of the fee.
  - Severity: Medium
  - Confidence: low

- **An attacker can block a victim from cancelling or reducing their order by filling the per-time sale-rate-delta limit at the victim's end time**
  - Root cause: a decrease always runs `_updateTime(poolId, endTime, -int256(saleRateDelta), ...)` (line 303 for an active order, line 278 for an order that has not started). This raises the net delta stored at `endTime`. `_addConstrainSaleRateDelta` reverts with `MaxSaleRateDeltaPerTime` if the absolute value goes above `MAX_ABS_VALUE_SALE_RATE_DELTA`. The limit applies to the net of all start and end deltas at that time, and anyone can add start deltas at any valid time.
  - Attack sketch: a victim's order ends at time E. The attacker opens orders that start at E (that is, orders that have not started yet). Their total sale rate is chosen so that the net delta at E sits exactly at `+MAX_ABS_VALUE_SALE_RATE_DELTA`. The attacker gives those orders different end times, so that each end time stays inside the limit. Any later decrease by the victim pushes the delta at E over the limit, so the call reverts. The victim cannot cancel or withdraw until E. The attacker needs a large sale rate (about `type(uint112).max / 91`) for at least 256 seconds. So this only works cheaply on pools with a low-value token. The attacker gets most of that capital back, minus fees.
  - Severity: Medium
  - Confidence: low

- **Both sides of the update amount round up, so each rate change can underpay or over-refund by 1 wei, drawn from a saved balance that all fee tiers share**
  - Root cause: `amountRequired` (line 311) and `remainingSellAmount` (line 317) both use `roundUp: true`. So `amountDelta = ceil(saleRateNext * d) - ceil(saleRate * d)` can be up to 1 wei below the exact increase cost, or up to 1 wei above the exact refund. When an update happens at a different time from the earlier update, the two errors do not cancel out. Every TWAMM pool for the same token pair, whatever its fee, uses the same saved balance: `updateSavedBalances(token0, token1, bytes32(0), ...)`.
  - Attack sketch: the attacker creates a zero-fee TWAMM pool for a valuable pair, so no withdrawal fee is charged. The attacker then repeatedly increases and decreases a small order at different timestamps, taking up to 1 wei each time from the shared balance. The gain is dust unless the token has very few decimals and a high value per unit. I list it only because the shared balance lets it affect other pools.
  - Severity: Medium
  - Confidence: low

- **Per-order refund rounding can consume other orders’ backing.** Root cause: `handleForwardData` calculates both remaining amounts with `roundUp: true` (lines 310–317), then refunds their difference (lines 320–332), whereas virtual execution sells the aggregate rate rounded down (lines 435–440). **Attack:** In a zero-fee pool with other users’ saved balances, an attacker creates two orders with distinct salts, each at rate `2^31` (half a token unit per second), with an even remaining duration `T`. Each deposits `T/2`. After one second, their combined rate sells one token unit. The attacker collects proceeds through `callType == 1`, then cancels both through `callType == 0`; each refund is `ceil((T−1)/2) = T/2`, returning all principal despite the executed sale. The missing unit comes from other orders’ backing; repetition scales the deficit, particularly materially for low-decimal sell tokens. **Severity: Medium. Confidence: high.**
