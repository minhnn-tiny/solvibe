## List A

- **Title: The rate at target can be pushed up or down much faster than designed, because the start time is rounded down to a 4-second epoch and the same seconds are counted again on every update.**
  - **Root cause:** Line 2214, `uint256 previousTime = interestRateAccumulator.marketEpoch() << 2;`, rebuilds the last update time from the stored epoch (`block.timestamp >> 2`). This throws away the last 0 to 3 seconds of the real last update time. Lines 2229-2233 then compute `elapsed = block.timestamp - previousTime` and `linearAdaptation = speed * elapsed`, and lines 2253-2260 apply it to `startRateAtTarget`. The caller (`CollateralTracker._updateInterestRate`) stores the new `endRateAtTarget` and writes back the same epoch. So a second update in the same block sees `elapsed = block.timestamp % 4` again and applies those seconds a second time. The same seconds are counted again on every call. Nothing in `_borrowRate` remembers that this time window was already applied. On Ethereum mainnet every block timestamp is 3 mod 4 (the genesis time is 3 mod 4 and slots are 12 seconds). So every extra call in a block adds 3 seconds of adaptation, and even consecutive blocks count 15 seconds instead of 12.
  - **Attack sketch:** The attacker deploys a contract that calls `CollateralTracker.accrueInterest()` in a loop, for example a few thousand times in one transaction. The function is public and has no access control. The guard is `nonReentrant`, which does not block calls made one after another. Each call runs `_borrowRate` with `elapsed = 3` and the current `err`, and stores a new rate at target. If utilization is above the 2/3 target (or the attacker raised it earlier in the same transaction, since `_poolUtilizationWad` keeps the highest value seen in the transaction), each call multiplies the rate at target by about `exp(1.585e-6 * err * 3)`. Each call costs only a few thousand gas when storage is already warm. So one full-block transaction applies hours of adaptation instead of 12 seconds. Repeating this over some blocks pushes the rate to `MAX_RATE_AT_TARGET` (800% APR at full utilization). Borrowers with `netBorrows > 0` then pay far more interest than the model intends. Some of them become insolvent and can be liquidated. A lender who holds the vault shares collects this interest. In the other direction, a borrower runs the same loop while utilization is below target. This drives the rate down to `MIN_RATE_AT_TARGET` and takes yield away from depositors. On a cheap L2 the cost is small.
  - **Severity:** Medium (it can become High if pushing the rate to the maximum is used to force liquidations).
  - **Confidence:** medium-high.

- **Title: Rate adaptation is capped at 4096 seconds, but the average rate it returns is charged over the full time since the last update.**
  - **Root cause:** Lines 2229-2232 cap `elapsed` at `IRM_MAX_ELAPSED_TIME` (4096 s). Both `endRateAtTarget` and the trapezoid average on lines 2253-2260 use only that capped window. But `CollateralTracker._calculateCurrentInterestState` multiplies the returned average rate by the full, uncapped `deltaTime`. After a quiet period longer than about 68 minutes, the interest charged for the whole gap comes from a rate that only moved for the first 4096 seconds. The next starting rate at target also moves only 4096 seconds' worth.
  - **Attack sketch:** Suppose utilization sits far above target during a quiet period, for example overnight on a thinly used market. A borrower simply avoids touching the vault. When the next update comes, the borrower pays interest for the whole gap at a rate that adapted for only 4096 seconds, which is much less than the model intends. Lenders get less yield. The reverse happens below target: borrowers overpay. Anyone can call `accrueInterest()` to limit the gap, so the loss depends on nobody else updating the vault.
  - **Severity:** Medium.
  - **Confidence:** low.

- **Title: A single utilization snapshot from the current transaction sets the rate change for the whole elapsed window.**
  - **Root cause:** Lines 2204-2208 compute `err` from the one `utilization` value passed in. Line 2226 turns that into a constant `speed`, and lines 2233 and 2253-2260 apply that speed to every second of `elapsed`. The caller passes the highest utilization seen so far in the transaction (`_poolUtilizationWad` reads the transient slot). So the value is not the utilization that held during the window. A large utilization change made earlier in the same transaction, which raises the stored maximum, is applied as if it had held for the whole window.
  - **Attack sketch:** The attacker first raises utilization inside one transaction, for example by withdrawing a large deposit or opening a large short position. This updates the transient maximum. Any later accrual in that transaction then adapts the rate as if utilization had been that high for the whole elapsed time. On its own the gain is small, because the first accrual of the transaction already uses up most of the window. Combined with the first candidate, the attacker gets `err` close to 1 for every repeated call and then unwinds the position. So this mainly makes the first candidate stronger.
  - **Severity:** Medium.
  - **Confidence:** low.

Each call persists the increased target rate, while the stored epoch remains unchanged and subsequent calls accrue no corresponding elapsed-time interest. Repeating batches can push the target rate toward its maximum; subsequent genuine accrual charges borrowers artificially elevated interest, draining collateral and potentially causing insolvency. At full utilization and a three-second remainder, approximately 823,000 calls move the target APR from 4% to 200% (800% borrow APR). **Severity: Medium. Confidence: high.**
