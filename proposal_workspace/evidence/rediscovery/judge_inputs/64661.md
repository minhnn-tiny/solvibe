## List A

- **1. An order that starts at the current block time is recorded as if it started when the pool began, so it can withdraw other users' proceeds.**
  - **Root cause:** Line 96, `else if (block.timestamp > config.startTime())`, returns 0 when `block.timestamp == startTime`. The comment on line 99 assumes the stored reward rate before the start time already equals the current rate. That only holds if the start time was an initialized time that virtual order execution crossed. When `handleForwardData` (callType 0) creates an order with `startTime == block.timestamp`, it takes the "already active" branch (line 271 is false). That branch only calls `_updateTime` for the end time. So nothing ever writes `poolRewardRatesBeforeSlot(poolId, startTime)`, and the slot stays 0. At creation, `getRewardRateInside` returns 0, and the order's snapshot is stored as 0 (line 235, `rewardRateInside - 0`). From the next second on, lines 100–105 return `rewardRateCurrent - 0`. That is the pool's whole accumulated reward rate since it was created, not the growth since the order began. The `>=` branch (lines 87–94) has the same problem: it returns `rewardRateEnd - 0`.
  - **Attack sketch:**
    1. The attacker waits for a block whose timestamp T is a valid order time, meaning a multiple of the minimum step size (I assume 256; `math/time.sol` was not provided). T must not be the start or end time of any order that has already been crossed. On chains with 1–2 second blocks this is easy to arrange.
    2. In that block, the attacker calls the TWAMM through Core's forward and creates an order with `startTime = T` and a short `endTime`. The order has a small sale rate `s`, so the attacker pays very little.
    3. One block later, the attacker calls collect proceeds (callType 1). `rewardRateInside = rewardRateCurrent - 0`, the snapshot is 0, and so `purchasedAmount = (globalRewardRate * s) >> 128`.
    4. The payout comes from `CORE.updateSavedBalances` on the TWAMM's shared saved balance. That balance holds every other order's unsold tokens and unclaimed proceeds.
    5. The attacker sizes `s`, or opens many orders with different salts in the same block, to drain the balance. Every order created this way gets the same overpayment, because the start-time slot is never written.

    A second path to the same state: create an order with a future start S, cut its sale rate to 0 before S (`_updateTime` writes (0,0) to S), then raise it again in the block where `block.timestamp == S`.

    Honest users who place an order starting "now" also get overpaid, which leaves the pool insolvent for the other users. The fix is to use `>=` on line 96, so that at creation the snapshot equals `current - before[start]` and later differences stay consistent.
  - **Severity:** High
  - **Confidence:** high (the only assumption is that `isTimeValid` accepts `startTime == block.timestamp` when it is a multiple of the step size)

- **2. The public view reads reward rate slots without first executing virtual orders, so it can return wrapped, very large values.**
  - **Root cause:** Lines 90–94 and 102–105 load `poolRewardRatesBeforeSlot(poolId, endTime)` and `poolRewardRatesSlot(poolId)` straight from storage, and subtract inside `unchecked`. If virtual orders have not been executed up to `block.timestamp`, the slot for a passed end time still holds the marker value 1 that `_updateTime` writes (line 166). It does not hold the real rate yet. In that case `1 - rewardRateStart` wraps to a value close to 2^256. Nothing in the function checks that the pool was executed up to the current time, or that `startTime < endTime` (the view can be called with any config).
  - **Attack sketch:** Inside TWAMM, every caller runs `_executeVirtualOrdersFromWithinLock` first, so TWAMM itself is safe. The risk is a periphery, lens, or third-party contract that calls `getRewardRateInside` directly to value an order or decide a payout, such as a lending market that accepts TWAMM orders as collateral. An attacker picks a moment after an order's end time but before anyone has executed virtual orders for that pool. At that moment the contract reads a huge "proceeds" value and lets the attacker borrow or withdraw against it. This only matters for integrators that skip the execute step.
  - **Severity:** Medium
  - **Confidence:** low
