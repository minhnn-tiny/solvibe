## List A

- **1. The premium commission can be skipped completely by settling premium before closing the position**
  - **Root cause:** The commission is `commissionFee = Math.min(commissionFeeP, commissionFeeN)` (line 1651). `commissionFeeN` is computed from `commissionN = uint256(int256(shortAmount) + int256(longAmount))` (line 1644, lines 1645-1650). The pool's settle path, `PanopticPool._settleOptions`, calls `settleBurn(owner, 0, 0, 0, realizedPremium, riskParameters)`. So `commissionN` is 0 and `commissionFeeN` is 0. The minimum is then 0, and `sharesToBurn` (line 1654) is 0, even when `realizedPremium` is large. All premium that goes through the settle path pays no commission.
  - **Attack sketch:** A user holds a position that has earned a lot of premium. A seller earns it on short legs. A buyer owes it on long legs. The user calls `PanopticPool.dispatch` with the same tokenId twice in `positionIdList`. The first entry passes `positionSizes[0]` equal to the stored size. That runs `_settleOptions`. Because `msg.sender == owner`, the short premium is realized too, and the stored premium accumulators are moved forward. `settleBurn` runs with zero long and zero short amounts, so no commission is charged. The second entry passes a different size and burns the position. `_updateSettlementPostBurn` now finds almost no new premium, so `realizedPremium` is close to 0 and the commission on the close is close to 0. The premium fee that should go to liquidity providers (burned shares) or to the protocol and builder is never paid. Every user can do this on every close, in one transaction.
  - **Severity:** Medium (lost fee revenue for liquidity providers and the protocol; no user funds stolen)
  - **Confidence:** medium

- **2. Premium earned in the token that is not the leg's token type pays no commission**
  - **Root cause:** Same lines as candidate 1 (1644-1651). The cap `commissionFeeN` is computed per collateral token, from that token's `longAmount + shortAmount` only. `PanopticPool._burnOptions` gets these from `PanopticMath.computeExercisedAmounts`, which puts a leg's notional only in the slot of the leg's token type. A Uniswap liquidity position earns fees in both tokens, so `realizedPremium` is nonzero in both trackers. In the tracker for the other token, `commissionN` is 0. The minimum with 0 makes the commission 0 there.
  - **Attack sketch:** A user sells options where every leg has token type 0. Swaps through the range pay fees in token0 and token1. On close, `settleBurn` on collateral tracker 0 charges commission on the token0 premium. `settleBurn` on collateral tracker 1 gets `longAmount = shortAmount = 0` and a positive `realizedPremium`, so it charges nothing on the token1 premium. A user can pick the token type of their legs so that most of the expected premium arrives in the other token. That part of the premium is then fee-free.
  - **Severity:** Medium (systematic loss of commission revenue)
  - **Confidence:** low (this relies on `computeExercisedAmounts` putting amounts only in the token-type slot; that library is not in the review folder)

- **3. With a builder code, only part of the commission is collected and liquidity providers get none of it**
  - **Root cause:** In the `feeRecipient() != 0` branch (lines 1659-1678), the code moves `(sharesToBurn * protocolSplit) / DECIMALS` to the risk engine and `(sharesToBurn * builderSplit) / DECIMALS` to the builder. Nothing is burned. If `protocolSplit + builderSplit < DECIMALS`, the rest of `sharesToBurn` stays with the option owner. The function still adds the full `commissionFee` to `tokenPaid` (line 1679), so the reported amount paid is higher than the amount actually taken. The `builderCode` comes straight from the caller of `PanopticPool.dispatch`.
  - **Attack sketch:** A trader calls `dispatch(..., builderCode)` with any builder code that gives a nonzero `feeRecipient`, on every mint and every burn. Each close then takes only the split fractions of the commission. With no builder code, the whole commission would have been burned to benefit liquidity providers. If the trader can also control the builder address for that code, they get `builderSplit` of their own commission back. Liquidity providers lose the commission they would have earned.
  - **Severity:** Medium
  - **Confidence:** low (it depends on how the risk engine sets the splits and maps builder codes to addresses, which is not in the review folder)
