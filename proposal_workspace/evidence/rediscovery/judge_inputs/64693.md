## List B

- **1. The `onClaim` callback is told the cumulative amount, not the amount actually sent**
  - Root cause: line 482, `IClaimRecipient(recipient).onClaim(user, token, amount, data)`. The tokens moved at line 480 are `toSend = amount - claimed[user][token].amount` (line 465). But the callback gets `amount`, which is the user's lifetime total from the Merkle leaf. From the second claim on, the callback reports more tokens than the recipient received.
  - Attack sketch: a recipient contract keeps per-user balances and credits the `amount` it is given in `onClaim`. The attacker earns rewards in any Merkl campaign. The attacker calls `setClaimRecipient(recipientContract, token)`, or passes it in `claimWithRecipient`. The attacker claims with non-empty `datas` when the tree shows a cumulative 100. The contract receives 100 and credits 100. The tree later grows to 101. The attacker claims again. The contract receives 1 token but credits 101. The attacker repeats this on every tree update, then withdraws the extra credit, which is paid from other users' deposits in the recipient contract.
  - Severity: High if a deployed recipient credits the `amount` argument, Medium otherwise.
  - Confidence: medium.

- **2. `tx.origin != user` lets any contract the victim calls claim for the victim, with attacker-chosen callback data**
  - Root cause: line 452, `tx.origin != user`, is accepted as authorization next to `msg.sender != user`. Any contract that runs inside a transaction signed by the victim passes the check for that victim. It can then set `datas[i]` (line 447) freely. Line 482 forwards that data to the victim's default recipient (lines 473 to 476) as if the victim had sent it.
  - Attack sketch: the victim has set `claimRecipient[victim][token]` to a contract that acts on `data`, for example by swapping, depositing into a vault, or forwarding to an address encoded in `data`. The attacker publishes any contract the victim will call, such as a mint, airdrop or approval helper. Inside that call, the contract calls `claimWithRecipient([victim], [token], [amount], [publicProof], [0], [maliciousData])`. Merkle proofs are public. `tx.origin == victim`, so line 458 does not revert. The tokens go to the victim's recipient, and `onClaim(victim, ...)` then runs the attacker's instructions. Examples are a swap with zero minimum output that the attacker sandwiches, or a transfer to the attacker. The victim never agreed to a claim with that data.
  - Severity: High, depending on what the recipient does with `data`.
  - Confidence: medium.

- **3. A third party can make the recipient callback fail silently, so the tokens arrive with no accounting**
  - Root cause: lines 482 to 484. The tokens are transferred first (line 480). Then any revert inside `onClaim` is swallowed by `catch {}`. The caller controls the gas and the `data`. With too little gas, the callback runs out of gas, and the 1/64 of gas kept back lets the outer call finish.
  - Attack sketch: this works for any caller who passes line 458 for the victim. That includes a contract using the `tx.origin` path, or anyone when the victim has set `operators[victim][address(0)] = 1`. The attacker claims for the victim with malformed `data`, or with a gas limit just large enough for the transfer. The recipient contract receives `toSend` but `onClaim` never records it, so the victim's share stays unaccounted in the recipient. The victim's `claimed` entry is already updated (line 466), so the victim cannot claim the same rewards again with correct data.
  - Severity: Medium.
  - Confidence: low.

- **4. A forced early claim cancels the victim's chosen recipient and callback**
  - Root cause: line 472, `if (msg.sender != user || recipient == address(0))`, drops the recipient supplied in the call whenever the caller is not the user. Line 466 then marks the amount as claimed, so the user's own call later sends nothing (`toSend == 0`, line 479).
  - Attack sketch: the victim allows open claiming (`operators[victim][address(0)] = 1`), or interacts with an attacker contract (`tx.origin` path). The victim submits `claimWithRecipient` with a custom recipient and `data`, for example to route the rewards to a contract that can use them or that applies the callback. The attacker front-runs it, or runs inside the victim's earlier transaction, and calls `claim` for the same leaf. The funds go to the default recipient, or to the victim address, without the callback. The victim's transaction succeeds but transfers zero. This is a loss when the default address cannot use the token, for example a blocklisted address or a contract without a withdraw path.
  - Severity: Medium.
  - Confidence: low.

- **5. Checked subtraction blocks all claims for users who claimed under a tree that is later rolled back**
  - Root cause: line 465, `amount - claimed[user][token].amount`, reverts when the active leaf amount is below the recorded claimed amount. After `revokeTree` or a valid dispute, `getMerkleRoot()` returns an older tree with smaller cumulative amounts. Every batch containing such a user then reverts at line 465.
  - Attack sketch: a user claims during the window when the newer tree is active. Governance then reverts to the older tree. The user's claims for that token revert until a new tree is posted with an amount at or above the old claimed amount. An operator's batch that contains this user also reverts as a whole. An attacker can only trigger this by claiming early, so the impact is a temporary denial of service.
  - Severity: Medium.
  - Confidence: low.
