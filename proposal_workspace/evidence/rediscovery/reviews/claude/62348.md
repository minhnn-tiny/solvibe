- **1. Swap-and-pop moves the last fungible but does not update its stored index, so a position can list the same fungible twice and its collateral is counted twice**
  - Root cause: in the full-removal branch, line 97 `sstore(add(dataSlot, sub(index, 1)), sload(add(dataSlot, sub(len, 1))))` moves the last array element into the freed slot. The function never rewrites `self.fungibleStates[movedFungible]`, so the moved fungible keeps its old index (`len`) instead of the new one (`index`). Later removals trust that stale index. Line 96 `iszero(eq(index, len))` then compares the wrong numbers, and line 100 `sstore(add(dataSlot, sub(len, 1)), 0)` zeroes whichever fungible sits last, which may be a different token. The removed token's state is cleared on line 87 even though its array entry stays. `addFungible` (line 46) treats a zero index as "not in the array" and pushes the token again, so the array ends up holding a duplicate.
  - Attack sketch: the attacker opens a position and uses only the normal deposit and withdraw paths on it.
    1. Deposit token A, then token B. The array is [A, B], with A at index 1 and B at index 2.
    2. Withdraw all of A. B moves to slot 0, so the array is [B]. B's state still says index 2.
    3. Deposit a small amount of A. A is pushed, so the array is [B, A], and A gets index 2. Now A and B both claim index 2.
    4. Withdraw all of B. The stale index 2 equals the length 2, so line 100 zeroes slot 1, which holds A. B's state is cleared, but B is still in slot 0. The array is [B].
    5. Deposit B again. Its index is 0, so it is pushed a second time. The array is [B, B], with B at index 2.
    6. Any appraisal that loops over `fungibles` and reads `fungibleStates[f].balance()` now counts B's balance twice. The attacker borrows against the doubled collateral and walks away with debt the real collateral does not cover. The protocol is left with bad debt. Repeating the pattern with more tokens adds more copies.
  - Severity: High
  - Confidence: high

- **2. A stale index can let a full withdrawal run on an empty array. `sub(len, 1)` then wraps and sets the array length to 2^256-1**
  - Root cause: the assembly block on lines 90 to 102 is unchecked. After the corruption from candidate 1, a token can still hold a nonzero balance and index while the `fungibles` array is empty. One way: take the state after step 4 above, where A has a hidden balance with index 2, then withdraw all of B so that the length is 0. A full withdrawal of that hidden token reads `len = 0`. Line 97 then reads `dataSlot - 1`, line 100 writes zero to `dataSlot - 1`, and line 101 `sstore(slot, sub(len, 1))` stores 2^256-1 as the array length.
  - Attack sketch: the attacker builds the hidden-balance state with the steps from candidate 1, empties the array, and then withdraws the hidden token in full. After that, any loop over `fungibles` for this position runs out of gas, and `isEmpty` can never return true. If the position has debt backed by other collateral (for example a non-fungible), appraisal and liquidation of that position revert, and the debt cannot be cleared. Whether the attacker's own transaction survives depends on whether a health check runs on this position at the end of the same call. A later `addFungible` would also write to `dataSlot - 1` and wrap the length back to 0, which gives the token index 0 while it still has a balance.
  - Severity: Medium
  - Confidence: low

- **3. Ordinary withdrawals in a normal order silently drop a fungible from the array. The owner's collateral is then undervalued and the position can be liquidated unfairly**
  - Root cause: the same missing index update on line 97. After one middle removal, the next full removal of the moved token (or of the token pushed into its old slot) zeroes the wrong slot on line 100. A token that still has a balance in `fungibleStates` then disappears from `fungibles`. Any appraisal that loops over the array leaves out that balance.
  - Attack sketch: a victim holds tokens A, B and C and withdraws all of A, then all of C, which is a normal sequence. C was moved into slot 0 with a stale index of 3. Withdrawing C writes B into a slot beyond the array end and zeroes slot 1, which held B, so the array becomes [C], with C's state cleared. B's balance is still recorded but is no longer counted. The victim's position now looks undercollateralized, and an attacker who watches for this liquidates or seizes it at a discount.
  - Severity: Medium
  - Confidence: medium
