- **1. The attacker can switch safe mode off for its own transaction by moving the live pool price back toward the stale spot EMA**
  - **Root cause.** The only automatic check that can actually fire is `bool externalShock = Math.abs(currentTick - spotEMA) > MAX_TICKS_DELTA;` (line 899). `currentTick` is the raw slot0 tick. `PanopticPool.getRiskParameters` reads it with `getCurrentTick()` and passes it in with no check against any time-weighted price. So the attacker can set this input to any value inside its own transaction. Candidate 2 explains why the other two checks never fire. Because of that, the automatic safe-mode level is 0 or 1, and the caller decides which one it gets.
  - **Attack sketch.** The market moves fast, more than 953 ticks (about 10%) in a few minutes. Oracle observations are clamped to 149 ticks per 64-second epoch, so `spotEMA`, the median and the latest observation all lag behind. Honest users now get `safeMode = 1`: they are checked at four ticks with 100% utilization, which means full collateral for sold legs and no cross-margining. The attacker does the following in one transaction, using a flash swap or flash accounting. (1) Swap on the Uniswap pool to push the price back to within 953 ticks of the stale `spotEMA`. `isSafeMode` now returns 0, and `getSolvencyTicks` also sees a small deviation, so it checks only the stale `spotTick`. (2) Call `dispatch` and mint short legs with the normal 20% seller requirement. The swap in step 1 happened before the first `dispatch`, so the `cumulativeTickDeltas` limit does not count it. (3) Swap back to the real price. This trade sells into the vault liquidity that was just added at the stale price, so the attacker's other address takes the value of the in-the-money short legs. The short account is now under-collateralized at the real price. It cannot be liquidated until the EMAs catch up, because `dispatchFrom` needs the account to be insolvent at the stale spot, TWAP and latest ticks too. Whatever the loss exceeds the 20% collateral becomes bad debt for the PLPs. With safe mode on, 100% collateral would have stopped the trade from being profitable.
  - **Severity:** Medium. **Confidence:** medium.

- **2. The second and third safe-mode checks can never fire, so automatic levels 2 and 3 (covered-only mints and blocked mints) never happen**
  - **Root cause.** `Math.abs(spotEMA - fastEMA) > (MAX_TICKS_DELTA / 2)` (line 904, threshold 476) and `Math.abs(medianTick - slowEMA) > (MAX_TICKS_DELTA * 2)` (line 909, threshold 1906) compare values that are all built from the same clamped observations. Each new observation is at most 149 ticks from the previous one (`clampTick` with `MAX_CLAMP_DELTA = 149`). Under a steady 149-tick-per-epoch move, the spot EMA (factor 0.75 per update) lags by about 50 ticks and the fast EMA (factor 0.53) lags by about 130 ticks. Their gap is about 80 ticks, far below 476. The median sits within 7 × 149 = 1043 ticks of the latest observation, and the slow EMA lags by at most about 410 ticks, so their gap stays under about 1450, below 1906. Longer gaps between updates push all factors to 0.75, which only makes the gaps smaller. The NatSpec also says condition 2 compares the fast EMA with the slow EMA, but the code compares spot with fast, and the eons EMA is never used. As a result, `safeMode` only reaches 2 or more through the guardian's `lockMode`.
  - **Attack sketch.** During a real crash with no guardian action, `dispatch` never sees `safeMode > 1`, which would force tick limits for covered positions, or `safeMode > 2`, which would revert with `StaleOracle`. Any user can keep minting uncovered positions with in-the-money swaps against the stale oracle. The only remaining protection is level 1, and the attacker can turn that off as shown in candidate 1.
  - **Severity:** Medium. **Confidence:** medium.

- **3. The guardian lock read by `oraclePack.lockMode()` is cleared, and `spotEMA` is corrupted, whenever the oracle rebases its reference tick, and anyone can trigger that rebase with `pokeOracle`**
  - **Root cause.** In `isSafeMode`, `oraclePack.lockMode()` (line 912) and `spotEMA` from `oraclePack.getEMAs()` (line 893) read bits 118–119 and bits 120–141 of the pack. `OraclePack.rebaseOraclePack` keeps only `OraclePack.unwrap(oraclePack) & UPPER_138BITS_MASK`, and that mask is `~((1 << 138) - 1)`. So it zeroes bits 0–137. That range covers the lock-mode bits and the low 18 bits of `spotEMA`, not only the residuals and the reference tick. `insertObservation` then reads `lockMode()` and runs `updateEMAs` on the rebased pack and stores the result. A short simulation confirms the effect. For a pool near tick 200000, the lock goes from 3 to 0, and `spotEMA` becomes 0 and then 150000 after one update. For a pool near tick −100, `spotEMA` becomes −65611. The error shrinks by only 75% per epoch, so it lasts several epochs.
  - **Attack sketch.** The guardian calls `lockPool` during an incident. This sets lock mode 3, so `isSafeMode` returns at least 3 and all mints revert. The price keeps moving. Once the clamped observation is more than 1024 ticks from the reference tick, the attacker calls `pokeOracle`, which is open to anyone, or any `dispatch`. The rebase sets the lock to 0, and the attacker mints again even though the guardian blocked minting. Every rebase, which happens on every move of about 11%, also leaves a `spotEMA` that is thousands of ticks wrong. For the next few epochs, `isSafeMode` reports a false shock (level 2). Every solvency check, including `dispatchFrom`'s `atTicks[0] = spotTick`, then uses a meaningless tick. Liquidations of insolvent accounts that look solvent at that tick are blocked, and honest users' mints and withdrawals revert.
  - **Severity:** High. **Confidence:** medium. The mechanism is certain, but the defect sits in `OraclePack.rebaseOraclePack` and shows up through the values `isSafeMode` reads.

- **4. An attacker can force safe mode on a victim's transaction by sandwiching it with a price move, which blocks withdrawals, mints and partial closes**
  - **Root cause.** As in candidate 1, line 899 uses the instantaneous `currentTick`, and the result is computed again for every call, not stored. A single-block price move of more than 953 ticks from `spotEMA` gives `safeMode = 1`. For `validateCollateralWithdrawable` and the final `_validateSolvency` in `dispatch`, that means 100% utilization and checks at four ticks, including the manipulated `currentTick`.
  - **Attack sketch.** The attacker sees a victim's `withdraw` from the CollateralTracker, or a `dispatch` that partly closes positions to reduce risk. The attacker front-runs it with a swap that moves the pool price more than 953 ticks, the victim's transaction reverts with `AccountInsolvent`, and the attacker swaps back right after. The cost is swap fees on both legs. The attacker can repeat this to keep a victim from leaving or from cutting risk while the market moves against them.
  - **Severity:** Medium. **Confidence:** low.
