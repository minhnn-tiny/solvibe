1. **Repaying with `useBalance = true` breaks the position's fungible list, so collateral can be counted twice and borrowed against**
   - Root cause: line 512, `position.removeFungible(Fungible.wrap(address(this)), amount);`. When `amount` equals the position's whole debt-token balance, `removeFungible` (Position.sol lines 96-97) moves the last entry of `fungibles` into the freed slot. It does not update the moved token's stored index in `fungibleStates`. After that, the moved token's index points past the end of the array, and two tokens can end up with the same index.
   - Attack sketch: the attacker owns position P. Inside `unlock`, they deposit collateral A, call `increaseDebtShare(P, d, address(this))` so the debt token D sits at index 2, then deposit token B (index 3). The list is [A, D, B]. They call `decreaseDebtShare(P, d', true)` with `d'` chosen so `amount` equals D's whole balance. They can top D up with `depositFungible` to make the numbers match exactly. B moves to slot 2, but B's stored index stays 3, so the list is [A, B]. They deposit a new token C, which is pushed to slot 3 with index 3, the same index B has. They withdraw all of B with `withdrawFungible`. Because B's index (3) equals the length (3), the code clears slot 3, which holds C. B stays in slot 2 with a zero balance. They deposit B again. B now has index 0, so it is pushed a second time and the list is [A, B, B]. `_appraisePosition` reads B's balance once per array entry, so B is valued twice. The attacker then calls `increaseDebtShare` up to the inflated value, takes the debt tokens out, and leaves bad debt. That bad debt is spread over all debt holders through `seize` top-ups.
   - Severity: High
   - Confidence: medium. The bug is real and this function reaches it. The faulty code itself is in `PositionLibrary.removeFungible`, which `withdrawFungible` also calls.

2. **Repaying outside `unlock` uses a stale `totalDebtBalance`, so the borrower skips all interest accrued since the last collection**
   - Root cause: lines 497-500. `amount = delta.fullMulDivUp(_totalDebtBalance, _totalDebtShare)` reads `totalDebtBalance` without first calling `_collectInterest`. The function does not require the locker to be unlocked, and it never calls `Locker.register`. So it can be called directly, outside `unlock`. Then the interest for the time since `lastInterestCollectionTimestamp` has not been added yet. Lines 541-542 then lower both totals. The next `_collectInterest` only charges interest on the smaller remaining balance, so the repaid part's interest for that time is never charged to anyone.
   - Attack sketch: the borrower takes a large debt through `unlock` → `increaseDebtShare`. They wait for a quiet period with no swaps, liquidity changes or `unlock` calls (each of those collects interest). Then they call `decreaseDebtShare(P, fullShare, false)` directly, not through `unlock`. They burn fewer debt tokens than they owe. The interest that would have been donated to liquidity providers and paid as the protocol fee is lost. At the 365% per year cap, one quiet day is about 1% of the debt.
   - Severity: Medium
   - Confidence: medium

3. **Anyone can repay a dust amount on any position, which makes the owner's full repayment revert. A front-runner can use this to block a rescue before `seize`.**
   - Root cause: lines 527-537. With `useBalance = false`, the only check is that the position exists (`position.owner == address(0)`). There is no owner check. Line 539, `position.decreaseDebtShare(delta)`, uses checked subtraction (`self.debtShare -= delta`). So a call with `delta` equal to the exact full debt share reverts if someone else has already lowered the share by even 1.
   - Attack sketch: the owner of an unhealthy position sends `decreaseDebtShare(P, P.debtShare, false)` to save it. A liquidator sees this in the mempool. They front-run with `decreaseDebtShare(P, 1, false)`, which burns about 1 wei of debt token. The owner's transaction reverts on the underflow at line 539. In the same block, the liquidator calls `seize(P, liquidator)` and takes the position. This works best when the owner's rescue repays the full debt, which is the common way a position is closed.
   - Severity: Medium
   - Confidence: low. The owner can retry with a smaller `delta`, and partial rescues are not affected.

4. **The position's health is never checked after a `useBalance = true` repayment. This also skips the guard in `seize` that stops owners from seizing their own position.**
   - Root cause: unlike `increaseDebtShare`, `withdrawFungible` and `withdrawNonFungible`, the `useBalance` branch (lines 503-526) takes an asset out of the position but never calls `Locker.register(bytes32(positionId))`. If the oracle values the debt token above 1 base unit, removing `amount` debt tokens lowers the position's value by more than it lowers the debt, which is `amount`. The position can then become unhealthy, or even underwater, and nothing checks it. `seize` rejects only registered positions (line 579), so the comment's protection ("prevents owner from purposely degrading a position to be underwater then profit from seizing it") does not apply here.
   - Attack sketch: inside one `unlock`, the owner of a position that holds mostly the debt token calls `decreaseDebtShare(P, d, true)` while the debt token is quoted above 1. The position falls below its debt. A contract the owner controls then calls `seize(P, helper)`. It receives the top-up of twice the deficit, minted at line 605, and the cost is spread over all debt holders. This only works if the oracle prices the debt token above 1 base unit. I could not confirm that from the files provided.
   - Severity: Medium
   - Confidence: low
