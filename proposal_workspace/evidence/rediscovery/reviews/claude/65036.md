# Blind review: Panoptic `RiskEngine._computeDelayedSwap` (target.sol lines 1976-2022)

- **1. The credit is used as a floor on the requirement, not subtracted from it, so a delayed swap that gains value becomes liquidatable**
  - **Root cause:** lines 2016-2020, `if (required > convertedCredit) { return required; } else { return convertedCredit; }`. The function returns `max(loanAmount * 1.2, convertedCredit)` in the loan token. The comment in `_getRequiredCollateralSingleLegPartner` says the requirement should be `max(loan - convert(credit), 1)`. So the credit should lower the requirement, but here it can only raise it. The credit is also already counted as balance in the credit token: `_getRequiredCollateralAtTickSinglePosition` adds it to `credits`, and `_getMargin` adds that to `balance0` or `balance1`. That balance only helps the loan token after the cross-buffer haircut (`_crossBufferRatio`, which is below 100% and drops to 0 when utilization is high). The result is that `convertedCredit` (rounded up at `atTick`) is charged in full in the loan token, while the same credit is only partly credited back. Partnering the two legs is therefore never cheaper than leaving them unpartnered (loan 1.2 x L, credit 0). Once `convert(credit) > 1.2 x loan`, the requirement rises one-for-one with the credit's value.
  - **Attack sketch:** The victim mints a delayed swap: a loan leg of L token0 and a credit leg of C token1, partnered, with C worth about L. The victim keeps L plus 0.2 L of token0 in their balance. Mint-time solvency passes, because the requirement is max(1.2 L, about L) = 1.2 L. Then token1 rises against token0, so the victim's position is in profit. `convertedCredit` grows past 1.2 L, so the token0 requirement becomes `convert1to0(C)`, while `bal0` stays at 1.2 L. The credit's value only comes back through `scaledSurplusToken1`, which is cut by the cross buffer. With a cross buffer of 0 (utilization of 90% or more), the account becomes insolvent at all four ticks as soon as C is worth more than 1.2 L. With a cross buffer of 80%, that happens once C is worth more than 6 L. An unprivileged liquidator then calls `PanopticPool.dispatchFrom(..., positionIdListToFinal = [])`, liquidates the profitable account, and takes the liquidation bonus out of the victim's collateral. A related effect: a user who wants to borrow L against the credit and withdraw L can never pass the solvency check. They would need `cb * convert(C) >= 1.2 L`, which forces `convert(C) > 1.2 L`, which pushes the requirement to `convert(C)`, which the haircut credit cannot cover. So the delayed-swap strategy cannot be used as a collateralized loan at all.
  - **Severity:** Medium (users lose the liquidation bonus on positions that are in profit, and the strategy is unusable).
  - **Confidence:** medium.

- **2. `convertedCredit` is not bounded and can overflow the later `toUint128()`, so solvency checks and liquidation revert**
  - **Root cause:** lines 2011-2013. `PanopticMath.convert0to1RoundingUp(creditAmount, Math.getSqrtRatioAtTick(atTick))` returns a `uint256` up to about 2^192 for a `uint128` credit at high ticks. Line 2020 returns it as-is. In `_getRequiredCollateralAtTickSinglePosition` it is added in an `unchecked` block, and `_getTotalRequiredCollateral` then calls `_tokenRequired0.toUint128()` or `_tokenRequired1.toUint128()`, which reverts when the value is 2^128 or more. Nothing in the function caps the result. A normal loan requirement (1.2 x a `uint128` amount) cannot reach that size.
  - **Attack sketch:** This works in a pool with a large price gap between the tokens (very high or very low tick, or a large mismatch in decimals). An account holder mints a delayed swap with the credit in the token whose converted value at the evaluation tick goes past 2^128. Every `isAccountSolvent` call for that account then reverts at that tick. Because `dispatchFrom` checks solvency at the spot, TWAP, latest and current ticks, liquidation of the account reverts, and the account can carry bad debt from its other legs. The holder could also cause a revert at the current tick by moving the spot price in a thin pool. This only matters in pools at extreme prices.
  - **Severity:** Medium (the account cannot be liquidated, which can leave the protocol insolvent).
  - **Confidence:** low.
