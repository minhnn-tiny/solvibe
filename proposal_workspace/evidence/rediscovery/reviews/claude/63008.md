- **1. The downward iterator skips an initialized tick that sits exactly at `startTick`, so a tick that the swap really crossed is never visited.**
  - Root cause: `reset` (lines 141 to 151) sets `self.currentTick = startTick` (line 143) and then calls `_advanceToNextDown`, whose first step looks up `TickLib.position((self.currentTick - 1).compress(self.tickSpacing))` (line 172). The search therefore starts at the compressed position of `startTick - 1`. When `startTick` is a multiple of `tickSpacing`, the tick at `startTick` itself is never checked. The iterator covers the open range `(endTick, startTick)`. A downward price move in Uniswap v4 crosses every initialized tick `t` with `endTick < t <= startTick`, so the range should include `startTick`. The upward iterator is correct, because an upward move crosses `(startTick, endTick]` and `reset` for the up direction uses `compress(currentTick) + 1`. The word preload on lines 147 and 148 uses `compress(startTick)`, which is the word an inclusive lookup would need. This suggests the author meant the start to be inclusive. When `startTick` is not aligned (for example 30 with spacing 60), the lookup of `compress(29) = 0` does find tick 0. So the bug only appears when the pool tick sits exactly on a tick boundary.
  - Attack sketch: (a) The attacker opens a position with a bound at an aligned tick `t`, so tick `t` is initialized. (b) The attacker swaps one-for-zero with `sqrtPriceLimitX96 = getSqrtPriceAtTick(t)`. The swap stops exactly at the boundary, so v4 sets `slot0.tick = t`. (c) The attacker, or any user, then makes a zero-for-one swap. v4 crosses tick `t` right away, changing active liquidity by `liquidityNet(t)`. Even a swap that does not move the price crosses `t` and leaves the tick at `t - 1`. (d) The hook builds `initDown(..., startTick = tickBefore = t, endTick = tickAfter)`. `reset` skips `t`, so the reward or fee code never crosses `t`. It does not update tick `t`'s growth-outside value. It also keeps using the liquidity from above `t` for the range below `t`. When `tickAfter = t - 1` the iterator is empty, yet v4 did cross `t`. (e) The swap tax or rewards are spread over the wrong liquidity, and positions with a bound at `t` compute the wrong rewards-inside value. The attacker repeats steps (b) and (c) to push rewards toward their own position. They can claim rewards that belong to other LPs, or more than the hook holds, which makes the hook insolvent.
  - Severity: High (theft or misallocation of LP rewards, and possible hook insolvency). If the protocol only loses a small amount per swap, Medium.
  - Confidence: medium. The off-by-one inside `reset` is certain. Whether the caller compensates (for example by passing `tickBefore + 1`) cannot be checked, because the caller is not in the files I was given.

- **2. Unbounded walk over empty bitmap words started by `reset` can make swaps run out of gas.**
  - Root cause: `reset` calls `_advanceToNextDown` (line 150). That function loops one bitmap word at a time, with one external `extsload` staticcall per word (line 175), until it finds an initialized tick or passes `endTick`. There is no cap on the number of words. With `tickSpacing = 1` the full tick range is about 6,900 words.
  - Attack sketch: In a pool with sparse liquidity, the attacker makes a large downward swap across a wide range that has no initialized ticks. Or the attacker leaves a position far from the price so that the next initialized tick is many words away. The hook's iteration repeats the word-by-word walk that v4 already did, which roughly doubles the gas of the swap. Swaps near the block gas limit, or bundles that include them, then revert.
  - Severity: Medium.
  - Confidence: low. v4's own swap loop already pays a similar cost per word, so the extra cost is at most about twice that. An attacker usually cannot create empty words in a pool that already has liquidity.
