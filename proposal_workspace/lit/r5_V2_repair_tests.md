### Macke2024-IncorrectDocs Testing the Effect of Code Documentation on Large Language Model Code Understanding
- Authors: William Macke and Michael Doyle (The MITRE Corporation); Year: 2024; Venue: Findings of the Association for Computational Linguistics: NAACL 2024, pages 1044–1050 (also arXiv:2404.03114)
- URL opened: https://aclanthology.org/2024.findings-naacl.66/ (ACL Anthology page); https://aclanthology.org/2024.findings-naacl.66.pdf (PDF, pages 1 to 4 read); https://arxiv.org/abs/2404.03114 (arXiv abstract page)
- Status: VERIFIED
- Tier: B
- Touches: N4
- Summary: The paper asks whether documentation changes how well an LLM understands code. Understanding is measured by asking GPT-3.5 and GPT-4 to write unit tests for the 164 HumanEval reference solutions and counting the share of tests that pass. Each function is shown in several versions: no docstring, its own docstring, a docstring copied from a different function, renamed variables, and docstrings with 10 to 75 percent of lines kept. A wrong docstring hurt the most: only 22.1% (GPT-3.5) and 68.1% (GPT-4) of tests passed, worse than every other version at a statistically significant level, while a missing or partial docstring made no significant difference.
- Delta: The paper shows, on small single functions, that wrong natural-language context hurts an LLM more than missing context. Its wrong context is a docstring from an unrelated function, and the task is test writing, not repair. It does not study agents, security, or tests that assert a bug. The project studies agents that repair a vulnerability in a real repository whose own tests assert the vulnerable behaviour. It finds that agents with a terminal keep those tests passing, and it judges repairs with shown and held-out PoVs. The paper is early evidence for one mechanism behind the project's finding, and nothing more.

### Pasiunaite2026-VulnBump VulnBump: A Benchmark for Fixing Vulnerable Dependencies in Real Projects While Keeping the Build and Tests Green
- Authors: Gabija Pasiunaite et al. (5 authors: Pasiunaite, McMorrow, Clark, Tal, Tu); Year: 2026; Venue: arXiv preprint (arXiv:2610.17374, submitted 12 October 2026). The code is at github.com/snyk-labs/snyk-vulnbump, so the authors appear to work at Snyk, whose agent is one of the systems compared [affiliation inferred from the repository name].
- URL opened: https://arxiv.org/abs/2610.17374 (arXiv abstract page)
- Status: VERIFIED
- Tier: B
- Touches: N4
- Summary: The benchmark asks coding agents to fix vulnerable dependencies by upgrading them. It has 307 upgrade tasks covering 2,066 fixable vulnerabilities in 43 repositories across six package managers. An upgrade passes only if, in a fresh container, the dependencies resolve, a rescan shows the targeted vulnerabilities are gone, the project builds, and all previously passing tests still pass. With Claude Sonnet 5.5 (the model name as the abstract page gives it), Snyk's own remediation agent passes 90.2%, Claude Code with Snyk's scanner 77.5%, and Claude Code alone 59.6%. A baseline that applies only the recommended version passes 46.9%. Giving Claude Code the scanner's guidance raises its pass rate by 17.9 percentage points; without it, Claude Code often stops at a version that is still vulnerable.
- Delta: VulnBump varies what the agent can run and is told (with or without the scanner) and measures the effect on vulnerability repair. In that respect it is close to the project's repair input study. It also judges the fix, the build and the tests together. But the repair is a version change in a manifest, and it is judged by rescanning, not by running an exploit. There is no held-out exploit, and the existing tests check that the project still works, not that the vulnerability stays. The project fixes business-logic bugs in Solidity code. It judges each repair with a shown PoV and held-out PoVs, varies the input among location, audit report and PoV, and varies execution in three steps. It also finds that the repository's own tests assert the bug. The authors' link to one of the tools compared should be noted when citing it.

### Carbonell2026-CWEFT CWEFT: CWE-Aware Evaluation of Free-Text vs. Typed Prompts
- Authors: Lanaya A. Carbonell and Anıl Koyuncu (Bilkent University); Year: 2026; Venue: 20th International Symposium on Empirical Software Engineering and Measurement (ESEM 2026), LIPIcs volume 394, pages 78:1–78:14, DOI 10.4230/LIPIcs.ESEM.2026.78
- URL opened: https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.ESEM.2026.78 (Dagstuhl publisher page)
- Status: VERIFIED
- Tier: B
- Touches: N4
- Summary: The paper asks whether naming the vulnerability or giving fix guidance in the prompt helps an LLM repair it, and whether the format of that guidance matters. It runs a controlled ablation with four prompt conditions that each differ by one factor, using fix patterns mined by APR4Vul. It generated 504 patches for 42 Java vulnerabilities from Vul4J (15 CWE classes) with Claude Sonnet 4.5, GPT-5 and Gemini 2.5 Pro. Each patch is scored in steps: it compiles, it stops the PoV, and it does so without breaking other tests. Naming the CWE class alone gave the highest rate of correct fixes, 19.8% against 12.7% with no added information (p = 0.049, exact McNemar test). Adding explicit repair guidance brought the rate down to 16.7%, and free-text and typed formats did not differ.
- Delta: CWEFT isolates one part of what the model is told and judges the result with a PoV. That is close to the "what it is told" factor in the project's repair input study, and its finding that more guidance did not help is directly comparable. But it uses single-turn prompts without an agent, without execution, and with one PoV per vulnerability, so it cannot see repairs that only fit the shown exploit. The project gives agents a location, an audit report, a shown PoV, or report and PoV. It varies what the agent can run in three steps, judges with held-out PoVs, and works on Solidity business-logic bugs.

### Bruno2026-BugReportsForAgents Writing Bug Reports for Software Repair Agents: What Information Matters Most?
- Authors: Vincenzo Luigi Bruno et al. (with Alessandro Giagnorio, Daniele Bifolco, Leon Wienges, Massimiliano Di Penta, Gabriele Bavota); Year: 2026; Venue: arXiv preprint (arXiv:2607.09553, submitted 10 July 2026)
- URL opened: https://arxiv.org/abs/2607.09553 (arXiv abstract page); https://arxiv.org/html/2607.09553v1 (full text, HTML)
- Status: VERIFIED
- Tier: B
- Touches: N4, N5
- Summary: The paper asks which parts of an issue report help a repair agent fix a bug. It labels every sentence of the 441 bug reports in SWE-bench Verified by information type, such as observed behaviour, expected behaviour, reproduction steps, location cues and suggested fixes. It then runs mini-swe-agent with GPT-5-mini, MiniMax M2.5 and Gemini 3 Flash, 8,649 runs in all. In a mixed-effects regression, a suggested fix in prose (odds ratio 2.01) or in code (1.76) and a line-level location (1.52) were most strongly linked to success. In an ablation on 65 tasks, removing location cues and suggested fixes together lowered the odds of success (odds ratio 0.60, p < 0.001), while removing either one alone was not significant. Reproduction steps, which help humans, helped agents less.
- Delta: The paper measures how the content of the task description changes repair success. That is the "what it is told" factor of the project's repair input study, and it also bears on the project's check that feature requests do not hint at the bug or fix. But it studies ordinary functional bugs judged by SWE-bench's hidden tests. The agent always has a shell, it is never given an exploit, and nothing is held back to catch repairs that only fit what was shown. The project studies security repairs, uses the PoV itself as one of the inputs, varies what the agent can run, and judges with held-out PoVs.
