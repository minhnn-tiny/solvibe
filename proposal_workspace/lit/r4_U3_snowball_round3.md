For each of the eight anchors, I listed the papers it cites (backward) and the papers that cite it (forward), and screened every title against the master index (`lit/master_index.tsv`, last column). Seven of the eight anchors gave nothing new, including the last four (the patching-architectures study, the agentic pull request study, AutoPatchBench, and Charoosaei et al.).

How the sources behaved:
- Semantic Scholar (S2) answered, but slowly. Most calls returned HTTP 429 a few times before succeeding; one title search needed 10 tries. I therefore used S2 only for the forward lists. I took every backward list from the paper itself (arXiv HTML, or the author PDF), which the task allows. These lists are complete; S2's own reference counts are smaller (for SlicePatch, S2 counts 49 references and the PDF lists 68 entries).
- S2 has no record yet for SWE-Residual (HTTP 404; posted 19 October 2026), for the FPS 2026 agentic pull request paper, or for AutoPatchBench.
- Google Scholar showed a CAPTCHA on both attempts, and DBLP returned its bot-check page. OpenAlex worked, through its `cites:` filter and its full-text phrase search.
- All requests were anonymous: no API key, no `mailto` parameter, and no name or email in any header, URL or payload (protocol rule 5a).

## New papers (tier A or B, not in the master index)

### Dai2025-FeedbackEval FeedbackEval: A Benchmark for Evaluating Large Language Models in Feedback-Driven Code Repair Tasks
- Authors: Dekun Dai et al. (Dekun Dai, MingWei Liu, Anji Li, Jialun Cao, Yanlin Wang, Chong Wang, Xin Peng, Zibin Zheng); Year: 2025 (v1 9 April 2025, v2 26 February 2026); Venue: arXiv preprint (arXiv:2504.06939). The arXiv page has no journal reference, and OpenAlex lists only the arXiv copy.
- URL opened: https://arxiv.org/abs/2504.06939 (arXiv abstract page); https://arxiv.org/html/2504.06939 (full text, HTML; I read how the benchmark is built, the six feedback types and the metric)
- Status: VERIFIED
- Tier: B
- Touches: N4
- Found by: backward snowballing from SWE-Residual (its reference 3).
- Summary: The benchmark asks how the kind of feedback a model receives changes how well it repairs code. It has 572 tasks from HumanEval, CoderEval and SWE-bench Verified, with 3,914 faulty versions. Apart from the SWE-bench Verified tasks, the faults are injected in three ways: by mutation operators, by an LLM asked to add subtle mistakes, or by keeping LLM solutions that fail the tests. Each faulty version comes with six kinds of feedback. These are test results (failing inputs, error traces, expected outputs), static-analyser output, a fixed message ("The code is incorrect. Please fix it."), advice from an LLM that cannot see the correct code, advice from an LLM that sees both the faulty and the correct code, and a mix of these. Success is the pass rate on the task's tests after k repair rounds. Across five LLMs (GPT-4o, Claude-3.5, DeepSeek-R1, GLM-4, Qwen2.5), mixed feedback repaired the most (63.6%). Next came advice written with the correct code in view (62.9%) and test results (57.9%). The fixed message gave 53.1%, static-analyser output 49.2%, and advice written without the correct code 48.8%. Extra repair rounds help, but the gain fades after two or three rounds. A later replication (Lalonde et al., arXiv 2609.00362; judged tier C below) found test results to be the strongest feedback again in Python. In a Java extension, however, simple feedback and JUnit test feedback did not differ significantly.
- Delta: Like the project's repair input study, it keeps the faulty code fixed and changes only what the model is told. Its feedback kinds roughly match the project's conditions. Test results correspond to the shown PoV. Advice written with the correct code in view corresponds to the audit report. The fixed message corresponds to location only, although it gives even less, since it does not name a location. This mapping is mine, not the paper's. The differences are large. The model never runs anything itself, so nothing matches the project's "shown test only" and "full terminal" conditions. Those conditions hold the project's main result: OpenHands succeeded in 2 of 12 runs with a terminal and in 10 of 12 when it could run nothing. The paper describes no tests held back from the feedback. Test feedback comes from running the task's tests, and success is the pass rate on the task's tests. So a fix that only covers the failure shown is not told apart, while the project judges each repair with held-out PoVs. Most faults are injected functional bugs, not security flaws. There are no exploits, no repository tests that assert the bug, and no smart contracts. The replication's finding, that the ranking of feedback kinds changed between Python and Java, is a reason to report the project's ranking of repair inputs per finding before claiming that it holds in general.

### Le2026-PAIRBench Benchmarking Code Improvement with Progressive, Adaptive, and Interactive Feedback
- Authors: Cuong Chi Le, Aashish Yadavally, Minh Le-Anh, Tien N. Nguyen; Year: 2026 (1 July 2026); Venue: arXiv preprint (arXiv:2607.01360; no comment or journal reference on arXiv)
- URL opened: https://arxiv.org/html/2607.01360 (arXiv HTML full text with title, authors and abstract; I read the method, the metric definitions, Table III and Section V-A); metadata and abstract also read through the arXiv API
- Status: VERIFIED
- Tier: B
- Touches: N3, N4
- Found by: forward snowballing from FeedbackEval (S2 citations), and again in an OpenAlex title search for FeedbackEval. It is two steps from the SWE-Residual anchor.
- Summary: PAIR-Bench measures how a model improves a wrong program over several turns of feedback. It holds 440 Python submissions to Codeforces with the verdict "Wrong Answer". Each has more than 100 hidden tests and a reference fix. After an unaided first attempt, the hidden tests that still fail are grouped by similar behaviour: how the reference solution executes them and how the output fails. Another LLM (GPT-OSS 120B) then writes a hint about one group. The hint is at one of six depths, from describing the symptom up to giving the implementation direction. The repairing model never sees the tests or the reference fix. Eight models (among them DeepSeek V3.2, Gemini 2.5 Flash Lite, GPT-4o-mini and Qwen3 Coder 30B) ran for up to 10 turns. The paper's Targeted Repair Success measures whether a model fixes the group of tests the current hint is about. It ranged from 42.56% (Gemma 3 27B) to 71.59% (DeepSeek V3.2). The paper's Broader Repair Gain is the gain on hidden tests outside that group, counted as a share of all hidden tests. It ranged from only 7.14% (GPT-4o-mini) to 10.97% (Gemini 2.5 Flash Lite). The authors conclude that "most improvements are localized to the targeted failure region." Final fix rates still reached 72.04% to 99.31%, because new hints kept coming over the turns. Without hints, Gemini reached 78.63% instead of 95.45%.
- Delta: In the project, the agent sees one PoV as a failing test, and held-out PoVs judge the repair. The pilot found that the agents' fixes covered only the case the shown PoV met. PAIR-Bench finds the same pattern in ordinary code: a model that fixes the failure it is told about seldom fixes the hidden failures it is not told about. A reviewer could cite it to argue that this behaviour is already known for LLM repair. Its six hint depths also vary what the model is told, as N4 does. The differences are these. The programs are short competitive-programming solutions with functional bugs, not smart contracts with security flaws. The model sees a hint in plain language written by another LLM, not an executable test or exploit. It cannot run code. It is a single model in a chat loop, not an agent in a repository, so there are no repository tests that could assert the bug. There is no human baseline and no loss measure. The project can cite it next to the indexed overfitting study (`Smith2015-CureWorse`) as current evidence that LLM repairs stay local to the failure they are shown. The project then adds what this paper cannot show: in a smart contract, the failure left over is a working exploit that still moves funds.

## Checked and judged tier C (not counted)

From the anchors' reference lists:
- Tyen et al., "LLMs Cannot Find Reasoning Errors, but Can Correct Them Given the Error Location" (Findings of ACL 2024; SWE-Residual ref. 27). This means that telling a model where the error is helps it correct the error, which bears on the location-only condition. But the errors are in reasoning traces, not code.
- Advani, "From Confident Closing to Silent Failure: Characterizing False Success in LLM Agents" (arXiv 2606.09863, FAGEN workshop at ICML 2026; SWE-Residual ref. 1). Agents claim success that the environment state contradicts. The tasks are tau2-bench and AppWorld, not code repair. The indexed `Bai2026-SilentFailures` is closer to the project.
- Recovery-Bench (NeurIPS 2025 workshop), "The Handoff Tax" (arXiv 2608.24358) and "Handoff Debt" (arXiv 2606.02875) (SWE-Residual refs. 25, 6, 13). Agents continue from a state or trajectory left by another agent; there is no security and no misleading tests.
- Parsons and Saunders, "Cognitive Heuristics in Software Engineering: Applying and Extending Anchoring and Adjustment to Artifact Reuse" (TSE 2004; SWE-Residual ref. 21). Human developers anchor on artifacts they reuse. This is background for why an agent might follow the repository's tests.
- Liu, Lee, Losiouk, Böhme, "Evaluating LLM-Based Regression Test Generation" (PACMSE FSE 2026, DOI 10.1145/3808129; Charoosaei ref. 21). LLMs write tests from commit messages to find bugs in parsers and interpreters. The paper is not about tests that assert buggy behaviour. Abstract read in OpenAlex.
- Jahanshahi and Mockus, "Cracks in the Stack: Hidden Vulnerabilities and Licensing Risks in LLM Pre-Training Datasets" (LLM4Code 2025; Model See ref. 19). Vulnerable code in a training corpus. It is background for the contamination question that `AlKaswan2026-ModelSeeModelDo` already covers.
- Tambon et al., "Bugs in Large Language Models Generated Code: An Empirical Study" (EMSE 2025; Model See ref. 48). Already screened in rounds 1 and 2, and not in the index.
- NLPerturbator (Chen et al., TOSEM 2026; prompt-fragility ref. 5). Robustness of code models to wording changes, measured on functional correctness only. The indexed `Sternfeld2026-PromptFragility` covers the security side.
- SlicePatch's 35 unindexed paper references are classic program repair, neural vulnerability repair (for example SeqTrans and VRepair), PHP and web scanners, and taint analysis. The closest is Son et al., "Fix Me Up: Repairing Access-Control Bugs in Web Applications" (NDSS 2013), which is a logic-bug repair method with no exploit-based judging.
- The agentic pull request paper's 12 unindexed references (for example DeVAIC and IRIS) were all seen in round 1 or are off topic.

From the forward lists:
- "Probing the Prefill: Detecting Code Vulnerabilities via Latent Activations" (arXiv 2608.16970; cites the prompt-fragility paper). Hidden-state probes for vulnerable C/C++ code.
- "ArrivalBench: Agent-Generated Data Pipelines Are Correct Once and Wrong Under Time" (arXiv 2610.02363; cites the prompt-fragility paper). Running a pipeline once against a fixed snapshot passes 86 to 100% of pipelines, while replaying them under adversarial schedules finds 7.0 to 79.2% of those silently wrong. Pipelines repaired against the snapshot test fail replay about as often as the others. This is the same lesson as held-out PoVs, but for data pipelines, with no security.
- "FuzzingBrain-Bench V1: Evaluating Open-Ended Bug Discovery by LLMs" (arXiv 2608.25158; cites the patching-architectures study). Crash discovery in C, C++ and Java.
- Model See's citers: "Distilling Reasoning Traces into Advisory Prompts for Software Engineering Tasks" (arXiv 2608.00437), "Goedel-Code-Prover" (arXiv 2603.19329; a COLM paper, according to its arXiv comment) and an Economics Letters paper. None are on the project's questions.
- AutoPatchBench's unindexed citers: OSS-CRS, SecRespond, a study of data leakage in tool-using agents, and a Russian-language survey of LLM security benchmarks. None are on the project's questions.

One step further (FeedbackEval and PAIR-Bench):
- Lalonde et al., "Revisiting Feedback-Driven LLM Code Repair: A Replication and Exploratory Java Extension" (arXiv 2609.00362). It replicates FeedbackEval; the finding is given in the FeedbackEval block.
- ConvCodeWorld (Han et al., ICLR 2025) and "When Benchmarks Talk: Re-Evaluating Code LLMs with Interactive Feedback" (Pan et al., arXiv 2502.18413). Both cited by PAIR-Bench; abstracts read. They vary feedback during code generation, not repair, with no held-out tests and no security.
- "Looping Is Not Reliability: State-Bound Evidence and Typed Revision Contracts for Agentic Code Repair" (AgenticDev 2026 workshop, arXiv 2607.24604; cites both FeedbackEval and PAIR-Bench). Forcing more test-and-revise rounds on HumanEval repairs lowered current correctness from 0.820 to 0.673. This is a different effect from the project's terminal result.
- "From Security Findings to Verified Fixes: Automated Repair of Infrastructure-as-Code Misconfigurations" (IacFix, ASE 2026, DOI 10.1145/3832783.3834509; cites FeedbackEval). A tool for configuration fixes, close to the indexed KuTIE (tier C). Abstract read in OpenAlex.
- The other 15 unindexed FeedbackEval citers (for example RepoDebug, LintEval, WatchPoint, CodeRankEval) are about refactoring, web development, ranking or agent memory, judged from their titles; WatchPoint's abstract was read.
