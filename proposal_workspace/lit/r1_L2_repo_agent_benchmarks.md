### Zhao2026-SusVibes Is Vibe Coding Safe? Benchmarking Vulnerability of Agent-Generated Code in Real-World Tasks
- Authors: Songwen Zhao et al. (with Danqing Wang, Kexun Zhang, Jiaxuan Luo, Zhuo Li, Lei Li); Year: 2026 (arXiv v1 December 2025, v4 September 2026); Venue: ICML 2026, PMLR 306 (stated in the arXiv comment and on the paper's first page; pages not seen)
- URL opened: https://arxiv.org/abs/2512.03262 (arXiv abstract page); https://arxiv.org/pdf/2512.03262v4 (full PDF, read in full)
- Status: VERIFIED
- Tier: A
- Touches: N1, N5
- Checks: (a) partly. The human's vulnerable code and the human's fix are used to validate the tests, but no agent-versus-human rate is reported and there is no control group. (b) partly. Security is judged by unit tests that the human fix commit added, not by exploits. (c) no. Tasks start from the commit just before the fix. (d) no.
- Summary: SusVibes has 186 feature-request tasks from 100 Python repositories in 10 domains, covering 79 CWE types (v4 counts; FALCON, below, describes it as 186 tasks and 77 CWEs). Each task comes from a real vulnerability-fixing commit: the feature is removed from the code just before the fix, and an agent-written request asks for it again. Twelve settings (SWE-agent, OpenHands and Claude Code, each with Claude 4 Sonnet, Kimi K2, Gemini 2.5 Pro and Gemini 3 Pro) reach at most 57.0% FuncPass and 12.9% SecPass (correct and secure). With SWE-agent and Claude 4 Sonnet, 79.3% of functionally correct solutions fail the security tests. Telling the agent the CWE, or asking it to pick likely CWEs first, raises SecPass only to 15.1% and 14.5%, and lowers FuncPass.
- Delta:
  - Task construction. The pipeline starts from about 20,000 fix records in ReposVul and MoreFixes. It keeps Python 3.7+ projects whose fix commit also changes tests (about 450). For each fix, it goes to the commit just before the fix. One SWE-agent instance deletes a region that covers every line the fix changes plus surrounding code. A second instance writes an issue-style request and is told not to mention security. A third instance checks that every line of the fixed implementation is justified by the request. If a line is not justified, the mask is made larger and the request is rewritten. 200 tasks pass execution checks and 186 remain after expert review.
  - Security judgment. The security tests are the tests that the human fix commit added (3.5 per task on average; 66.9 functional tests on average). A task is kept only if the masked code fails all tests, the code before the fix passes the functional tests but fails the security tests, and the fixed code passes both. Five experts reviewed the security tests: 6.5% were tied to the reference fix rather than to the security property, and tests that were partly or fully tied were rewritten. The paper calls test outcomes "a practical proxy for security".
  - Human baseline and control group. Every task is a feature the human wrote with a vulnerability. The paper does not report how often an agent rewrote the human's bug, and it has no tasks where the human wrote the feature correctly.
  - Languages and agents. Python only. SWE-agent, OpenHands and Claude Code; four models; 200 steps; one run per task (pass@1). A short generic security reminder is in every prompt.
  - Numbers. Best FuncPass is 57.0% (SWE-agent with Claude 4 Sonnet), with SecPass 11.8%. Claude Code with Claude 4 Sonnet reaches 41.4% FuncPass and 5.9% SecPass. On the tasks that every model solved correctly, the secure share is 18.3% (Claude 4 Sonnet), 22.0% (Kimi K2), 30.4% (Gemini 2.5 Pro) and 21.4% (Gemini 3 Pro).
  - What SusVibes has that the project lacks: more tasks, repositories and CWE types; an automatic pipeline that builds tasks and Docker environments; Claude Code as a setting; an expert check that tests accept other secure designs; mitigation experiments with CWE hints.
  - What the project has that SusVibes lacks: a per-function comparison with the human on the same request and starting code; a control group of functions the human wrote correctly, with an LLM security review run on both versions and each reported flaw confirmed by a new PoV; Foundry exploits adapted from audit reports instead of unit tests; Solidity business-logic bugs with fund losses; tracing each finding to its vulnerability-introducing commit; repair with a shown PoV and held-out PoVs, and the repair input study; models chosen so their training data ends before the findings were published.
  - Point to check in the proposal. SusVibes builds the request so that every line of the fixed code is justified by it. A request built this way can state the rule that the fix restores without naming security. The project's pilot found that this wording decides the outcome: 12 of 15 runs avoided the bug when the request stated that rule, while all 13 compiled runs wrote it when the request described the human's design. SusVibes does not test what its requests reveal. Also, AuraForge (below, same group) reports that agents retrieved the reference implementation in 16% of 5,174 SusVibes runs. SusVibes removes git history but does not otherwise control for training data.

### Chen2026-SecureVibeBench SecureVibeBench: Benchmarking Secure Vibe Coding of AI Agents via Reconstructing Vulnerability-Introducing Scenarios
- Authors: Junkai Chen et al. (13 authors, last author David Lo); Year: 2026 (arXiv v1 September 2025, first titled "SecureAgentBench: Benchmarking Secure Code Generation under Realistic Vulnerability Scenarios" as cited in SusVibes); Venue: Proceedings of the 64th Annual Meeting of the ACL (Volume 1: Long Papers), ACL 2026, pp. 24144–24168, DOI 10.18653/v1/2026.acl-long.1107
- URL opened: https://arxiv.org/abs/2509.22097 (arXiv abstract page); https://arxiv.org/pdf/2509.22097v5 (full PDF, read in full); https://aclanthology.org/2026.acl-long.1107/ (ACL Anthology page)
- Status: VERIFIED
- Tier: A
- Touches: N1, N5
- Checks: (a) partly. The task is framed as human versus agent, but the human patch is vulnerable by construction; the only direct comparison is a static-analysis count. No control group. (b) yes, for the historical vulnerability (the ARVO PoV); new flaws are only flagged by Semgrep. (c) yes. (d) no.
- Summary: 105 C/C++ memory-safety tasks from 41 OSS-Fuzz projects in ARVO. The agent starts from the parent of the commit where a human introduced the vulnerability and gets a requirement for the change that commit made. Five frameworks and five models are tested; the best pair (SWE-agent with Claude Sonnet 4.5) writes code that is both correct and secure in 23.8% of tasks.
- Delta:
  - Task construction. Starts from 4,993 ARVO vulnerabilities. B-SZZ proposes candidate vulnerability-introducing commits (1,632 instances). The ARVO PoV then confirms each candidate: the fix commit must be safe, the candidate commit vulnerable, and its parent safe (254 instances). After oracle checks (232) and removal of overly complex cases, 105 tasks remain. GPT-4.1 writes each requirement from the human's commit message, the human's patch and the linked issue. The prompt asks it to "cover all aspects of the code change" so that another developer could "implement the same functionality as the gold patch", to leave out implementation detail, and to stay neutral on security. The authors check by hand that requirements are security-neutral and contain no code from the human patch. Requirements average about 200 words.
  - Security judgment. The ARVO PoV checks whether the agent re-created the historical vulnerability ("correct but vulnerable"). Semgrep 1.137.0 with about 2,400 rules marks new risks as "suspicious", not vulnerable. A manual check of 120 flagged programs found 11.4% truly vulnerable, 39.0% risky and 49.6% not vulnerable. Functionality is checked by differential testing against the human patch with the project's test suite (434 test cases on average).
  - Human baseline and control group. The paper argues for comparing agents with humans in the same scenario. Because the human patch is vulnerable by construction, it cannot report a human rate on the PoV. The only direct comparison uses Semgrep: 4.9% of agent patches are suspicious when compared with the code before the patch, and 2.6% when compared with the human patch. There are no tasks where the human made the change correctly.
  - Languages and agents. C/C++ memory-safety bugs (heap buffer overflow, CWE-122, is 46.7% of tasks). SWE-agent 1.1.0, OpenHands 0.50.0 and Aider 0.86.1 with Claude Sonnet 4.5, GPT-5, Claude 3.7 Sonnet, GPT-4.1 and DeepSeek-V3.1, at temperature 0, 75 iterations and a $2 cap, one run each. Also Claude Code with Sonnet 4.5 and Codex with GPT-5.
  - Numbers. Best "correct and secure" rate 23.8%; mean 11.6%. Claude Code: 17.1% correct and secure, 26.7% correct but re-creating the PoV vulnerability. Codex: 19.0% and 21.8%.
  - What SecureVibeBench has that the project lacks: a search for the vulnerability-introducing commit at scale, confirmed by the PoV; differential functional testing against the human patch; cost and time analysis; Aider, SWE-agent and OpenHands with five models.
  - What the project has that SecureVibeBench lacks: a measured rate of how often each agent re-created the human's bug, next to a control group of functions the human wrote correctly; new flaws confirmed by new executable PoVs, where SecureVibeBench only flags them with a tool that was wrong about half the time; Solidity business-logic bugs with fund losses; held-out PoVs and the repair input study; models chosen by training cutoff (SecureVibeBench discusses contamination but does not control it).
  - Point to check in the proposal. SecureVibeBench's requirements are written to reproduce the human's change. Its own example task (rawspeed, ARVO 5296) asks the agent to "ensure (with an assert)" that the value does not exceed the type's maximum. That is the design in the human's vulnerable change: an assert checks the upper bound instead of limiting the value. The agent patch the paper shows as vulnerable followed the request and used the assert; the patch shown as secure limited the value with `std::min` instead. The project's pilot found the same effect: when the request described the human's design, all 13 compiled runs wrote the bug.

### Wu2026-LSCB Last Secure Code Benchmark: Is the Code You Vibe Secure?
- Authors: Tianyi Wu et al. (15 authors, last author See-Kiong Ng); Year: 2026; Venue: arXiv preprint (2610.14766, October 2026)
- URL opened: https://arxiv.org/abs/2610.14766 (arXiv abstract page); https://arxiv.org/html/2610.14766v1 (full text, read for method)
- Status: VERIFIED
- Tier: A
- Touches: N1, N5
- Checks: (a) no measured comparison; the authors note that two models often replayed the upstream code from memory. (b) yes; each security test "drives a proof-of-concept attack through the external surface". (c) no. (d) no.
- Summary: 450 tasks built from 150 real vulnerabilities in seven languages (Java, C, C++, JavaScript, Python, PHP, Go) and 24 CWEs. 115 scenarios are public CVEs from CVE-Factory; 35 are Java scenarios that five security experts built from vulnerabilities in their companies' code. Each scenario gives three tasks: the smallest whole function containing each changed range is removed, the touched files are removed, or a source scope is emptied. Six frontier systems pass functional tests on 73.6%–91.3% of tasks but are functional and secure on only 16.4%–25.1%; the best passes all three versions of a scenario in 12.0% of scenarios. One added sentence asking for security raised one model to 46.2% (+21.5 points).
- Delta: LSCB is the closest design to the project's treatment group outside Solidity: it removes the function that contains the human's vulnerable code and judges the agent's rewrite with attack tests. Its requests are drafted by an agent that did not see the fix, then checked clause by clause by an agent that did see it, for requiring the vulnerable implementation or leaking the fix, and by experts for wording that "pushes the implementer toward the vulnerable design". This overlaps with N5. The project adds what LSCB lacks: a human-versus-agent rate and a control group; Solidity business-logic bugs with fund losses; tracing to the vulnerability-introducing commit; repair with held-out PoVs and the repair input study; model choice by training cutoff (LSCB reports memorised replays but does not control for them). LSCB checks wording but does not measure how wording changes outcomes, which the project's pilot did. One run per task; the agent harness is not described in the parts read [uncertain].

### Shen2025-SecRepoBench SecRepoBench: Benchmarking Code Agents for Secure Code Completion in Real-World Repositories
- Authors: Chihao Shen, Connor Dilgren, Purva Chiniya, Luke Griffith, Yu Ding, Yizheng Chen; Year: 2025 (v1 April 2025, titled "SecRepoBench: Benchmarking LLMs for Secure Code Generation in Real-World Repositories"; v3 February 2026); Venue: arXiv preprint. Semantic Scholar lists the LLM4Code workshop at ICSE, and a search snippet says LLM4Code 2026 [uncertain]; the arXiv page shows no venue.
- URL opened: https://arxiv.org/abs/2504.21205 (arXiv abstract page); https://arxiv.org/html/2504.21205v3 (full text, read for method)
- Status: VERIFIED
- Tier: A
- Touches: N1
- Checks: (a) no; the developer's code is used only to validate tests and the PoV. (b) yes; the OSS-Fuzz PoC is run against the completed code. (c) no; tasks come from fix commits. (d) no.
- Summary: 318 code-completion tasks from 27 C/C++ repositories in ARVO, covering 15 CWEs. Each task masks the smallest set of syntax-tree nodes that covers a developer's security fix (fix commits that change one function), with a GPT-4o-drafted, hand-edited description. Security is judged by compiling the project with the completion and running the OSS-Fuzz PoC (a crash means vulnerable); correctness by the developer unit tests that the fixed code passes. 29 standalone models and 15 agents (OpenHands, Aider, Claude Code) were tested; the best, OpenHands with o3, reaches 53.5% secure-pass@1.
- Delta: Same technique as the project's treatment group (remove the human's vulnerable code, regenerate it, judge with the PoV), but the task is completion of a masked region inside one function, not a feature request, and there is no human-versus-agent rate or control group. Contamination is handled by renaming a local variable; the authors saw literal memorization before renaming. The project adds Solidity business logic, the control group, LLM review confirmed by PoVs, held-out PoVs for repair, the repair input study, and cutoff-based model choice.

### Wang2026-EVMbench EVMbench: Evaluating AI Agents on Smart Contract Security
- Authors: Justin Wang et al. (with Andreas Bigger, Xiaohai Xu, Justin W. Lin, Andy Applebaum, Tejal Patwardhan, Alpin Yukseloglu, Olivia Watkins); Year: 2026; Venue: Proceedings of the 43rd International Conference on Machine Learning (ICML 2026), PMLR 306, pp. 125067–125099 (arXiv 2603.04915)
- URL opened: https://proceedings.mlr.press/v306/wang26k.html (PMLR page); https://raw.githubusercontent.com/mlresearch/v306/main/assets/wang26k/wang26k.pdf (full PDF, read for method and results)
- Status: VERIFIED
- Tier: A
- Touches: N2, N3, N7
- Checks: (a) no. (b) yes; patches are graded by hidden exploit tests, exploits by on-chain balance changes. (c) no. (d) no; the agent never sees an exploit, only hints at three levels.
- Summary: 117 high-severity vulnerabilities from 40 audits, mostly public Code4rena reports (plus a few scenarios for the Tempo chain). Only Solidity bugs that can lose user or platform funds were kept, and bugs found before July 2023 were removed. Three modes: Detect (find the audit's high-severity bugs; scored by recall and by the median historical payout, maximum $218,434); Patch (44 bugs in 22 repositories); Exploit (23 bugs in 16 repositories, graded by replaying the agent's transactions and checking balances). Best Patch 41.7% and Exploit 71.0% (GPT-5.3-Codex with Codex CLI); best Detect 45.9% (Claude Opus 4.6 with Claude Code). With a hint that names the broken mechanism, GPT-5.2 reaches 90.2% on Patch and 78.3% on Exploit. Three runs per setting.
- Delta: EVMbench uses the same data source as the project (Code4rena findings) and the same kind of judge (exploit tests in Foundry-based repositories). Its Patch mode is the closest prior design to N3: the existing tests must still pass and "unseen exploit tests" uploaded at grading time must fail. It also notes that "in some cases, existing tests rely on vulnerable logic" and simply does not penalize those failures; the project instead measures how such tests steer the agent (N4). Differences: EVMbench has no feature-writing task, no human-versus-agent comparison and no control group; its agent must find the bug itself and is never shown a PoV, so it cannot test whether a shown PoV leads to a narrow fix; it does not vary the repair input or terminal access; and it reports payouts and balance-based success, not an estimate of who loses how much for each exploit. Task overlap with the project's findings should be checked, since both draw on Code4rena.

### Iranmanesh2026-P2Patch P2Patch: Exploit-Guided Vulnerability Repair
- Authors: Mohsen Iranmanesh, Sina Moradi Sabet et al. (10 authors, last author Mohammad A. Tayebi); Year: 2026; Venue: arXiv preprint (2610.20245, October 2026)
- URL opened: https://arxiv.org/abs/2610.20245 (arXiv abstract page); https://arxiv.org/pdf/2610.20245v1 (full PDF, method and results read)
- Status: VERIFIED
- Tier: A
- Touches: N3, N4
