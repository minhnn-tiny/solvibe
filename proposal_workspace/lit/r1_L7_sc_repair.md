### Wang2026-EVMbench EVMbench: Evaluating AI Agents on Smart Contract Security
- Authors: Justin Wang et al. (OpenAI, Paradigm, OtterSec, as listed in the PDF); Year: 2026; Venue: ICML 2026, Proceedings of the 43rd International Conference on Machine Learning, PMLR vol. 306, pp. 125067–125099 (arXiv 2603.04915)
- URL opened: https://arxiv.org/abs/2603.04915 (arXiv abstract page); https://arxiv.org/pdf/2603.04915 (PDF, Sections 3–4 and Appendices B, F, G, H read); https://proceedings.mlr.press/v306/wang26k.html (PMLR proceedings page)
- Status: VERIFIED
- Tier: A
- Touches: N2, N3, N4
- Summary: The benchmark draws 117 high-severity vulnerabilities from 40 Code4rena audit repositories and has three modes: Detect, Patch (44 vulnerabilities from 22 repositories) and Exploit (23 vulnerabilities from 16 repositories). In Patch, the agent gets the repository, its test suite and a shell, and must find and fix loss-of-funds bugs; it is not told which bug is graded. GPT-5.3-Codex in Codex CLI scored highest on Patch (41.7%); when GPT-5.2 was given a medium hint (a location plus a short description of the broken mechanism) it reached 90.2% on Patch, and the authors conclude that Patch difficulty comes mostly from finding the bug. Listed Patch failure modes include fixing a different bug and "a narrow fix that does not block the exploit path".
- How patches are judged: (a) exploit tests that the agent never saw, uploaded at grading time, plus the repository's original tests; original tests that rely on the vulnerable behaviour are excused, and test files the agent may not edit are reset first; (b) yes, the exploit tests are held out, but the agent is shown no exploit, and grading appears to use one exploit reproduction per vulnerability [uncertain]; (c) partly: hint levels vary (none, low = a file or contract name, medium = location plus mechanism); the agent always has a full shell; no audit report or exploit is ever given as input.
- Delta: EVMbench measures repair at scale across 22 repositories, adds Detect and Exploit modes, and shows that with a location-plus-mechanism hint GPT-5.2 reaches 90.2% on Patch, far above the best score without hints (41.7%). It does not show the agent any exploit, so it cannot measure whether an agent fits a shown failing test; the project shows one PoV as a failing test and holds back the others for each finding. EVMbench never changes what the agent can run; the project compares no execution, the shown test only, and a full terminal. EVMbench excuses tests that assert the buggy behaviour at grading time but does not study how such tests steer the agent; the project reports that agents with a terminal kept those tests passing and so kept the bug. EVMbench has no human baseline, no control group of correctly written functions, and no per-exploit loss estimate (its Detect mode uses historical audit payouts).

### Huang2026-CyberChainBench CyberChainBench: Can AI Agents Secure Smart Contracts Against Real-World On-Chain Vulnerabilities?
- Authors: Jintao Huang et al.; Year: 2026; Venue: arXiv preprint (arXiv 2606.26216)
- URL opened: https://arxiv.org/abs/2606.26216 (arXiv abstract page); https://arxiv.org/pdf/2606.26216 (PDF, task design, grading and results read)
- Status: VERIFIED
- Tier: A
- Touches: N2, N3, N7
- Summary: The benchmark holds 541 DeFiHackLabs incidents on 9 EVM chains, each pinned to a block, with tasks for detection, exploit generation (200 cases) and patch synthesis (94 proxy-upgradeable cases). The patch check compiles the patched contract, injects it at the vulnerable address with `vm.etch`, replays the original attack transaction (it must revert or keep under 1% of the original profit), and replays past legitimate transactions to the same entry point (all must succeed). The best patch pass rate was 23.4% (Codex with GPT-5.5, which blocked 47.9% of attacks); Gemini 3.1 Pro blocked 98.9% but passed 1.1%, because its patches broke normal callers. Exploits are graded by profit in US dollars; the top agent realised $57.4M across the 200 exploit cases.
- How patches are judged: (a) replay of the historical attack transaction plus replay of historical legitimate transactions; (b) no: the agent receives the attack transaction hashes and a trace tool, can call the same `validate_patch` check repeatedly for 30 minutes, and that same attack is the final judge; (c) no: every patch task gets the vulnerability type, the function to fix and the attack transactions.
- Delta: CyberChainBench uses real incidents on historical chain state, checks functionality with real user transactions, and grades exploits by realised profit. Because the shown attack is also the judge, a patch that blocks only that one transaction counts as a success; the project holds back PoVs that the agent never sees, so it can count such shallow repairs. CyberChainBench does not vary the repair input or what the agent can run, has no human-written version to compare against, and measures the attacker's historical profit rather than estimating who loses how much under each PoV.

### Germano2025-ExploitReplayRepair Repairing DeFi Vulnerabilities: Benchmarking LLMs with Executable Solidity Exploits
- Authors: Lucas Bastos Germano and Julio Cesar Duarte (Military Institute of Engineering, Brazil); Year: 2025; Venue: Anais Estendidos do XXXI Simpósio Brasileiro de Sistemas Multimídia e Web (WebMedia 2025), Workshop Brasileiro de Sistemas Web3, pp. 311–315, DOI 10.5753/webmedia_estendido.2025.16331
- URL opened: https://sol.sbc.org.br/index.php/webmedia_estendido/article/view/38210 (publisher page); https://sol.sbc.org.br/index.php/webmedia_estendido/article/download/38210/37985 (PDF, read in full)
- Status: VERIFIED
- Tier: A
- Touches: N2, N3
- Summary: Six reproducible DeFiHackLabs incidents (BBX, BTNFT, DCF, H2O, IPC, SR) and nine LLMs give 54 repair runs. Each model gets the main vulnerable contract and a vulnerability description in one prompt; the patched contract is compiled, its bytecode is swapped in at the original address on a forked chain, and the original exploit is replayed. For hard cases the authors changed the exploit to allow other attack paths and varied state (more attack rounds, shifted block time and height). GPT-5, GPT-4.1 and Claude Opus 4.1 mitigated 4 of 6 cases; Phi-4 and Qwen2.5-Coder-32B mitigated 2; no model fixed H2O under the strengthened checks, and some failed repairs "blocked the specific trace used by the original attacker but left alternative sequences open".
- How patches are judged: (a) replay of the incident's exploit on a forked chain, plus basic sanity flows; (b) partly: the model never sees the exploit, and the changed exploits act as extra checks beyond the original attack path, but there is no designed split between a shown test and held-out tests; (c) no: the input is always the code fragment plus a description, in a single prompt, and the model runs nothing.
- Delta: This paper reports the same failure the project targets (a fix that stops the original attack trace but leaves another attack path open) and catches it with exploit variants. It covers six cases, uses single prompts rather than coding agents in a repository, and gives the model no exploit, no tests and no terminal. The project builds validated Foundry PoVs per audit finding, shows one as a failing test and holds back the others, varies the input (location, report, PoV, report and PoV) and what the agent can run, compares the agent with the human developer, and estimates the loss of each exploit.

### Bobadilla2025-ExploitMitigation Do Automated Fixes Truly Mitigate Smart Contract Exploits?
- Authors: Sofia Bobadilla, Monica Jin and Martin Monperrus (KTH); Year: 2025; Venue: IEEE Transactions on Software Engineering, 2025 (DOI 10.1109/TSE.2025.3618123; journal reference shown on the arXiv page)
- URL opened: https://arxiv.org/abs/2501.04600 (arXiv abstract page); https://arxiv.org/pdf/2501.04600 (PDF, Sections III–V read)
- Status: VERIFIED
- Tier: A
- Touches: N2, N3
- Summary: The authors review 20 smart-contract repair tools and run the 7 they could reproduce: sGuard, sGuard+, SmartFix, SolGPT (their name for Napoli and Gatteschi's ChatGPT method), TIPS, Elysium and SmartShield. They wrote 91 executable Hardhat exploits for SmartBugs-Curated (52 of its 143 contracts could not be exploited) and a hand-written functional check for each. Exploit mitigation ranged from 29% (SmartShield, 26 of 91) to 74% (SolGPT, 67 of 91); bytecode tools often broke functional checks (Elysium 26 of 91, SmartShield 21 of 91). Of 111 exploit-blocking patches reviewed by hand, 108 were correct; for bad randomness, every reviewed patch blocked the exploit by changing the hash function but kept the same insecure pattern, which the authors name as a limit of judging by exploits.
- How patches are judged: (a) executable exploits plus functional checks made of benign transactions, then manual review of a sample; (b) in effect yes, since the tools never see the exploits (most take static-analyser output), but each contract has one exploit and there is no split between a shown and a held-out exploit; (c) no, each tool gets its own usual input.
- Delta: This is the first study to measure repair tools by whether real exploits still work, and it describes patches that stop the concrete exploit while the weakness remains. It tests older non-agent tools on small, older contracts from SmartBugs-Curated with classic bug classes such as reentrancy and unchecked calls. The project tests coding agents on business-logic bugs from audit contests, uses several PoVs per finding where possible, shows one PoV and holds back the others so that the failure these authors describe can be counted, varies input and execution access, and compares the agent's code with the human developer's code.

### Zhang2025-ACFIX ACFIX: Guiding LLMs with Mined Common RBAC Practices for Context-Aware Repair of Access Control Vulnerabilities in Smart Contracts
- Authors: Lyuye Zhang et al. (Nanyang Technological University); Year: 2025 (arXiv 2024); Venue: IEEE Transactions on Software Engineering, 2025 (DOI 10.1109/TSE.2025.3590108, from OpenAlex and Semantic Scholar records; the arXiv page calls it a technical report); listed on the ICSE 2026 journal-first programme
- URL opened: https://arxiv.org/abs/2403.06838 (arXiv abstract page); https://arxiv.org/pdf/2403.06838 (PDF, evaluation section read)
- Status: VERIFIED
- Tier: B
- Touches: N2, N3
- Summary: ACFIX mines 49 common role-permission pairs from 344,251 on-chain contracts. GPT-4 then uses chain-of-thought prompting to pick a pair and write a patch, and a debate between generator and verifier agents checks it. On a new benchmark of 118 real access-control vulnerabilities, ACFIX repaired 94.92%, against 52.54% for plain GPT-4.
- How patches are judged: (a) three checks: comparison with 20 real developer fixes, DeFiHackLabs exploit scripts run on the original and repaired code for the 28 cases taken from DeFiHackLabs, and manual review by two authors; (b) the exploit scripts are not shown to the model, one per case, with no designed split; (c) the input is the contract plus a written vulnerability description; one extra experiment gave only the vulnerable function with no description, but it tested locating the flaw, not repairing it.
- Delta: ACFIX targets one bug class with mined domain knowledge and uses exploits as one of three judges. It does not use coding agents, does not hold back exploits by design, and does not ask whether the description or an exploit helps the repair. The project covers business-logic bugs, judges every repair with PoVs including held-out ones, and varies the input and execution access.

### Eshghie2025-FLAMES FLAMES: Fine-tuning LLMs to Synthesize Invariants for Smart Contract Security

### Torres2022-Elysium Elysium: Context-Aware Bytecode-Level Patching to Automatically Heal Vulnerable Smart Contracts
- Authors: Christof Ferreira Torres, Hugo Jonker and Radu State; Year: 2022; Venue: RAID 2022, 25th International Symposium on Research in Attacks, Intrusions and Defenses (DOI 10.1145/3545948.3545975 per OpenAlex)

- Status: VERIFIED
- Tier: B
- Touches: N2

- How patches are judged: (a) replay of historical transactions on patched contracts, with bug finders choosing what to patch; (b) no; (c) no.
- Delta: A bytecode tool for known bug classes, judged by transaction replay. The project repairs source code with agents, and its held-out PoVs test whether the fix generalises beyond one attack.
