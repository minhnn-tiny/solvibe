## New papers (not in the master index)

### Wang2026-PatchFuzz PatchFuzz: Patch Fuzzing for JavaScript Engines
- Authors: Junjie Wang et al. The arXiv version lists Junjie Wang, Yuhan Ma, Xiaofei Xie, Xiaoning Du and Xiangwei Zhang. The journal version, per Crossref and OpenAlex, lists Zhihua Xie in place of Yuhan Ma. Year: 2026; Venue: Information and Software Technology, vol. 194, article 108087 (June 2026), DOI 10.1016/j.infsof.2026.108087. First posted as an arXiv preprint (arXiv:2505.00289, 1 May 2025).
- URL opened: https://arxiv.org/abs/2505.00289 (arXiv abstract page) and https://arxiv.org/pdf/2505.00289 (full PDF; I read the introduction, the motivating example, the results and the case study). The journal details come from the Crossref record (https://api.crossref.org/works/10.1016/j.infsof.2026.108087). The ScienceDirect page returned HTTP 403.
- Status: VERIFIED
- Tier: B
- Touches: N3
- Summary: Patch fuzzing tests the code that a security patch just changed. The aim is to find bugs that the patch did not fully fix or that it added. PatchFuzz finds security-fix commits in open-source JavaScript engines with heuristic rules. It takes the PoC that developers committed as a regression test, makes it runnable, and uses it as a fuzzing seed. It instruments only the code that the call graph of the patch points to, and it mutates the PoC lightly so that it keeps what made it trigger the bug. The motivating example is a ChakraCore bug: the patch for CVE-2018-0777 was bypassed by adding one statement to its PoC (this became CVE-2018-8137), and the next patch was bypassed again in the same way. In 7-day campaigns PatchFuzz found 54 bugs in six engines (21 in JavaScriptCore, 7 in V8, 3 in SpiderMonkey, 3 in ChakraCore, 13 in JerryScript, 7 in QuickJS). 25 received CVE IDs and the bounties totalled $62,500. When its seeds were replaced with the corpus of an earlier fuzzer (DIE), it reproduced only 2 of the 54 bugs. The paper does not count how many of the 54 bugs bypass a specific earlier patch. The authors say that linking found bugs to the historical PoCs is hard to validate.
- Delta: The paper shows, on human patches, that small changes to the PoC a patch was checked against can reach code the patch left vulnerable. This supports the project's claim under N3 that a repair which blocks the shown PoV is not shown to be complete. The differences are large. First, its extra inputs come from automatic mutation of one PoC near the patched code. The project's held-out PoVs are written by hand from audit reports and can follow a different attack path, which local mutation may not reach. Second, it judges with crash sanitizers on memory-safety bugs. The project judges business-logic bugs with Foundry assertions on funds. Third, it studies human patches in browser engines over several years. It has no agents, no repair inputs to vary, no limits on running code, and no smart contracts or losses. The project can cite it next to Evocatio, Sleuth and SlicePatch, which are already indexed, as evidence that mutating the given PoC finds bypasses of patches. A small set of mutated versions of the shown PoV would also be a cheap extra check on agent repairs; this is my suggestion, not the paper's.
