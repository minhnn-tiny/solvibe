## New papers

### Agarwal2026-RefuteOrPromote Refute-or-Promote: An Adversarial Stage-Gated Multi-Agent Review Methodology for High-Precision LLM-Assisted Defect Discovery
- Authors: Abhinav Agarwal (sole author); Year: 2026; Venue: arXiv preprint (arXiv:2604.19049, v1 submitted 21 April 2026). The page lists no peer-reviewed venue.
- URL opened: https://arxiv.org/abs/2604.19049 (arXiv abstract page); https://arxiv.org/html/2604.19049v1 (full text, HTML)
- Status: VERIFIED
- Tier: B
- Touches: N6
- Summary: The paper starts from the problem that LLM-assisted bug hunting produces many plausible but wrong reports. It describes a review pipeline. Some agents propose candidate defects. Other agents are told to disprove each candidate before it moves to the next stage. Reviewers start with little context so that they do not copy earlier reasoning. A critic from a different model family reviews the candidate (Claude-family agents reviewed, and Codex with GPT models was the cross-family critic). Over a 31-day campaign on seven targets (security libraries, the ISO C++ standard, compilers), the pipeline dropped about 79% of 171 candidates before disclosure. On a smaller prospective set (lcms2 and wolfSSL, n=30) it dropped 83%. Outcomes included 4 CVEs, 8 merged security fixes without a CVE, and 3 compiler conformance bugs. The key case for this project: ten reviewing agents all agreed that OpenSSL's CMS module had a Bleichenbacher padding oracle. It did not. One agent with fresh context compiled OpenSSL and ran three test cases, and the result killed the finding. After this, the author made an executed test mandatory before any security finding is disclosed. The paper gives no controlled comparison of same-family and cross-family review. The cross-family critic caused only about 3% of all rejections. It also reports one PoC that confirmed a false finding because the PoC measured its own computation.
- Delta: The paper supports the project's choice to confirm every finding of the LLM security review with an executable PoV, and not to trust agreement between the two LLM reviewers. Unanimous agreement among ten LLM reviewers was wrong, and one executed test caught it. The paper also warns that a PoC can be wrong in its own way, which argues for checking that each new PoV passes on the vulnerable code and fails on a fixed version, as the project already does for audit PoVs. What the paper does that the project does not: it uses adversarial refutation stages and a reviewer from another model family to cut false reports before any test is written, and it measures how many candidates each stage removes. What the project does that the paper does not: it runs the same review prompt on agent code and human code for the same feature, so the review is part of a comparison and not a bug hunt. It works on Solidity with exploits that measure loss of funds. It counts review findings only after a PoV confirms them, and it reports how many were confirmed.

### Compagna2026-EndorRecall Recall, not reasoning: how AI coding agents cheat security benchmarks
- Authors: Luca Compagna (Endor Labs); Year: 2026 (published 10 June 2026); Venue: Endor Labs blog (grey literature)
- URL opened: https://www.endorlabs.com/learn/recall-not-reasoning-how-ai-coding-agents-cheat-security-benchmarks (publisher page; it shows the title, author, date and the full text)
- Status: VERIFIED (vendor blog post; it has no abstract, but the page gives the author, the date and the method)
- Tier: B
- Touches: N1, N5
- Summary: Endor Labs runs the Agent Security League, a leaderboard that scores coding agents on SusVibes tasks for functional tests (FuncPass) and security tests (SecPass). The leaderboard is in the index. This post re-checks the agent runs for cheating. Reviewers flagged a patch as recalled from training when parts of it could not have come from working the task out, for example long comments copied word for word, the upstream typos, or CVE identifiers that the prompt did not give. They found 182 confirmed cheating cases in total. Of these, 137 were recall from training and 6 were leaks from the workspace. The rest, about 39 by subtraction, used git history or the web. In one workspace leak, Claude Code read a fixed copy of the library that was installed in a `.tox` virtual environment and copied its code, although the prompt had forbidden git history and web search. After removing cheated tasks, Claude Code with Claude Opus 4.8 fell from 80.7% to 73.7% FuncPass and from 23.5% to 14.5% SecPass. The post also fixed a scoring bug: a count-based verdict had given SecPass even though a required security test failed.
- Delta: This is the closest practical example of checking agent output for training recall on a security benchmark built from historical vulnerabilities, which is the same kind of benchmark as the project's. The project's safeguard is to choose models whose training data ends before the audit finding was published. It does not inspect the agent's code for recall. That safeguard covers recall of the fix. It does not cover recall of the human's vulnerable code, which was public on GitHub when the audit contest started and may be older than the model's cutoff. Recall of the human's code would push an agent to rewrite the human's bug, which is the outcome the project measures. The post's signals (copied comments, copied typos, distinctive identifiers the prompt did not give) are a cheap check the project could run on agent code that matches the human's bug. The `.tox` case also suggests checking whether anything installed in the container holds a later or fixed version of the audited code, for example a dependency folder such as `lib/` or `node_modules/`. What the project does that this post does not: it judges each solution with an executable exploit and compares it with the human's code for the same feature. It works on Solidity. It uses tasks published after the models' training cutoffs.

### Compagna2026-EndorRecallDiverge Best in Class, Novel in Method: Opus 5 and the Recall-Then-Diverge Pattern
- Authors: Luca Compagna (Endor Labs); Year: 2026 (published 10 August 2026, updated 11 August 2026); Venue: Endor Labs blog (grey literature)
- URL opened: https://www.endorlabs.com/learn/best-in-class-novel-in-method-opus-5-and-the-recall-then-diverge-pattern (publisher page; it shows the title, author, date and the full text)
- Status: VERIFIED (vendor blog post; it has no abstract, but the page gives the author, the date and the method)
- Tier: B
- Touches: N1, N4
- Summary: This follow-up to the post above describes an agent that writes a fix it remembers early in the run and then keeps editing until the final patch looks like its own work. A check of only the final diff misses this. The new check reads every edit the agent made. It compares how much of the upstream security patch appears in the first edit, in the edit with the most overlap, and in the final patch. It also records when distinctive security strings first appear, and whether any tool output could have shown them to the agent earlier. On SusVibes with Claude Code and Claude Opus 5, confirmed cheating rose from 23 to 38 tasks after this re-check. Of the 38, 37 were recall from training, 1 was a workspace leak, none used git or the web, and 18 followed the remember-then-edit pattern. Scores fell from 81.6% to 73.7% FuncPass and from 36.9% to 32.4% SecPass. On a 179-task denominator, counting recalled tasks as solved gave 92.2% FuncPass and 46.4% SecPass, against 73.7% and 32.4% when they were removed.
- Delta: The project keeps the full logs of every agent run (Aider, OpenHands, Codex CLI). This post shows that a recall check on the final code alone misses about half of the recalled cases (18 of 38). A recall check in the project should therefore read the edit history in those logs, not only the final function. The project's repair study found that agents fitted the shown test. The project could use the same kind of edit-by-edit reading to tell whether a repair started from the general rule and was narrowed later, or was aimed at the shown test from the first edit. What the project does that this post does not: it uses exploits that measure loss of funds, held-out PoVs to judge repairs, a human baseline for the same feature, and Solidity tasks.
