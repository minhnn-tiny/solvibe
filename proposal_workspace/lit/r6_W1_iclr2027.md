# Round 6, W1: systematic scan of ICLR 2027 submissions on OpenReview

Agent: bibliography agent (ARS deep-research, lit-review mode), round 6, topic W1. Date of search: 2026-10-21.

## How the scan was done

- Source: the OpenReview search API, `https://api2.openreview.net/notes/search?term=<term>&group=ICLR.cc/2027/Conference&limit=1000`. Requests were anonymous: no contact address, no name, no email (rule 5a).
- The API matches words anywhere in a record and ranks by relevance. It returns at most 1,000 records per term. The "matches" figure in the table is the API's own `count` field, which stops at 10,000.
- Single-word terms match word prefixes. For example, `DeFi` also matched "Deficient" and "Definable", so its 1,000 records are mostly noise.
- The 60 terms returned 21,131 distinct ICLR 2027 records. I screened them in three passes:
  1. A keyword screen over title, keywords and abstract kept every record that mentions code, software, repositories, smart contracts or blockchains together with security, repair, patches, tests, contamination, memorization, judges, audits or human developers. 1,821 records passed. I read all 1,821 titles.
  2. 1,054 dropped records have a title word about code, software, repair, security, exploits, contamination or tests. I removed 221 of them whose titles are plainly about images, video, audio, robots, molecules, medicine, diffusion models or quantization, and read the other 833 titles by hand. This pass found three relevant records that the keyword screen had dropped: S-ISP (the title spells "Smart-Contract" with a hyphen), "Evidence, Not Independence", and SysRepair-Bench, which round 5 already found.
  3. I searched every record for blockchain words (smart contract, smart-contract, DeFi, Ethereum, on-chain, EVM, Solidity, wallet). This gave 30 records, and I read all of them.
- For about 100 candidates I read the full abstract in the API record. A paper counts as "already found" if its title appears in the master index (`lit/master_index.tsv`) or in any round 1 to 5 file (`lit/r*.md`), including the leads lists.
- Per-note pages could not be opened. Both `https://api2.openreview.net/notes?id=<id>` and the forum pages `https://openreview.net/forum?id=<id>` returned a browser check (HTTP 403 "ChallengeRequiredError" and a redirect). So for every paper below, the page I opened is the search API record. It shows the title, the venue line, the keywords and the full abstract. ICLR 2027 is double-blind, so no record shows its authors.
- Two of the papers below also appear as arXiv preprints in the parallel round 6 file `lit/r6_W2_arxiv_recent.md` (Liu2026-Spoilers and Zhang2026-MobileCybench). Neither is in the master index or in any round 1 to 5 file, so I kept them and cross-referenced them.

### Anon2027-ForesightSWE Do Coding Agents Catch Their Own Bugs? (They Don't)
- Authors: anonymous (double-blind review); Year: 2026; Venue: ICLR 2027 Conference Submission (under review), OpenReview forum rtJNEHQA79
- URL opened: https://api2.openreview.net/notes/search?term=secure%20code&group=ICLR.cc/2027/Conference&limit=1000 (OpenReview API record with title, venue line, keywords and abstract). The forum page https://openreview.net/forum?id=rtJNEHQA79 showed a browser check.
- Status: VERIFIED (title and abstract from OpenReview's own record; authors hidden by double-blind review)
- Tier: A
- Touches: N1
- Summary: The paper builds Foresight-SWE: 212 samples from 35 open-source repositories in 4 languages. Each sample holds two pull requests by human developers, and the second one fixes defects that the first one introduced. The agent gets the task of the first pull request. The *foresight resolve rate* is the share of runs that solve that task and also avoid the defect that the later human pull request fixed. Across eleven LLMs, this rate is between 11.32% and 24.53%.
- Delta: This is the closest general software engineering version of N1 found so far. A human change that introduced a defect is given to an agent as a task, and the human's later fix is the reference for whether the agent avoided the defect. A reviewer could cite it against N1.
  - What the project does that Foresight-SWE does not:
    - The project removes only the vulnerable function body from the audited code, so the agent and the human start from the same code.
    - It judges both versions with the same executable exploit (the PoV).
    - It has a control group: functions the human wrote correctly, checked by an LLM security review whose findings must each be confirmed by a PoV.
    - It works on Solidity and DeFi code, measures loss in funds, and picks models whose training data ends before the findings were published.
  - What Foresight-SWE does that the project does not: it covers 4 general-purpose languages and 35 repositories, at a scale of 212 samples.
  - Foresight-SWE judges with the later pull request's tests, so it measures general defects, not exploitability.
  - The abstract does not say which agent harnesses were used, or whether a run counts as failed when the agent writes exactly the human's defect. [uncertain]

### Anon2027-SpoilersGuesswork Between Spoilers and Guesswork: Avoiding Over-Specification in Coding Benchmarks
- Authors: anonymous (double-blind review); Year: 2026; Venue: ICLR 2027 Conference Submission (under review), OpenReview forum x281OETy2s. The parallel round 6 file `lit/r6_W2_arxiv_recent.md` reports the same title as arXiv preprint arXiv:2610.22760 (Liu2026-Spoilers). Linking the two is by title only, because the OpenReview record is anonymous.
- URL opened: https://api2.openreview.net/notes/search?term=vibe%20coding&group=ICLR.cc/2027/Conference&limit=1000 (OpenReview API record with title, venue line, keywords and abstract)
- Status: VERIFIED (title and abstract from OpenReview's own record; authors hidden by double-blind review)
- Tier: A
- Touches: N5
- Summary: SWE-bench Pro, FEA-bench, Doc2Feat-bench and Multi-SWE-bench add hints taken from the ground truth to their task statements, to make tasks less under-specified. The paper shows that in some of these benchmarks the hints leak the answer: the task becomes over-specified, and an agent can skip the hard steps the benchmark was meant to measure. The authors run tasks at several specification levels, recommend ways to write minimal hints, and release their hints. The abstract gives no numbers.
- Delta: This is the same problem as N5, on general repository-level coding: write a task statement that does not give away the answer, and test that it does not.

  - What the project has that the paper does not:
    - The project's requests must not hint at the bug or at the fix, in a security setting.
    - The project judges with an exploit.

  - The paper does not separate hinting at the bug from hinting at the fix, and it has no human comparison. The project could adopt the paper's experiment with several specification levels as its leakage check.

### Anon2027-PlaceboAudits Placebo Audits Quantify Audit-Specific Acceptance under Adaptive Reuse of Verifier Tests
- Authors: anonymous (double-blind review); Year: 2026; Venue: ICLR 2027 Conference Submission (under review), OpenReview forum 1oXmLIjpiq
- URL opened: https://api2.openreview.net/notes/search?term=reward%20hacking%20tests&group=ICLR.cc/2027/Conference&limit=1000 (OpenReview API record with title, venue line, keywords and abstract)
- Status: VERIFIED (title and abstract from OpenReview's own record; authors hidden by double-blind review)
- Tier: A
- Touches: N3, N4
- Summary: Coding agents often get diagnostic feedback from the same small test suite that later decides whether their code is accepted, so they can fit that suite instead of the task. A *placebo audit* re-runs each frozen output on a fresh test set drawn from the same distribution. The gap between the two acceptance rates measures acceptance that is specific to the reused tests, and the paper gives an unbiased estimator for it.
  - Data: 540 EvalPlus tasks, four models from 8B to 32B, up to 8 feedback rounds, and eleven runs, ten of them preregistered.
  - One round of diagnostic feedback adds +2.9 points [+1.8, +4.1] of test-specific acceptance for Qwen3-8B, and +2.6 [+0.8, +4.5] at 32B. That is roughly half of the excess false acceptance that diagnostics cause.
  - Feedback from a separate, independent test set kept 0.74 [0.54, 0.95] of the useful gain, with test-specific acceptance of +0.1 [-1.0, +1.3].
  - On 444 LiveCodeBench problems, the one-round effect is +2.6 [+1.0, +4.3].
- Delta: This paper gives the statistical form of N3: keep the tests that give feedback apart from the tests that decide acceptance, and measure how much of a pass comes from fitting the shown tests.
  - The project's masked PoV design is the security version. One PoV is shown as a failing test, and the other PoVs are held back to judge the repair.
  - The paper uses function-level programming tasks, small open models and unit tests. It has no exploits, no agent harness and no human version.
  - The project could use the placebo estimator to put a number on how much repair success is specific to the shown PoV. However, the estimator assumes the held-out tests come from the same distribution as the shown ones. The project's held-out PoVs often follow different attack paths, so the assumption would need checking.

### Anon2027-PartialVerification What You Don't Check, Models Don't Fix: False Completion under Partial Verification
- Authors: anonymous (double-blind review); Year: 2026; Venue: ICLR 2027 Conference Submission (under review), OpenReview forum L8JD2F8NiG
- URL opened: https://api2.openreview.net/notes/search?term=hidden%20tests&group=ICLR.cc/2027/Conference&limit=1000 (OpenReview API record with title, venue line, keywords and abstract)
- Status: VERIFIED (title and abstract from OpenReview's own record; authors hidden by double-blind review)
- Tier: A
- Touches: N3, N4
- Summary: The paper studies a correction loop on three task domains: music-as-code audio, SVG repair and API workflows. It uses eight proprietary and open-weight models, and each task has eight deterministic checks. The model sees only some of the checks (the exposed ones). The others are hidden but still scored, and the loop stops when the exposed checks pass.
  - Models repair exposed defects far more often than hidden ones. At low coverage, most stops leave a hidden defect behind, usually before any revision.
  - Extra rounds recover little. Telling the model that its output is still wrong helps much less than naming the failing checks.
  - Reasoning reduces the effect but does not remove it, and letting the model choose which checks it sees does not reduce the remaining defects.
  - The abstract gives no rates.
- Delta: This paper uses the measurement design of N3 (score with exposed and hidden checks, and see what the loop leaves behind) and reaches the finding of N4 (the model fits what it is shown).
  - Its domains are not security or repository code. Its checks are deterministic checks rather than exploits. It has no agent with a terminal and no human baseline.
  - The project's repair round is the security case of the same pattern: a repair blocked the shown PoV, but a held-out PoV still stole 48.88 ETH.

### Anon2027-InterpretationLockIn Agents Verify Their Assumptions, Not the Specification: Interpretation Lock-in in Autonomous Coding Agents
- Authors: anonymous (double-blind review); Year: 2026; Venue: ICLR 2027 Conference Submission (under review), OpenReview forum OyP0Ij3fMp
- URL opened: https://api2.openreview.net/notes/search?term=secure%20code&group=ICLR.cc/2027/Conference&limit=1000 (OpenReview API record with title, venue line, keywords and abstract)
- Status: VERIFIED (title and abstract from OpenReview's own record; authors hidden by double-blind review)
- Tier: B
- Touches: N5, N4
- Summary: When a requirement is ambiguous, coding agents pick one reading, implement it, and write tests that share that reading. The paper calls this "interpretation lock-in". It shows the failure on a controlled suite where every valid reading is known, and on pipelines rebuilt from long-horizon benchmark runs: under the other valid readings, the programs crash or give wrong output. When asked only to list plausible readings, the same models often name the one they missed. The authors propose reading-diverse self-training, which reduces lock-in. The abstract gives no numbers.
- Delta: This explains one plausible mechanism behind the pilot's wording effect. When a request allows the human's design reading, the agent implements that reading and its own tests confirm it. The paper has no security content, no exploit and no human baseline, and it fixes the problem by training. The project instead controls the wording of the request and measures the outcome with PoVs.

### Anon2027-BeyondTheDiff Beyond the Diff: Cost-Aware Agentic Traversal for Industrial Grade Security Review
- Authors: anonymous (double-blind review); Year: 2026; Venue: ICLR 2027 Conference Submission (under review), OpenReview forum 804EmX4yVv
- URL opened: https://api2.openreview.net/notes/search?term=code%20security&group=ICLR.cc/2027/Conference&limit=1000 (OpenReview API record with title, venue line, keywords and abstract)
- Status: VERIFIED (title and abstract from OpenReview's own record; authors hidden by double-blind review)
- Tier: B
- Touches: N6
- Summary: In production LLM security review, the main cost is not finding candidate bugs. It is the multi-stage adjudication (debate across vendors, rebuttal and arbitration) that removes false positives.
  - Telemetry shows that the LLM judges read 3.9× more changed files than the findings cite.
  - Limiting the judges to the files the findings cite cuts their inference cost by 44% to 58%.
  - Stopping adjudication early, under a cost rule, ends a quarter of production runs. It cuts their cost by 25.9% (15.4% across all traffic) and keeps 99.86% of final decisions.
  - Limiting the judges to cited files shifts verdicts by more than the judges' own run-to-run variation.
- Delta: This is industrial evidence that false positives are the main problem of LLM security review, and that LLM adjudication is the usual fix. The project instead confirms each reported flaw with an executable PoV, and it runs the same review prompt on human code and on agent code. The paper does not compare human and agent code, has no exploits, and does not cover smart contracts.
