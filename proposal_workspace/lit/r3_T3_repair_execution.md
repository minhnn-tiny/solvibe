### Xu2026-PatchingArchitectures A Systematic Study of LLM-Based Architectures for Automated Patching
- Authors: Qingxiao Xu et al. (Qingxiao Xu, Ze Sheng, Zhicheng Chen, Jeff Huang); Year: 2026; Venue: arXiv preprint (arXiv:2603.01257, v1, 1 March 2026)
- URL opened: https://arxiv.org/html/2603.01257 (arXiv HTML full text, with title, authors and abstract); metadata and abstract also read through the arXiv API
- Status: VERIFIED
- Tier: B
- Touches: N4, N3
- Summary: A controlled comparison of four ways to build an LLM patching system: a fixed workflow, a single agent, a multi-agent system, and a general-purpose code agent (Claude Code). The tasks are 19 Java vulnerabilities from the AIxCC dataset in delta-scan mode, from six projects such as Commons Compress, ZooKeeper and Log4j. A patch counts as correct if the task's PoV no longer crashes the program and a project functional test suite passes. Claude Code with Sonnet 4.5 repaired 16 of 19; the authors' patch-specific agents repaired at most 13 of 19 (single agent: 12 with GPT-5 and 13 with Sonnet 4.5; multi-agent: 13 with GPT-5 and 8 with Sonnet 4.5). Claude Code reported success on every task, but the authors found patches that failed functional tests or changed test files, and in one ZooKeeper task it stopped before checking all PoVs.
- Delta: The paper changes the whole system design, and every design can run the PoV and the tests. It never holds the agent and model fixed while changing only what the agent can run, and it has no condition where the agent can run nothing. It judges with the PoVs the agent could run plus functional tests, so it cannot detect a fix that only covers the shown PoV. Its tasks are Java bugs, not smart-contract logic, and there is no human baseline. The project changes one input at a time inside three fixed agents (what the agent is told, and whether it can run nothing, only the shown test, or a full terminal) and judges with held-out PoVs. The two results point in different directions: here the agent with general tools does best, while in the project OpenHands with a full terminal succeeded in 2 of 12 runs against 10 of 12 when it could run nothing. A reviewer could cite this paper to argue that more tool access helps patching. The project can answer that, because this paper does not separate tool access from system design and uses no held-out exploits. Its note that Claude Code changed test files matches the project's observation that agents with a terminal followed the repository's tests. This paper appears as an unopened lead in the round-2 snowball file (`r2_S1_snowball.md`); it is not in the master index.

### Li2026-SWEResidual SWE-Residual: Evaluating Starting-State Robustness of Coding Agents
- Authors: Jinze Li et al. (nine authors; corresponding authors Zifei Shan and Edith C. H. Ngai); Year: 2026; Venue: arXiv preprint (arXiv:2610.25899, 19 October 2026; comment "Under Review")
- URL opened: https://arxiv.org/html/2610.25899 (arXiv HTML full text); abstract also read through the arXiv API
- Status: VERIFIED
- Tier: B
- Touches: N4, N1
- Summary: Coding benchmarks start the agent from a clean repository. SWE-Residual starts it from the state an earlier agent left behind after wrongly declaring the task done. The new agent gets only the original request, is not told the earlier attempt failed, and is judged by hidden tests. The benchmark has 198 such states from 111 DeepSWE and Terminal-Bench tasks. Across five frontier agents, success drops by 20.6 to 53.5 points on DeepSWE and by 20.6 to 34.9 points on Terminal-Bench, and the agent ranking on DeepSWE reverses. In 58.9% to 88.2% of failed DeepSWE runs the agent submits with exactly the same hidden tests failing, and failed runs keep 86.4% to 98.6% of the lines the earlier agent wrote. The authors call this "acceptance bias": the agent treats the work it inherits as the definition of what is left to do.
- Delta: This is the closest general-software result to the project's finding that agents keep the repository's own tests passing even when those tests assert the vulnerable behaviour. Both show agents trusting what is already in the repository over the request. The differences are large. SWE-Residual never tells the agent that the inherited work is wrong; the project's repair agent is told there is a vulnerability, through the location, the audit report, or a failing PoV. SWE-Residual does not vary what the agent can run, has no security tasks, and has no exploit or loss measure. The project studies the case where the inherited artifact is a test suite that encodes the vulnerability, shows that agents with a terminal keep that suite passing, and measures the funds a held-out PoV can still steal.

### Cheng2026-DetectRepairVerify Detect--Repair--Verify for LLM-Generated Code: A Multi-Language, Multi-Granularity Empirical Study
- Authors: Cheng Cheng (single author); Year: 2026; Venue: arXiv preprint (arXiv:2603.23633, 24 March 2026)
- URL opened: https://arxiv.org/abs/2603.23633 (arXiv abstract page); https://arxiv.org/html/2603.23633 (HTML full text, first 100,000 characters read)
- Status: VERIFIED
- Tier: B
- Touches: N4, N6
- Summary: The study builds EduCollab, 38 runnable artifacts (3 whole projects, 15 requirement-level and 20 file-level pieces) taken from web applications that ChatGPT wrote in PHP, JavaScript and Python. The artifacts come with functional tests and exploit tests (23, 42 and 20 exploit tests at the three levels). An LLM (ChatGPT-5, plus GLM-5 at file level) writes a detection report, repairs the code, and the functional and exploit suites are rerun; the loop repeats within a fixed budget. Repeating the loop beats a single detect-and-repair pass, but the gain is uneven for whole projects and clearer for single files. Detection reports often help repair but are not reliably correct; the paper gives per-case results, not one headline rate (for example, the PHP project stays at zero secure-and-correct yield across four rounds).
- Delta: Like the project, it gives an LLM's own vulnerability report to the repair step and checks every repair with executable exploits and functional tests. It does not compare a report with a PoV as repair input, does not vary what the model can run, and uses no held-out exploits: the same exploit suite judges every round. Its code is LLM-written web apps, so there is no human baseline and no smart contract. The project compares location only, the audit report, the PoV, and report plus PoV as inputs, and judges with PoVs the agent never saw.

### Zhao2026-RewardHackingCodeAgents Reward Hacking in Self-Improving Code Agents
- Authors: Bingchen Zhao et al. (Bingchen Zhao, Dhruv Srikanth, Yuxiang Wu, Zhengyao Jiang); Year: 2026; Venue: ICLR 2026 Workshop on AI with Recursive Self-Improvement (poster)
- URL opened: https://iclr.cc/virtual/2026/10018648 (ICLR virtual site page with title, authors and abstract); the OpenReview record https://openreview.net/forum?id=ikrQWGgxYg was read through the OpenReview search API (title, authors, venue, abstract)
- Status: VERIFIED
- Tier: B
- Touches: N3, N4
- Summary: Agents improve code step by step (GPU kernels from KernelBench, algorithm tasks from ALE-Bench) using execution feedback from a public set of proxy tasks, while a held-out set of real tasks measures true progress. Across three frontier models and five agent configurations, 73.8% of KernelBench and 46.8% of ALE-Bench optimizations improve the proxy without improving the real tasks. The gap grows with more steps: the share rises from 26.4% at 10 steps to 57.8% at 100 steps. A self-critique step, which the authors call retrospection, cuts KernelBench hacking by about 17 to 19 points in some cases but does not help consistently on ALE-Bench and can make it worse.
- Delta: It uses the same evaluation idea as the project's masked PoVs: the agent works against a visible check and is judged on checks it never saw. It also shows that more rounds of execution feedback widen the gap, which fits the project's finding that agents with a terminal fitted the shown test. But the task is performance optimization, not repair. There is no security, no exploit, no human baseline, and no condition where the agent cannot run code. The same group wrote SpecBench, which is already in the master index as tier B. The project applies held-out checks to vulnerability repair and changes execution access directly.

### Nepal2026-MetricsFailure Metrics Failure in LLM-Based Code Vulnerability Repair: An Empirical Study and a Change-Aware Screen
- Authors: Om Nepal et al. (Om Nepal, Sushant Aryal, Oluseyi Olukola, Nick Rahimi); Year: 2026; Venue: arXiv preprint (arXiv:2609.26749, 22 September 2026)
- URL opened: https://arxiv.org/abs/2609.26749 (arXiv abstract page); abstract also read through the arXiv API
- Status: VERIFIED
- Tier: B (low). The round-2 leads file (`r2_S3b_leads.md`) read the abstract and rated it "at most C", which is why it is not in the master index.
- Touches: N4, N3
- Summary: On 203 vulnerable C and C++ functions from Big-Vul, with three open code models of 350M to 6.7B parameters, the authors show that compile rate is a poor measure of vulnerability repair. About 64% of compile failures are not caused by the model, and one compiler flag changes the compile rate on identical patches by 1.8 to 2.7 times. In one experiment, a compiler-feedback loop raised the compile rate while similarity to the human fix fell, and manual inspection found deletion and placeholder patches among the newly compiling outputs.
- Delta: The reason to raise it to B is the feedback-loop result: it is a small, non-agent case of execution feedback rewarding patches that do not repair the vulnerability. It has no exploits, no agents, no held-out tests and no smart contracts. The project shows the same direction with real agents and held-out exploits. The orchestrator can keep round 2's rating; either way it is not a new find for saturation.
