### Chen2026-SecureVibeBench SecureVibeBench: Benchmarking Secure Vibe Coding of AI Agents via Reconstructing Vulnerability-Introducing Scenarios
- Authors: Junkai Chen et al. (13 authors, last author David Lo); Year: 2026; Venue: Proceedings of the 64th Annual Meeting of the Association for Computational Linguistics (ACL 2026), Volume 1: Long Papers, pp. 24144–24168, DOI 10.18653/v1/2026.acl-long.1107 (seen on the ACL Anthology page). The SusVibes reference list cites an earlier version titled "SecureAgentBench: Benchmarking Secure Code Generation under Realistic Vulnerability Scenarios" [uncertain that this is the same arXiv entry's first title].
- URL opened: https://arxiv.org/abs/2509.22097 (arXiv abstract record); https://arxiv.org/html/2509.22097v5 (full text); https://aclanthology.org/2026.acl-long.1107/ (publisher page)
- Status: VERIFIED
- Tier: A
- Touches: N1, N5, N6
- Properties: (a) partly. Each task rebuilds the code state in which a human introduced the vulnerability, and the proof-of-vulnerability (PoV) program checks whether the agent writes the same vulnerability. The only direct comparison with the human's code is static: Semgrep findings in agent code fall from 4.9% to 2.6% of tasks when findings also present in the human's own patch are discounted, which the authors read as humans introducing fewer issues but not none (2.3%). (b) yes: an ARVO-verified PoV for the known vulnerability, plus Semgrep for other issues; Semgrep flags are called "suspicious" and are not confirmed by any exploit. (c) yes: vulnerability-introducing commits from 41 OSS-Fuzz projects.
- Summary: 105 C/C++ tasks from 41 OSS-Fuzz projects, drawn from 4,993 collected vulnerabilities. An LLM writes each requirement from the commit message, the human's patch and the issue, with instructions to stay security-neutral; the authors then review the requirements by hand. Five agents (SWE-agent, OpenHands, Aider, Claude Code, Codex CLI) run with five LLMs, including Claude Sonnet 4.5 and GPT-5. The best setup (SWE-agent with Claude Sonnet 4.5) produces 23.8% correct-and-secure solutions; Codex CLI produces correct code that still contains the PoV-confirmed vulnerability in 21.8% of tasks, and Claude Code in 26.7% (full text, Table 4).
- Delta: This is the closest prior work to N1. It uses the same idea (start where the human introduced the bug, ask for the same feature, judge with the PoV) and three of the project's agent frameworks (Aider, OpenHands, Codex CLI, with Claude Sonnet 4.5). What it does that the project does not: 105 tasks at scale, C/C++ memory-safety bugs, a static check for other new issues, and differential functional tests against the human's patch. What the project does that it does not: Solidity business-logic and accounting bugs where the PoV steals funds (N2) and a loss estimate per exploit (N7); a control group of functions from the same commit that the human wrote correctly, where every flaw found by LLM review must be confirmed by a new PoV (N1, N6), while SecureVibeBench counts unconfirmed Semgrep flags; several PoVs per finding with held-out PoVs to judge repairs (N3); and the repair input study (N4). A further design difference: SecureVibeBench rebuilds the repository just before the vulnerability-introducing commit, while the project removes the function body from the audited code. The proposal should present SecureVibeBench as the direct precursor and state these differences plainly.

### Zhao2026-SusVibes Is Vibe Coding Safe? Benchmarking Vulnerability of Agent-Generated Code in Real-World Tasks
- Authors: Songwen Zhao et al. (6 authors); Year: 2026; Venue: Proceedings of the 43rd International Conference on Machine Learning (ICML 2026), PMLR volume 306 (seen on the PMLR page)
- URL opened: https://arxiv.org/abs/2512.03262 (arXiv abstract record); https://arxiv.org/html/2512.03262v4 (full text); https://proceedings.mlr.press/v306/zhao26ax.html (publisher page)
- Status: VERIFIED
- Tier: A
- Touches: N1, N5
- Properties: (a) partly: by construction the human's pre-fix code fails the security tests, but the paper does not report how often agents re-create the human's vulnerability, and it has no control group. (b) yes: security tests taken from the fix commit; they must fail on the pre-fix version and pass on the fixed version, and humans reviewed each one. (c) yes: tasks start from vulnerability-fixing commits; the feature is masked out of the commit just before the fix.
- Summary: 186 feature-request tasks from 100 Python repositories, covering 79 CWE types. An LLM writes each feature request from the masked code, with an instruction not to mention security, and each request is checked line by line against the secure implementation. Twelve agent settings (SWE-agent, OpenHands, Claude Code with Claude 4 Sonnet, Kimi K2, Gemini 2.5 Pro and Gemini 3 Pro) were tested. The best setting, SWE-agent with Claude 4 Sonnet, passes the functional tests on 57.0% of tasks but the security tests on 11.8%; 79.3% of its correct solutions are insecure. Telling the agent the target CWE raised the secure rate to 15.1% and lowered the functional rate to 55.4%; letting it pick CWEs from the list gave 14.5% and 50.0% (full text, Table 5).
- Delta: Same design idea as N1 in Python: re-implement a real feature where a human wrote insecure code and judge with an executable test. It is larger than the project and tests hint strategies. It starts from fix commits rather than tracing the vulnerability-introducing commit, compares no agent output with the human's code per task, has no control group, no repair round, no held-out tests and no loss measure. The project adds Solidity (N2), the control group with PoV-confirmed new flaws (N6), held-out PoVs for repair (N3), varied repair inputs and execution access (N4), and loss estimates (N7). The project's pilot result (when the request stated the rule that the fix restores, 12 of 15 runs avoided the bug) contrasts with SusVibes' result that naming the CWE helps little; the two manipulations differ, and the proposal should explain why.

(6 authors); Year: 2026; Venue: Proceedings of the 3rd International Workshop on Large Language Models For Code (LLM4Code '26), DOI 10.1145/3786181.3788703 (seen in the Crossref record and in the paper's ACM reference block). Earlier arXiv title: "SecRepoBench: Benchmarking LLMs for Secure Code Generation in Real-World Repositories" (seen as a cited title in the SecureVibeBench reference list).
- URL opened: https://arxiv.org/abs/2504.21205 (arXiv abstract record); https://arxiv.org/html/2504.21205v3 (full text); https://api.crossref.org/works/10.1145/3786181.3788703 (Crossref record)
- Status: VERIFIED
- Tier: A
- Touches: N1, N5
- Properties: (a) partly: the masked region is the code that the developer's fix changed, and the crash input must crash the developer's pre-patch code, so the human's version is the vulnerable reference; the paper does not measure how often models reproduce it (it only notes some literal memorization before the authors mutated the code). (b) yes: the OSS-Fuzz proof-of-concept input is run on the completed code; a crash means vulnerable. Correctness uses the developers' unit tests. ### Asare2023-CopilotVsHumans Is GitHub's Copilot as Bad as Humans at Introducing Vulnerabilities in Code?
- Authors: Owura Asare, Meiyappan Nagappan, N. Asokan; Year: 2023; Venue: Empirical Software Engineering (journal), DOI 10.1007/s10664-023-10380-1 (seen in the Crossref record)
- URL opened: https://arxiv.org/abs/2204.04741 (arXiv abstract record); https://arxiv.org/html/2204.04741v5 (full text)
- Status: VERIFIED
- Tier: A
- Touches: N1
- Properties: (a) yes: each scenario re-creates the file just before a human introduced a known vulnerability, and Copilot's suggestion is classed as the human's vulnerable code, the human's fix, or neither. (b) no: exact text match, then manual review by three coders; no tests or exploits, and no search for other vulnerabilities. (c) yes: Big-Vul C/C++ vulnerabilities and their fix commits.
- Summary: 153 scenarios selected from Big-Vul (C/C++, single-file, single-location changes). The prompt is the buggy file up to the vulnerable lines, so this is code completion, not a feature request. After manual recategorisation, Copilot reproduced the vulnerable code in 51 of 153 cases (33.3%) and the fix in 39 (25.5%); 63 (41.2%) were neither. The rate varied by CWE and by the year of the vulnerability, and the authors conclude that Copilot is "not as bad as human developers".
- Delta: The earliest study of the project's core comparison: same starting point as the human, outcome compared with what the human wrote. It uses one completion tool from 2022, text similarity and manual judgement instead of an executable test, and single-location C/C++ changes, with no control group, repair or loss. The project replaces text matching with a PoV that runs on both the human's and the agent's code, uses agents that write a whole function from a feature request, works on Solidity, and adds the control group (N1, N2, N6).

### Wu2026-LastSecureCode Last Secure Code Benchmark: Is the Code You Vibe Secure?
- Authors: Tianyi Wu et al. (15 authors); Year: 2026; Venue: arXiv preprint (arXiv:2610.14766, 10 October 2026)
- URL opened: https://arxiv.org/abs/2610.14766 (arXiv abstract record); https://arxiv.org/html/2610.14766v1 (full text)
- Status: VERIFIED
- Tier: A
- Touches: N1, N5
- Properties: (a) no: there is no human arm; the authors only note that some models reproduce the upstream implementation from memory. (b) yes: experts rewrote the security tests so that each drives a proof-of-concept attack through the program's external interface; each must fail on the vulnerable code and pass on the fixed code. (c) partly: 115 of 150 scenarios come from real CVEs through CVE-Factory (Luo et al., ICML 2026), and the agent starts from the vulnerable project with the patched code removed; 35 Java scenarios were written by experts from their companies' code.
- Summary: 450 tasks from 150 vulnerabilities in seven languages and 24 CWEs, at three sizes: fill in a function, write a file, or rebuild a source tree. Specifications ask only for function; a review agent and five experts remove clauses that require the vulnerable design or leak the fix, with more than 93% agreement in a 30-task double review. Six frontier agents pass 73.6% to 91.3% of tasks functionally but only 16.4% to 25.1% both functionally and securely (best: Claude Fable 5). Appending one sentence that asks for security raised joint success by 15.6 to 21.5 points for three of four models and by 1.1 points for the fourth.
- Delta: Closest on N5: it checks specifications for leaks of the fix and for clauses that force the vulnerable design, and it judges with attack-driving tests. It does not compare with the human's code, has no control group, no repair, no held-out tests and no loss measure, and its scenarios are mostly web and memory CWEs rather than smart-contract accounting bugs. The proposal can cite it for N5 and contrast its positive reminder effect with SusVibes and RealSec-bench, where reminders helped little or hurt.

### Vero2025-BaxBench BaxBench: Can LLMs Generate Correct and Secure Backends?
- Authors: Mark Vero et al. (8 authors, including Jingxuan He and Martin Vechev); Year: 2025; Venue: Proceedings of the 42nd International Conference on Machine Learning (ICML 2025), PMLR volume 267, first page 61344 (seen on the PMLR page)
- URL opened: https://arxiv.org/abs/2502.11844 (arXiv abstract record); https://arxiv.org/html/2502.11844v3 (full text); https://proceedings.mlr.press/v267/vero25a.html (publisher page)
- Status: VERIFIED
- Tier: A
- Touches: N1 (judging method), N6
- Properties: (a) no: human-written sample solutions were used only to validate tests and refine exploits. (b) yes: exploits written by security experts run end to end against the running backend in Docker. (c) no: synthetic backend scenarios.
- Summary: 392 backend-generation tasks, judged with functional tests and expert exploits covering 13 CWEs. The best model for correctness, OpenAI o1, reached 62%, and exploits succeeded on about half of the correct programs of each model. For Claude-3.5 Sonnet, pass@1 and secure pass@1 were 53.6% and 32.9% with no reminder, 45.5% and 34.5% with a generic security reminder, and 41.0% and 35.4% with an oracle reminder that lists the scenario's CWEs; inside OpenHands the same model went from 59.5% and 31.8% (no reminder) to 45.9% and 39.0% (oracle reminder) (full text, Table 2).
- Delta: Shares the project's main judging principle: an executable exploit, not a scanner, decides security. It also shows that reminders trade correctness for a small security gain. It has no human-written counterpart per task, no repository history, no repair round, and web vulnerabilities rather than DeFi accounting bugs; exploits are written per scenario, not for a specific human bug, and there is no loss measure.

### Liang2026-SecTDD Security Tests as Executable Specifications for LLM Code Generation: Benefits, Trade-offs, and Coverage Limits
- Authors: Yunhao Liang et al. (6 authors); Year: 2026; Venue: arXiv preprint (arXiv:2608.09740). The full text carries an ACM reference block for FSE 2027 [uncertain whether accepted; the arXiv comments field is empty].
- URL opened: https://arxiv.org/abs/2608.09740 (arXiv abstract record); https://arxiv.org/html/2608.09740v2 (full text)
- Status: VERIFIED
- Tier: A
- Touches: N3, N4
- Properties: (a) no. (b) yes: executable functional and security tests, split into a visible set and a hidden set. (c) no: tasks from CWEval, SALLM and CodeGuard+.
- Summary: SecTDD separates three factors: whether tests are shown upfront, whether failed runs trigger revision, and how failures are selected and shown. Visible and hidden tests are split by behaviour family or attack mechanism, not at random, so hidden cases keep the security property but change encodings, boundary values or the attack construction.
