## Sub-area 1. Finding the commit that introduced the bug (SZZ and its variants)

### Sliwerski2005-SZZ When Do Changes Induce Fixes? (On Fridays.)
- Authors: Jacek Śliwerski, Thomas Zimmermann, Andreas Zeller; Year: 2005; Venue: MSR 2005 (International Workshop on Mining Software Repositories), Saint Louis, Missouri (ACM footer on the author PDF; OpenAlex lists DOI 10.1145/1083142.1083147)
- URL opened: https://thomas-zimmermann.com/publications/files/sliwerski-msr-2005.pdf (author PDF)
- Status: VERIFIED
- Tier: B
- Touches: N1 (task construction)
- Summary: The original SZZ method. It links a version archive (CVS) to a bug database (Bugzilla), finds the fixing changes, and traces the lines they changed back to the earlier changes that introduced them ("fix-inducing changes"). In Mozilla and Eclipse, fix-inducing changes show distinct patterns in size and day of the week.
- Delta: The method the project's history search follows (blame the lines the fix or report points to). It was built for general bugs found through bug trackers, not for vulnerabilities named in audit reports, and it has no execution-based check.

### Bao2022-VSZZ V-SZZ: Automatic Identification of Version Ranges Affected by CVE Vulnerabilities
- Authors: Lingfeng Bao et al.; Year: 2022; Venue: ICSE 2022 (44th International Conference on Software Engineering), DOI 10.1145/3510003.3510113 (the ICSE 2022 program lists it as "SZZ for Vulnerability: Automatic Identification of Version Ranges Affected by CVE Vulnerabilities")
- URL opened: https://baolingfeng.github.io/papers/ICSE2022VSZZ.pdf (author PDF); https://conf.researchr.org/details/icse-2022/icse-2022-papers/76/SZZ-for-Vulnerability-Automatic-Identification-of-Version-Ranges-Affected-by-CVE-Vul (ICSE 2022 program page)
- Status: VERIFIED
- Tier: B
- Touches: N1 (task construction)
- Summary: Standard SZZ blames the commit that last modified the buggy lines, but vulnerabilities are usually introduced in early versions. V-SZZ uses line mapping to find the earliest commit that modified the vulnerable lines and treats it as the introducing commit. On 172 CVEs with hand-annotated introducing commits (5 C/C++ and 41 Java projects), 99 had wrong version data in NVD; V-SZZ reaches F1 of 0.736 (C/C++) and 0.630 (Java) for the introducing commit, and 0.928 and 0.952 for the affected versions.
- Delta: Directly relevant to the project's tracing rule. The project's script takes the commit that last changed most of the reported lines, which is the rule V-SZZ argues fails for vulnerabilities; V-SZZ takes the earliest. Neither rule is checked by execution in V-SZZ. The project can run its PoV on both candidates and on their parents to settle which one introduced the bug.

### daCosta2017-SZZFramework A Framework for Evaluating the Results of the SZZ Approach for Identifying Bug-Introducing Changes
- Authors: Daniel Alencar da Costa et al.; Year: 2017; Venue: IEEE Transactions on Software Engineering (OpenAlex lists 2016, the online date; DOI 10.1109/TSE.2016.2616306)
- URL opened: https://rebels.cs.uwaterloo.ca/papers/tse2017_dacosta.pdf (author PDF)
- Status: VERIFIED
- Tier: B
- Touches: N1 (task construction)
- Summary: Because a ground truth is not readily available, the authors judge five SZZ implementations on data from ten open source projects with three criteria: earliest bug appearance, future impact of changes, and realism of bug introduction. Earlier improvements to SZZ tend to inflate the number of wrongly identified bug-introducing changes; a single change may be blamed for hundreds of future bugs; at least 46% of bugs are attributed to changes years apart from one another.
- Delta: Gives criteria the project can apply to its own traced commits (for example, the "earliest bug appearance" check, which a PoV can test directly by execution). It covers general bugs, not vulnerabilities.

### RodriguezPerez2020-HowBugsAreBorn How Bugs Are Born: A Model to Identify How Bugs Are Introduced in Software Components
- Authors: Gema Rodríguez-Pérez et al.; Year: 2020; Venue: Empirical Software Engineering (OpenAlex record, DOI 10.1007/s10664-019-09781-y)
- URL opened: https://aserebre.win.tue.nl/EMSE2019.pdf (author manuscript PDF)
- Status: VERIFIED
- Tier: B
- Touches: N1 (task construction)
- Summary: Questions the assumption that "a bug was introduced by the lines of code that were modified to fix it". Proposes a model, based on the idea of a perfect test, that decides whether a bug is present after each change, and applies it by hand to 116 bugs in two projects; some bugs were not introduced by any change to the code (for example, changes in an external API). Four SZZ-based algorithms reach F-scores of 0.44 to 0.77, with at most 63% true positives.
- Delta: The "perfect test" idea is what the project's PoV provides: run the exploit on each candidate commit and its parent to find the first snapshot with the bug. The paper does this by hand reasoning for general bugs; the project can do it by execution for each finding, and should report findings whose cause lies outside the traced lines (for example, a change in a dependency or in another contract).

### Alexopoulos2022-VulnLifetimes How Long Do Vulnerabilities Live in the Code? A Large-Scale Empirical Measurement Study on FOSS Vulnerability Lifetimes
- Authors: Nikolaos Alexopoulos et al.; Year: 2022; Venue: 31st USENIX Security Symposium (USENIX Security 22), pp. 359-376
- URL opened: https://www.usenix.org/conference/usenixsecurity22/presentation/alexopoulos (USENIX publisher page)
- Status: VERIFIED
- Tier: C
