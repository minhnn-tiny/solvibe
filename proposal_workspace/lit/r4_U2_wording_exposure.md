## New papers (tier A and B)

### Shahriar2026-WordsSpeakLouder Words Speak Louder Than Code: Investigating Cognitive Heuristics in LLM-Based Code Vulnerability Detection
- Authors: Asif Shahriar et al. (Hongyu Cai, Hadjer Benkraouda, Gang Wang, Z. Berkay Celik); Year: 2026 (arXiv v1 29 June 2026, v2 15 October 2026); Venue: IEEE Symposium on Security and Privacy (S&P) 2027, per the arXiv comment "Accepted at IEEE Symposium on Security and Privacy (IEEE S&P) 2027"
- URL opened: https://arxiv.org/abs/2606.30587 (arXiv abstract page)
- Status: VERIFIED
- Tier: B
- Touches: N6
- Summary: The paper asks whether an LLM's verdict on whether code is vulnerable depends on context that has nothing to do with the code. It keeps the code fixed and changes only the surrounding text. Three kinds of text are tested: who wrote the code (a halo effect), how the task and its consequences are described (framing), and earlier analysis results (anchoring). All eight LLMs tested, across three programming languages, were affected. The average rate at which verdicts changed was 33.2% for framing, 23.5% for anchoring and 18.4% for author attribution. Models often switched from "safe" to "vulnerable" without finding the real flaw. A black-box attack built on these effects suppressed up to 97% of vulnerabilities the models had found before.
- Delta: The paper shows that an LLM security review changes its verdict when it is told who wrote the code or what is at stake. The project's control-group review (N6) runs the same prompt on agent code and on human code. This result means the prompt must not say, or hint, which version an agent wrote, and the task wording must be exactly the same for both versions. The project's rule that every reported flaw needs a confirming PoV removes false alarms caused by such wording. It does not recover flaws the reviewer missed because of the wording. The paper does not compare agent code with human code, does not confirm findings with executable tests, and does not cover Solidity or business-logic bugs in smart contracts. The project does not vary the context around the code.

### Gong2026-AFCRA Adaptive Code Revision Attacks on AI Pull Request Reviewers
- Authors: Jingzhi Gong et al. (Jie M. Zhang, Gunel Jahangirova, Meng Wang); Year: 2026 (arXiv v1 4 October 2026); Venue: arXiv preprint
- URL opened: https://arxiv.org/abs/2610.05399 (arXiv abstract page)
- Status: VERIFIED
- Tier: B
- Touches: N3, N6
- Summary: An AI pull request reviewer explains what must be fixed before it approves code. An attacker can use that explanation to fix the reported problem while keeping a vulnerability in the revised code. The authors call this AFCRA, an attack that revises code using the reviewer's feedback. They build AFCRA-Bench from 159 disclosed vulnerabilities, each with executable exploits. The exploits separate real repairs from revisions that keep the vulnerability. Over five rounds of review with Sonnet 5 and GPT-5.5 as reviewers, AFCRA succeeded 2.5 times and 12.5 times as often as the strongest attack that changes only text or comments. In the case studies, reviewers accepted fixes for the reported problem and missed the vulnerability that was still there.
- Delta: The paper shows the failure the project found in its repair round: a change that removes the reported problem but leaves the exploit working. It also shows that only an executable exploit reveals this, because the LLM reviewer approves the change. The paper studies an attacker who keeps the vulnerability on purpose and an LLM reviewer who judges the change. The project studies agents that try honestly to repair, and it judges them with held-out PoVs that the agent never sees (N3). It also varies the repair input and what the agent can run (N4). The paper does not hold exploits back from the code author, does not compare agents with human developers, and does not cover smart contracts or measure losses. Its finding that LLM reviewers approve repairs while a vulnerability survives supports the project's rule that LLM review findings (N6) must be confirmed by executable tests.

### Kordonsky2026-FSTab Extracting Recurring Vulnerabilities from Black-Box LLM-Generated Software
- Authors: Tomer Kordonsky et al. (Amit LeVi, Maayan Yamin, Noam Benzimra, Avi Mendelson); Year: 2026 (arXiv v1 2 February 2026, v4 5 June 2026); Venue: ICML 2026 Second Workshop on Agents in the Wild: Safety, Security, and Beyond (AIWILD), per the arXiv comment
- URL opened: https://arxiv.org/abs/2602.04894 (arXiv abstract page)
- Status: VERIFIED
- Tier: B
- Touches: N1, N5
- Summary: LLM-generated software tends to follow recurring templates, so its vulnerabilities are predictable. The authors build a table, called FSTab, that links features visible in an application's frontend to backend vulnerabilities, separately for each model. An attacker can use it to predict backend vulnerabilities from the frontend alone, without the source code. The same table also measures how consistently a model repeats the same vulnerabilities across programs, across rewordings of the task that keep its meaning, and across application domains. On GPT-5.2, Claude-4.5 Opus and Gemini-3 Pro, it reached up to 94% attack success and 93% vulnerability coverage on the Internal Tools domain (Claude-4.5 Opus), even when that domain was left out of training. The abstract does not say how the vulnerabilities were detected.
- Delta: The paper finds that a model's vulnerabilities persist when the task is reworded without changing its meaning. This sits next to Minimal Prompt Perturbations (indexed), which found that tiny edits can flip security. In the project's pilot, the request variants changed the content of the request: one described the human's design, the other stated the rule the fix restores. That content decided whether the bug came back. FSTab suggests that rewording which keeps the meaning should matter less than changing that content, so the project can treat its request variants as content changes and not as noise from wording. The paper generates whole applications from scratch and has no human version to compare against. It does not confirm vulnerabilities with exploits and does not cover smart contracts. The project starts from the audited repository and compares the agent with the human developer on the same function.

### Improta2025-QualityInQualityOut Quality In, Quality Out: Investigating Training Data's Role in AI Code Generation
- Authors: Cristina Improta et al. (Rosalia Tufano, Pietro Liguori, Domenico Cotroneo, Gabriele Bavota); Year: 2025; Venue: 33rd IEEE/ACM International Conference on Program Comprehension (ICPC 2025), DOI 10.1109/ICPC66645.2025.00056 (DOI from OpenAlex; acceptance from the arXiv comment)
- URL opened: https://arxiv.org/abs/2503.11402 (arXiv abstract page); OpenAlex record for the ICPC DOI
- Status: VERIFIED
- Tier: B
- Touches: N1
- Summary: The paper tests whether code with quality problems in the training data leads a model to generate code with quality problems. The authors fine-tuned a pre-trained model on a large training set. In that set, 4.98% of the functions had at least one issue related to security, maintainability, best practices or similar. The model then generated 551k Python functions, and 5.85% of them had at least one issue. They removed the flawed functions from the training set and fine-tuned a second model. It was as functionally correct as the first, and only 2.16% of its functions had issues, a statistically significant drop.
- Delta: This is a controlled experiment showing that flawed code a model saw in training raises the rate of flawed code it writes. That is one possible reason an agent rewrites the human's bug, besides memorizing the specific repository (Model See, Model Do?, indexed). The project cannot run this kind of experiment because its models are closed. The models' training data ends before the findings were published, but the vulnerable code was public earlier. So the project would need a black-box exposure check, for example asking the model to complete the human's function from its first lines and measuring how close the output is to the original. The paper uses function-level Python, fine-tuned open models and static checks. It has no human comparison, no executable exploits and no smart contracts.

### Akli2026-UnderSpecification When Prompt Under-Specification Improves Code Correctness: An Exploratory Study of Prompt Wording and Structure Effects on LLM-Based Code Generation
- Authors: Amal Akli et al. (Mike Papadakis, Maxime Cordy, Yves Le Traon); Year: 2026 (arXiv v1 27 April 2026); Venue: arXiv preprint
- URL opened: https://arxiv.org/abs/2604.24712 (arXiv abstract page)
- Status: VERIFIED
- Tier: B (borderline B or C: it measures correctness, not security)
- Touches: N5
- Summary: The paper tests whether prompt edits that remove detail from a task hurt the correctness of generated code, using 10 models on HumanEval and the more detailed LiveCodeBench. The edits hurt correctness on HumanEval but had almost no net effect on LiveCodeBench. LiveCodeBench tasks repeat information across the description, constraints, examples and input and output conventions. Some edits improved correctness. They broke misleading words or structure that led the model to a wrong solution it seemed to recall from similar tasks. A manual analysis names the ways this happens: disrupting over-fitted terminology, removing misleading constraints, and removing identifier names that trigger the wrong solution.
- Delta: The paper shows that particular words in a task description can pull a model toward a solution it has seen before, and it lists which kinds of wording do this. That bears on how the project writes feature requests (N5). A request that uses the human's identifiers or describes the human's design may steer the agent toward the human's code. In the pilot, requests that described the human's design led to the bug in all 13 compiled runs. The paper measures only functional correctness on standalone function-level tasks. The project measures security on repository-level agent tasks, judges the result with a PoV, and checks that its requests do not hint at the bug or the fix.

### Bharadwaj2026-SecDrift SecDrift: Measuring Sector-Conditioned Security Drift in AI-Generated Code
- Authors: Narayanaswami Natraj Bharadwaj and Dhivya Chandramouleeswaran; Year: 2026 (arXiv v1 28 July 2026); Venue: arXiv preprint
- URL opened: https://arxiv.org/abs/2607.25225 (arXiv abstract page)
- Status: VERIFIED
- Tier: B. **Already seen:** round 2 screened it as C (`r2_S3a_leads.md`), but it is not in the index. I re-tier it for thread 2. It is not counted as new in the table.
- Touches: N5
- Summary: The paper tests whether naming an industry sector in a coding prompt changes how often the generated code is vulnerable. The task stays fixed and only the domain words are swapped, and each sector prompt is compared with a matching neutral prompt. It covers 7 LLMs (6 gave code that could be analysed), 8 critical-infrastructure sectors, 9 CWE categories and 5 repeats, for 5,355 evaluations, judged by static analysis. The vulnerability rates were 14.0% for industry prompts and 11.4% for neutral ones. The difference was not significant (Fisher's exact p = 0.24) and came from two CWE categories. None of the 8 sectors drifted measurably from the neutral prompt. The choice of model mattered more: rates ranged from 11.6% to 16.1%. The abstract's numbers do not agree with each other: it calls the gap "-2.7pp" and says industry prompts "appear more secure", although 14.0% is higher than 11.4% [uncertain which is right].
- Delta: The paper gives a statistical test of a change in task wording that keeps the task's meaning, with a matched neutral prompt and a placebo sector. It finds no effect. The project's request variants change what the request says: one describes the design, the other states the rule. SecDrift's null result supports reading the pilot's effect as coming from that content, not from surface wording. The project could borrow the matched-baseline and placebo design to check that its neutral requests do not hint at the bug. The paper uses synthetic tasks and static analysis, has no human version and no exploits, and does not cover smart contracts.
